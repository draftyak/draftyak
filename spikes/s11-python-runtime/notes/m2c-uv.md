# uv 0.13.1 and Pyodide 314 (note for M2c)

Checked on 2026-10-17 with uv 0.13.1 (`62faed335 2026-10-13`), offline (`--offline`, nothing downloaded). Plan §4 DX says `draftyak-plugin build` runs uv "inside a `cpython-3.14.2-emscripten-wasm32-musl` environment (uv has no Pyodide 314 target)". What uv 0.13.1 actually offers:

- **Interpreter.** `uv python list --all-platforms --only-downloads --offline` lists `pyodide-3.14.2-emscripten-wasm32-musl` (implementation `pyodide`), whose download is `https://github.com/pyodide/pyodide/releases/download/314.0.7/xbuildenv-314.0.7.tar.gz`: Pyodide 314.0.7's cross-build environment, the release S11 pins. It also lists 3.13.2 (0.29.5), 3.12.7 (0.27.8) and 3.11.3 (0.25.1). There is no `cpython-*-emscripten-*` key, so M2c should name the `pyodide-3.14.2-emscripten-wasm32-musl` key.
- **Resolution target.** `--python-platform` (`uv pip install`, `uv pip compile`) accepts `wasm32-pyodide2024` and `wasm32-pyodide2025`, but no 2026 value, while Pyodide 314.0.7's C-extension wheels are tagged `cp314-cp314-pyemscripten_2026_0_wasm32` (e.g. `pydantic_core-2.41.5-…`). uv 0.13.1 therefore can't pick C-extension wheels for this ABI. Pure `py3-none-any` wheels resolve for any platform.
- **What that means for the build.** Resolve and hash-pin pure-Python dependencies with uv (`--require-hashes`, `--no-build`, explicit indexes), and take C-extension wheels from Pyodide's own `pyodide-lock.json` by `file_name` and `sha256`, the way `scripts/fetch-runtime.ts` takes them from the pinned index `https://cdn.jsdelivr.net/pyodide/v314.0.7/full/`. Re-check `--python-platform` on each uv bump: a `wasm32-pyodide2026` value would let uv resolve both kinds.
- **Not run here.** `uv python install pyodide-3.14.2-emscripten-wasm32-musl` downloads from github.com, which this item's network rules don't allow; M2c should try it first.
