# S7b: the Sign in with ChatGPT session (M0.27, session 1)

The owner's part of S7 takes about 20 minutes, most of it the sign-in and the consent screen. The live test, `test/siwc.live.test.ts`, does the rest through `test/live-session.ts`, the same procedure the rehearsals run against M0.26's fakes:

1. It checks the opt-in and the shell, then consumes the opt-in.
2. It revokes any tokens an earlier run left in `.env.live`, and stops, keeping them, if that isn't confirmed.
3. It signs in through the system browser on `127.0.0.1:1455`, refusing first if another program holds the port, and stores the tokens only through the kit's `saveEnvLive`.
4. It drafts once with `text.format`, then once with `submit_draft` in each place a tool can go: a namespace, an `additional_tools` item, and the top level.
5. It hands the session to a second local process, the hub (`test/transfer-child.ts`), and forgets it. The hub drafts once, refreshes, revokes and forgets. With `DRAFTYAK_S7_DEFERRED_MIN` set, it first keeps the session until its access token has expired and drafts once more (After expiry, below).
6. It drafts twice with an API key, if `DY_LIVE_RESPONSES_API_KEY` is set and the key lists a model it may use (Models, below).
7. It deletes every `DY_LIVE_SIWC_*` entry and writes `evidence/live.json`.

The evidence holds shapes, sizes, codes and request IDs hashed with a key that is never stored. It never holds a token, prompt or draft text, account ID or e-mail address.

## Before the session (orchestrator, about 5 minutes)

Work from the root of a clean checkout of `m0` that includes M0.27: the main checkout `C:/dev/draftyak` or a fresh worktree. The evidence is written into that checkout, and its fingerprint must read `dirty: false`.

1. Run `git status --porcelain`; it prints nothing. Then run `pnpm install --frozen-lockfile`.
2. Run the rehearsal: `pnpm --filter @draftyak/spike-s07-siwc test` (about 2–4 minutes on a busy machine).
3. Check that no `OPENAI_*` variable is set (the run refuses otherwise) and that nothing listens on port 1455. A Codex CLI sign-in in progress would.
4. Check that no benchmark holds the kit's machine-wide lock: `%LOCALAPPDATA%\draftyak-dev\bench.lock.owner` is missing, or names a process that no longer runs (its `pid`, in Task Manager). The run waits at most 4 minutes for that lock and then fails as `machine-busy`, with the opt-in already used, so hold sibling benchmarks back for the session.
5. Ask the owner about plan usage. On ChatGPT Plus, "the five-hour usage limit is shared across all apps where they use their ChatGPT plan" (Accounts and sessions), Codex included, so the drafts can end `fails(USAGE_LIMIT)`. The owner checks ChatGPT Settings → Usage (https://chatgpt.com/settings/usage) for room, and Codex pauses for the session if it uses the same account. On Pro the five-hour limit doesn't apply.
6. Run `node spikes/s07-siwc/test/session-env.ts status`. Expect `.env.live: C:\dev\draftyak\.env.live (git ignores it)` and `not set` for every `DY_LIVE_SIWC_*` name. If the second part reads anything other than `git ignores it`, stop and fix that first.
7. Check that `spikes/s07-siwc/evidence/live.json` doesn't exist yet. If it does, it is an earlier session's evidence: commit or move it, or opt in with `--again` in step 3 below.

During step 5:

- **No tab opened:** open the address the run printed after `open this address:`.
- **A second tab opened:** the code exchange failed with `invalid_grant`, and the run signs in again with the client issued to the first attempt. Sign in once more.
- **OpenAI shows an error page instead of the consent screen** (not eligible, not available, something went wrong): note its wording without personal details and close the tab. The orchestrator then runs `node spikes/s07-siwc/test/session-env.ts stop`, and the run ends within seconds as `signin: blocked(stopped)`; a stop sent while the run still waits for the lock ends it before any browser opens. Declining on the consent screen ends it as `signin: blocked(SIGN_IN_FAILED:access_denied)`. Either way the run still writes the evidence, revokes nothing because nothing was issued, and drafts with the API key if one is set and a model is found. After an error page that refuses the account (not eligible, not available), ADR 0009 records `Not run` with the API-key fallback. A page that only says something went wrong calls for another run, and the same page on that run means `Not run`; a decline, or a stop with no error page, calls for another run (What ADR 0009 records, below).
- **Nothing happens for 8 minutes:** the sign-in times out as `signin: blocked(SIGN_IN_FAILED:timeout)`.

Models: the plan drafts use the first model that `GET /v1/models` lists as `visibility: "list"`, in the server's order. If the list can't be read, they use `gpt-6.1-sol`, the model in the docs' example (Models and inference, still at its recorded SHA-256 on 2026-10-18). Before the plan drafts, it also prints the slugs the list marks `visibility: "list"`, in the server's order (`Listed models, in the server's order: …`), so a rerun after a refused model can take the next one through `DRAFTYAK_S7_MODEL`.

## After expiry

Access tokens last an hour (Token reference), and drafts come on demand, often hours apart, so most real drafts call `Session.accessToken()` after the access token has expired, and it refreshes then. The hub's own refresh, minutes after the sign-in, doesn't cover that case. `DRAFTYAK_S7_DEFERRED_MIN` adds a step that does:

- **The setting.** `DRAFTYAK_S7_DEFERRED_MIN`, set in the shell like `DRAFTYAK_S7_MODEL`: the longest the hub may wait, in whole minutes from 1 to 120. Unset, the step is off. Any other value stops the run before the sign-in with `refusing to start: DRAFTYAK_S7_DEFERRED_MIN must be whole minutes from 1 to 120; …`, and the opt-in is kept. Session 1 uses 70. In Git Bash: `DRAFTYAK_S7_DEFERRED_MIN=70 pnpm --filter @draftyak/spike-s07-siwc test:live --reporter=verbose`. In PowerShell, where that prefix isn't a command: `$env:DRAFTYAK_S7_DEFERRED_MIN = '70'; pnpm --filter @draftyak/spike-s07-siwc test:live --reporter=verbose`, then `Remove-Item Env:DRAFTYAK_S7_DEFERRED_MIN` once the run has ended.
- **The step.** After its refresh, the hub keeps the session until 3 minutes after that refresh's access token expires. It then drafts once more, with its first draft's model and structure, through the broker with a token from `Session.accessToken()`, which refreshes first, as the product would. Then it revokes the newest tokens and checks them as before. If that moment is more than the cap away, it revokes at once, and the details say `after expiry: not run (due in <n> min, over the <cap>-minute cap)`. A failed refresh or draft after expiry never skips the revocation: after a refresh refused as unusable, the hub revokes the newest refresh token it holds.
- **Timing.** The run lasts about the tokens' lifetime plus 3 minutes longer, about 63 minutes with one-hour tokens, with nothing for the owner to do. Before the hub starts, the run says how long it expects to wait, from the lifetime of the tokens handed over (`After expiry: the hub process keeps the session until 3 minutes after its access token expires, about 63 minutes …`, or `… past the <cap>-minute cap. It most likely revokes the session without that step …`); the hub decides from its own refresh's tokens. Either way, the run then prints nothing more until the hub has ended (`The hub process has ended. After expiry: …`), at most the cap plus about 13 minutes later. Keep this PC on mains power and awake, with no sleep, hibernation or restart, until the run has ended. The wait holds neither the kit's machine-wide lock nor port 1455. The live test's time limit and the hub's grow by the cap plus one more refresh, draft and revocation.
- **Removing DraftYak** in ChatGPT's settings (step 7) waits until the run has ended; the next morning is fine. Removed during the wait, the session ends at OpenAI, and the refresh after expiry fails for that reason instead.
- **The details** add `after expiry: refreshed <true|false> (rotated <true|false>, <n> s after expiry, idle <m> min), draft <ok|code>`, and the evidence adds `transfer.deferred` (What ADR 0009 records, below).

## What the lines mean

| Line | Values | Then |
|---|---|---|
| `signin:` | `ok`, or `blocked(<code>[:<reason>])`, such as `blocked(SIGN_IN_FAILED:access_denied)`, `blocked(stopped)` or `blocked(ID_TOKEN_INVALID:audience)` | When blocked, the drafts and the transfer read `not-run(signin blocked)`. If OpenAI issued tokens before the spike refused them, they are revoked anyway. |
| `text.format:` | `ok`; `unsupported`, when the route refused the structure's own fields (`UNSUPPORTED_CAPABILITY`, or a 400, whose `param` names `text`); `fails(<code>[:<param>])` for any other refusal, such as `fails(UNSUPPORTED_CAPABILITY:model)`, `fails(ROUTE_NOT_SUPPORTED)`, `fails(NOT_ELIGIBLE)` or `fails(USAGE_LIMIT)`; `fails(refusal)`, `fails(timeout)`; `not-run(<why>)` | `details: desktop drafts:` gives each structure's result, with the code and `param` behind an `unsupported`. |
| `submit_draft:` | `ok` when any placement drafted; `unsupported` when every placement was refused for its own fields (`tools`, `tool_choice`, or the `additional_tools` item, `input[0]`); else the first `fails(…)` | The placements that worked go into ADR 0009 and plan §5. |
| `transfer:` | `ok` (the hub took the session, drafted like the desktop and refreshed it; with the step after expiry, its refresh after expiry also worked, and so did the draft after it when it drafted, unless the step didn't run, which only `details: after expiry: not run (…)` shows); `fails(TRANSFER_REFUSED:<detail>)`; `fails(<code>:<detail>)` when the hub took it but couldn't go on, such as `fails(SIGN_IN_FAILED:discovery: issuer)`; `fails(deferred-refresh:<code>)` when its refresh after expiry failed, such as `fails(deferred-refresh:REAUTH_REQUIRED)`; `fails(deferred-draft:<code>)` when its draft after expiry failed and its first draft worked; `fails(draft:<code>)`; `fails(refresh:<code>)`; `fails(exit <code>)` when it gave no result; `not-run(<why>)` | When the hub refused the session, gave no result, or took it without sending a refresh or revoking it, this process revokes its own copy. |
| `revoked:` | `yes`, or `no(<reason>)` | Anything but `yes` fails the test, and the owner removes DraftYak in ChatGPT's settings (step 7). |

`revoked: yes` means every refresh token the run was issued was revoked with a 200 and then refused as invalid (`invalid_grant`, `invalid_refresh_token` or `refresh_token_invalidated`) when tried once more. The 200 alone proves nothing: "An empty HTTP `200` is the revocation success response, including for an already-invalid token" (Accounts and sessions), and Self-hosted VMs adds that "Host-specific usage attribution and revocation of ChatGPT plan access for transferred sessions are not yet available." The reasons for `no`:

- `no(revocation unconfirmed)`: the revocation endpoint didn't answer 200.
- `no(revocation unconfirmed: probe <code>[:<upstream code>])`: the token tried once more was refused for another reason, such as a 429, a 5xx, no answer, an incomplete answer or `refresh_token_reused`.
- `no(the revoked refresh token still works)`: it refreshed. The run revoked the new token at once and never used it.
- `no(revocation unconfirmed: refresh_token_reused)`, `no(revocation unconfirmed: the hub's refresh got no answer)`, `no(revocation unconfirmed: the hub's refresh after expiry got no answer)` or `no(revocation unconfirmed: the hub's refresh after expiry was answered but not kept)`: one of the hub's own refreshes may have left a newer token than the one it revoked.
- `no(hub process ended without a result)`: this process revoked its copy, but the hub may have refreshed it first.
- `no(no refresh token; remove DraftYak in ChatGPT)`: the grant had no `offline_access`, so there was nothing to revoke.
- `no(entries left in .env.live)`: a `DY_LIVE_SIWC_*` entry was back after the cleanup, such as a late `stop`.

Before anything is recorded, the run can also stop with a message and no evidence. Either fix the cause and run again (the first three), or opt in again first (the rest):

- `refusing to start: OPENAI_… set in this shell`: unset the variables. The opt-in is kept.
- `refusing to start: live.json holds an earlier session's evidence`: commit or move it, or opt in with `--again`.
- `the owner hasn't opted in`: the test skips. Under `DRAFTYAK_STRICT_SKIPS=1` it fails instead.
- `127.0.0.1:1455 is held by another program`: close the other program. This check runs before any browser opens.
- `… didn't answer`: a network problem. Tokens an earlier run left in `.env.live` stay there.
- `an earlier run's tokens in .env.live weren't revoked: …`: they stay there. Run again later, or the owner removes DraftYak in ChatGPT's settings and the orchestrator runs `forget tokens`.
- `machine-busy` after `bench lock: waiting for …`: the run holds the kit's machine-wide lock while port 1455 is bound and waits up to 4 minutes for another benchmark to release it. Stop the benchmark.

If a run fails after the sign-in (an error, a timeout, an interrupted test), it revokes what it still holds before it ends and prints each outcome as `After the failure, <which tokens>: revoked <yes or no(…)>`. Tokens in `.env.live` whose revocation isn't confirmed stay there, `status` shows them as `set`, and the next opted-in run revokes them before it signs in. Tokens the run no longer holds, such as those handed to the hub, can't be kept: the owner removes DraftYak in ChatGPT's settings. If no run follows, the owner removes DraftYak there, then the orchestrator runs `forget tokens`.

## What ADR 0009 records (M0.27's second half)

- **Decision.** These rules are fixed before the session, so every line the run prints leads to one decision, or to another run before ADR 0009 is written:
  - **`Go`** needs `signin: ok` and at least one structure `ok`, with the structured-output path the plan route takes: `text.format`, or `submit_draft` and which placements work. That updates plan §5's `tools=[submit_draft]` wording. A failure on the other structure line doesn't change it. The transfer and the step after expiry can then limit it (below).
  - **`Not run`** only when OpenAI itself refuses: an error page in place of the consent screen that refuses the account (not eligible, not available), or one that only says something went wrong on two runs, whatever the `signin:` line then reads (`blocked(stopped)` after the orchestrator's stop); an error OpenAI sends back in place of a code without the owner declining (`signin: blocked(SIGN_IN_FAILED:<error>)` with `authorization refused` in `signIn.attempts[].error.detail`, `access_denied` included; `server_error` and `temporarily_unavailable` call for another run, and `no_code`, a callback with neither a code nor an error, is traced); with no structure `ok`, drafts that fail with `ROUTE_NOT_SUPPORTED` or with a refusal that `drafts[].error.plugin` reads as `PERMISSION_DENIED` (`NOT_ELIGIBLE`, `SCOPE_NOT_AUTHORIZED`, or `ADMISSION_REFUSED` or `API_ERROR` with a 403); or a grant that leaves plan usage off (`not-run(plan usage off)` or `not-run(no refresh token)`) though the owner allowed it on the consent screen. ADR 0009 then records the API-key fallback (`ai-responses-api` in `api-key` mode) and API-key mode's results, if a key was set. A refusal the trace shows DraftYak's own request caused is fixed and run again instead.
  - **`No-go`**, with the same fallback, when both structure lines read `unsupported` and the route refused them: the plan route takes neither structure. A 400 behind an `unsupported` (`API_ERROR:<param>` in `details: desktop drafts:`) counts only once the trace (`drafts[].error`, `drafts[].upstream[].errorBody`, and API-key mode's drafts if a key was set) shows the plan route refused a request the API takes; a request DraftYak got wrong is fixed and run again.
  - **Another run** for anything else that leaves no structure `ok`, and before `Not run` or `No-go` whenever a structure line calls for one. A refusal by the spike's own checks is fixed first: `signin: blocked(…)` from discovery (`SIGN_IN_FAILED:discovery: …`), the ID token (`ID_TOKEN_INVALID:…`), the callback or the token response (`SIGN_IN_FAILED:registration incomplete`, `:the callback named another client` or `:token response incomplete`), and drafts read as `fails(invalid)`. A decline the owner made (`signin: blocked(SIGN_IN_FAILED:access_denied)`, or plan usage turned off on the consent screen), the 8-minute timeout (`signin: blocked(SIGN_IN_FAILED:timeout)`), a stop with no error page (`signin: blocked(stopped)`), a page that only says something went wrong, the first time, and a temporary failure (`fails(UNAVAILABLE)`, `fails(STREAM_INTERRUPTED)`, `fails(STREAM_FAILED)`, `fails(timeout)`, or `fails(API_ERROR)` with a 429 or 5xx in `drafts[].error.status`) need no fix. A temporary failure that repeats on the next run, a callback's `server_error` or `temporarily_unavailable` included, is traced like any other code. So is a `fails(STREAM_FAILED)` whose `drafts[].error.apiCode` isn't a temporary one: `STREAM_FAILED` is the spike's code for any error inside the stream it doesn't know. Two failures call for another run, not `Not run`: `fails(USAGE_LIMIT)`, the plan's limit (on Plus, a five-hour window every app on the plan shares), after the window resets; and `fails(UNSUPPORTED_CAPABILITY:model)`, a refused model, with `DRAFTYAK_S7_MODEL` set to another model the account lists (`models.listedSlugs`); with none left, it is traced like any other code. `fails(refusal)`, the model declining the prompt, and `fails(incomplete:<reason>)` are traced and run again, never `Not run`. `fails(BROKER_REFUSED)`, the broker's own refusal, is fixed first. Any other code is traced in the evidence (`signIn.attempts[]`, `authCalls`, `drafts[]`) and fixed where the cause is DraftYak's; a code the trace shows is OpenAI's refusal leads to `Not run`.
  - **The transfer.** `transfer: ok` shows the documented transfer works technically; it is allowed on headless and VPS hubs only if OpenAI says yes. `fails(refresh:<code>)` comes from the run's only refresh before expiry, which the hub forces minutes after the sign-in whatever `earliest_refresh_at` says (`signIn.token.earliestRefreshAt`). Refused while that still pointed ahead, it is the spike's own early refresh, fixed and run again. Otherwise `fails(refresh:REAUTH_REQUIRED)` or `fails(refresh:INVALID_CLIENT)` is judged like a refresh after expiry refused as unusable (below). `fails(draft:<code>)` with a code that refuses the hub's session, such as `fails(draft:ADMISSION_REFUSED)` or `fails(draft:NOT_ELIGIBLE)`, turns `Go` into `Go with fallback`, with headless hubs on the API key. A `fails(refresh:…)` or `fails(draft:…)` whose code calls for another run on the desktop, such as `USAGE_LIMIT`, `UNAVAILABLE`, `STREAM_INTERRUPTED` or `aborted` (the desktop's `timeout`), calls for one here too, and the hub's own refusals and failures (`fails(TRANSFER_REFUSED:…)`, `fails(SIGN_IN_FAILED:discovery: …)`, `fails(ERROR)`, `fails(exit <code>)`) are fixed and run again, like the spike's own refusals above. Any other code is traced as on the desktop, with `Go with fallback` in place of `Not run`. `fails(deferred-refresh:…)` and `fails(deferred-draft:…)` aren't failed transfers: the hub took the session and refreshed it, so the transfer counts as `ok`, or as `fails(draft:<code>)` if `details: hub process:` shows the hub's first draft failing. `transfer: not-run(…)` comes only with no tokens to hand over, a case the rules above decide. When the sign-in granted plan usage, `transfer.planUsage` `disabled` means the hub's forced refresh came back listing scopes without `chatgpt.tokens.use.direct`. Whatever the `transfer:` and `after expiry:` lines read, it is traced and judged like `PLAN_USAGE_DISABLED` after expiry (below). The owner decides headless-hub use at the gate.
  - **After expiry,** judged apart from the transfer, from the `after expiry:` detail and `transfer.deferred`:
    - **Works:** `refreshed true (…), draft ok`. A session outlives its first hour on the product path, where `Session.accessToken()` refreshes once the access token has expired.
    - **Refused as unusable:** `fails(deferred-refresh:REAUTH_REQUIRED)`, from `invalid_grant` or another code for an unusable refresh token other than `refresh_token_reused` (`transfer.deferred.apiCode`), or `fails(deferred-refresh:INVALID_CLIENT)`, the client that refreshed before the wait refused after it. On the product path a session then ends with its first access token: the decision is at most `Go with fallback`, M7 must keep sessions alive another way and show it before plan usage ships, and the owner decides at the gate.
    - **Answered but not kept:** `refreshed false (…)` and `fails(deferred-refresh:SIGN_IN_FAILED)`, with a 2xx in `transfer.deferred.refresh.status` and `token response incomplete` in `transfer.deferred.detail`: OpenAI answered the refresh, but the spike refused the answer, and `revoked:` reads `no(revocation unconfirmed: the hub's refresh after expiry was answered but not kept)`. It is traced from the answer's fields (`transfer.deferred.refresh.shape`): fixed and run again where DraftYak's reading of the answer is at fault, else judged as refused as unusable.
    - **Inconclusive:** no answer, a 429 or a server error (`fails(deferred-refresh:UNAVAILABLE)`), a refresh refused as reused (`transfer.deferred.apiCode` `refresh_token_reused`), any other code, or a refusal after DraftYak was removed in ChatGPT during the wait. ADR 0009 says so and makes `Go` conditional on M7 showing a refresh after expiry.
    - **Not tested:** `after expiry: not run (…)` (over the cap), or no `after expiry:` detail (the setting unset, or the hub ended before the step). ADR 0009 says which refresh was tested, if any (`transfer.refresh`; none when the hub ended before its forced refresh), and makes `Go` conditional on M7 showing a refresh after expiry.
    - **The draft fails after a working refresh:** `refreshed true (…), draft <code>`, with `fails(deferred-draft:<code>)` on the `transfer:` line when the hub's first draft worked. A code that refuses the refreshed token, the account or the route (`ADMISSION_REFUSED`, `API_ERROR` with a 401 or 403 in `transfer.deferred.draft.status`, `INVALID_USER`, `SCOPE_NOT_AUTHORIZED`, `NOT_ELIGIBLE` or `ROUTE_NOT_SUPPORTED`), or `PLAN_USAGE_DISABLED`, which the hub raises once a refresh's answer lists scopes without `chatgpt.tokens.use.direct` (an answer with no `scope` keeps the earlier ones; `transfer.deferred.refresh.shape.scopes`, `transfer.planUsage`), is traced: fixed and run again where DraftYak's refresh or its reading of the answer is at fault, else judged as refused as unusable. Any other code answers the refresh question and is judged as a desktop draft's would be (above).
  - **`revoked:`** isn't part of the decision: anything but `yes` still fails the test and needs the removal in step 7, and ADR 0009 records it with the revocation evidence.
- **The consent wording,** as the owner copied it, whether the screen let the owner turn plan usage off, and the error page's wording if the flow was blocked.
- **Evidence** (`evidence/live.json`, `data`), answering the "Spike choices to confirm" in `notes/sources.md`:
  1. **Port:** `port`, `lock`.
  2. **Placement:** `drafts[]`, with `structure`, `toolChoice`, `outcome`, `problems`, `error` (`code`, `apiCode`, `param`, `status`), `upstream[].errorBody` and `events.completed.functionCalls`: each `function_call` output item's `name`, its `namespace` (`absent` without one) and its field names, never its arguments. A namespaced call that comes back in another form, such as a qualified name, reads `fails(invalid)` with `output: unexpected tool call` in `problems`, and `functionCalls` shows the form.
  3. **Refresh:** `signIn.token.earliestRefreshAt`, `transfer.refresh.shape` (which fields a refresh returns, an `id_token` among them) and `transfer.afterRevoke.refreshShape`, the error body on refresh. With the step after expiry, `transfer.deferred`: `ran`, with `dueInMs` when it didn't run; else `refreshed`, `rotated` (against the refresh token of the hub's first refresh), `msAfterExpiry` (how long after the access token expired the refresh went out), `idleMs` (since the hub's previous request), `refresh` (its status, time and answer's shape), `draft` (as `transfer.draft`) and, when the session refused a token, `code`, `detail`, `status` and `apiCode`. When `transfer.deferred.refreshed` is `false`, the access token that `transfer.afterRevoke.models` tried had already expired, so its status doesn't show whether revocation ends access tokens.
  4. **Discovery:** `discovery.endpoints.*.sameOrigin` and their paths, `discovery.id_token_signing_alg_values_supported`, `jwks` (a field a key leaves out reads `absent`) and `signIn.token.idToken.alg`. `signIn.token.idToken.facts` holds yes/no answers, never a claim value: whether `aud` holds the issued client ID (`audHasClientId`), `dynamic_agent_client` (`audHasDynamicAgentClient`) or the resource (`audHasResource`), whether `azp` is the issued client ID (`azpIsClientId`) and whether `iss` is the issuer (`issIsIssuer`). They show why a sign-in ended `blocked(ID_TOKEN_INVALID:issuer)`, `:audience` or `:authorized party`.
  5. **Streaming:** `drafts[].upstream[].chunks`, the sizes as they arrived; `drafts[].events.completed.repeatsOutput`; and the header names in `drafts[].upstream[].headers` and `authCalls[].headers`.
  6. **Host-ID format:** the run registers a `urn:uuid:` host ID (UUIDv4), so `signin: ok` shows OpenAI accepted that form; the evidence doesn't hold the ID. Whether the hub derives the recommended RFC 9278 thumbprint from a key it already holds is ADR 0009's call.
  7. **The callback port in the broker:** a plan change, not evidence. ADR 0009 carries it into M9: plugin egress to loopback port 1455 is refused like 47613–47615, beside M0.12's `brokerDecision` list (9229, 47613–47615), which doesn't hold 1455 yet.
  - Beyond the seven: **plan usage** (`signIn.token.scopes`, `signIn.planScope` for `chatgpt.tokens.use.direct`, and `signIn.planCheck`, the result of `Session.accessToken()`); **the plan's models** (`models`: the list's shape, `listedSlugs`, the slugs it marks `visibility: "list"` in the server's order, and `chosen`; `model`: the slug the drafts used and its source); **the transfer** (`transfer`: `result`, `accepted`, `rotated`, the hub's `draft`, `refresh` and `deferred`, `revoked`, and `desktopForgot`); **revocation** (`revocation`: `transfer`, `orphan`, `accessOnly`, `fallback`, `remaining`; `leftovers.probe`; and `transfer.afterRevoke`, whether the revoked refresh token and the old access token still work); **the verifier** (`brokered[]`, each plugin-side request with its field names and the broker's verdict); **API-key mode** (`apiKey`: the model and its source, the shape the key's model list came in, and the drafts); and `withheld`, the number of values that read `(withheld)`.
