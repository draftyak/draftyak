# ADR 0015: Scheduling clock rule, Temporal and the Slack rate dependency

- **Status:** proposed
- **Date:** 2026-10-17
- **Spike:** none (checks in `spikes/sched-clock`)
- **Plan:** §3 Scheduler, §8 Scheduling UX, §9.3, §13 Scheduling suite, §15 Scheduling ADR
- **Owner decision:** no

## Context
§15 asks for a scheduling ADR with no spike of its own: it records §3's clock rule, the Temporal requirement and that claim-time Slack reads depend on Slack's internal-app rate exemption (S6). §3 builds the scheduler on one injected clock (`kernel/clock.ts`) with separate wall and monotonic sources. No timer is derived from `notBefore`: the scheduler ticks at most every 15 s, `clock.after(ms)` throws above 15 s, and a GritQL rule bans raw timers in `apps/hub/src/outbox/`, because Node fires a delay over 2^31−1 ms (about 24.9 days) after 1 ms. A scheduled claim or retry needs min(hubNow, secondNow) ≥ `notBefore` and max(hubNow, secondNow) ≤ `deliverBy`, where `secondNow` is the `Date` header of the claim's own pre-claim read as the broker observed it, plus monotonic time since; a skew over 2 min holds the account's claims. Creating a schedule needs Temporal to turn a wall time and IANA zone into UTC with `disambiguation:'reject'`, so DST gaps and overlaps come back as `NONEXISTENT_LOCAL_TIME` or `AMBIGUOUS_LOCAL_TIME`; without Temporal new schedules fail with `SCHEDULING_UNAVAILABLE` and approved items still send. §9.3 freezes `schedule.localWallTime` (`YYYY-MM-DDTHH:mm±HH:MM`) in the snapshot, and §8's approval window renders the send time with Rust (jiff), so M1.18 needs schedule and DST vectors on which jiff and Temporal agree.

`spikes/sched-clock` checks what these rules rest on:
- `src/clock.ts` prototypes `kernel/clock.ts`: wall and monotonic sources, `after(ms)` refusing anything but whole milliseconds from 0 to 15,000 before any timer exists, and the tick `nextTick(now, nextDue)`. `src/claim.ts` prototypes the claim check (`checkClaim`, whose holds carry their retry time) and `secondNow` from an IMF-fixdate `Date` header.
- `test/timers.test.ts`, `test/two-clock.test.ts` (fast-check 4.10.2, with a simulated scheduler) and `test/dst.test.ts` run in `pnpm test`.
- `grit-check/` holds its own root `biome.json`, the rule `no-raw-timers.grit` and `fixtures/`, outside the main lint (ADR 0001); `test/grit.test.ts` lints the fixtures with Biome 2.5.15.
- `test/temporal.heavy.test.ts` runs a probe on both pinned Nodes (fetch-node binaries, `DRAFTYAK_NODES`): Temporal, the rejects in America/New_York, Europe/London and Australia/Lord_Howe, the ICU and tzdata versions, and every Node delay API at 2^31 ms.
- `jiff-check/` is its own Cargo workspace (Rust 1.95.0, jiff 0.2.38 with `tzdb-bundle-always`, jiff-tzdb 0.1.9) that answers the same questions from jiff's bundled database; `test/jiff.heavy.test.ts` runs its rustfmt, clippy and tests and compares it with Temporal on both Nodes, through `test/dst.ts`; `prefetch.ts` fetches its locked crates for `pnpm m0:prefetch`.

Constraints: local runs cover the Windows x64 dev box only, and the item has no `ci.json`, so no `spikes-run` job; CI's `full` job runs the heavy tier on Linux when the spike changes. Biome's plugin syntax was checked against what Biome 2.5.15 itself ships (its configuration schema, `biome lint --help` and the binary's own error messages) and by running it. ADR 0008's live check of the Slack exemption belongs to M0.25.

## Options
- **Claim clock:** the hub clock alone, which a wrong RTC or a manual change moves either way; the provider's `Date` alone, which a lying upstream or a plugin could set; or both clocks with min against `notBefore` and max against `deliverBy` (§3), which needs one more read per claim, already made by the pre-claim checks.
- **Waiting for a due item:** one timer for `notBefore − now`, which Node fires at once past 2^31−1 ms and which drifts across suspend and wall-clock jumps; or bounded ticks of at most 15 s through `clock.after(ms)` that re-read both clocks (§3). `node:test`'s MockTimers can't drive Temporal (§13), so the clock is injected.
- **Retrying a held claim:** at the next tick, as §3 says for a failed read, which comes at once while the row is still due, so the retry repeats the pre-claim read straight away; or at a retry time the hold carries, from which the scheduler counts the row.
- **Keeping raw timers out of outbox code:** Biome's GritQL plugin (§3), scoped either by the plugin entry's own `includes` or by an `overrides` entry; or a unit test that scans `apps/hub/src/outbox/` for timer names and modules, as §9.3 does for ticket imports. Neither can follow a timer through a variable or another module.
- **Gap or overlap:** read the kind from Temporal's `reject` error, or from the `earlier` and `later` resolutions.
- **The approval window's tzdata (Rust):** jiff's global `tz::db()` with default features, which reads the system's zoneinfo first on Unix; or `TimeZoneDatabase::bundled()`, jiff-tzdb's embedded copy, pinned with the crate.
- **Keeping jiff and Temporal in step:** require the bundled Node's tzdata version to equal jiff-tzdb's, or compare their answers and fail only on a difference.
- **Claim-time Slack reads:** rely on the internal-app exemption (Tier 3, `limit` up to 999) as §3 does, or budget every claim at the Tier 1 limits of unlisted apps (1 call a minute per method, 15 objects).

## Decision
Go

Plan changes:
- §3 Time zones, M1.18 `resolveLocalTime`: both Nodes throw the same `RangeError` ("Temporal error: Rejecting ambiguous time zones.") for a gap and for an overlap, so the hub classifies the wall time itself and never parses the message: if `earlier` and `later` give the same instant it is unique; if `earlier` still shows the wall time asked for it is an overlap (`AMBIGUOUS_LOCAL_TIME`); otherwise a gap (`NONEXISTENT_LOCAL_TIME`)
- §3 Time zones, §14 `doctor`, M10 `release-guard`: Temporal is missing only when `typeof Temporal === 'undefined'`; `typeof Temporal` is `'object'` on both pinned Nodes, so a `'function'` check (M0.23b's acceptance) never holds
- §3 Tick, Pre-claim and Clock rule, M2a: a hold carries its retry time, and the scheduler counts a held row (after a skew hold, the account's rows) from that time instead of `notBefore`, so `nextTick` never brings it straight back. An early hold (the min clock under `notBefore`) retries when the min clock can reach `notBefore`, but no sooner than 1 s, since a `Date` has whole seconds, and no later than 15 s; a skew hold or a failed pre-claim read retries one 15 s tick later, alerting and auditing once per episode, not per retry; missed is final. A held item then costs at most one pre-claim read a tick, plus up to three shorter retries. With a plain "next tick", which comes at once while the row is still due, and reads of 200 ms, a 90 s slow upstream costs about 450 reads before the claim, and a hub clock 5 min fast 4,501 over a 15-minute window; the retry times make those 7 and 60. A row whose window isn't two safe integers in order is never claimed (`window`)
- §3 Tick, M2a: in outbox code the GritQL rule bans `setTimeout`, `setInterval`, `getBuiltinModule` and `createRequire` as names anywhere (identifier, member, key or type member) and as strings or plain template literals; `AbortSignal`, `Atomics`, `globalThis` and `global` as values (`AbortSignal` stays usable as a type); and module sources, strings and plain template literals naming `timers`, `node:timers`, `timers/promises` or `node:timers/promises`, which covers imports, re-exports, `import x = require()`, `require`, `module.require`, `import()` and `getBuiltinModule`. At 2^31 ms all five Node delay APIs fire almost at once on both Nodes, with a `TimeoutOverflowWarning`; outbox code waits through `clock.after` (`kernel/clock.ts`). The rule can't follow a timer through a variable or another module, so it catches slips; the claim's two-clock check, not the rule, keeps a send from going early
- M2a root `biome.json`: scope the rule with an `overrides` entry (`includes: ["apps/hub/src/outbox/**"]`, `plugins: [<rule>]`). Biome 2.5.15 matches a plugin entry's own `includes` against the absolute path, so `"apps/hub/src/outbox/**"` there matches nothing and the rule silently never runs (an absolute glob, or one starting `**/`, matches). A `biome-ignore` comment naming `lint/plugin/no-raw-timers`, `lint/plugin` or `lint` silences the rule in every form: a line, block or doc comment, a `-start`/`-end` range or a file-level `-all`. So M2a refuses the token `biome-ignore` anywhere in outbox code, not only `// biome-ignore`
- §8, M1.18, M1b: Rust renders send times from `TimeZoneDatabase::bundled()`. With jiff's default features, `tz::db()` reads `TZDIR` or `/usr/share/zoneinfo` first on Linux and macOS (Android's concatenated database first on Android), so `tzdb-bundle-always` only embeds the data. M1.18's vectors name both tzdata versions (Node's `process.versions.tz`, `jiff_tzdb::VERSION`). M10's `release-guard` runs the jiff-check comparison against the bundled Node and fails only on a difference; a version mismatch alone warns, since Node 26.5.1's 2026b and jiff-tzdb's 2026e answer every case here alike
- §3 Clock rule, M1.18 (`spec/approval-v1.md`): add that an HTTP `Date` has whole seconds and is written before the response travels, so `secondNow` lags a right upstream by less than 1 s plus the latency and never leads it. With a right hub clock that delays a scheduled claim by at most the lag; with a slow hub clock it can let a claim through up to the lag after `deliverBy`, so the spec either states that bound or has the late check add 1 s and the read's round trip to `secondNow`. `secondNow` takes a `Date` only if it is the IMF-fixdate its own instant prints: `Date.parse` reads 31 Feb as 3 Mar, hour 24 as the next day and second 60 as second 0, and ignores the weekday. The prototype's order: a malformed window refuses first; then a skew over 2 min (or an unreadable clock) holds; then max over `deliverBy` means missed; then min under `notBefore` means not yet

### What held as planned
- **Clock rule.** Over 10,000 fast-check cases each: no claim early or late while either clock is right, however wrong the other (errors up to two days); none while the two clocks bracket the true time; the two-clock check never claims where either clock alone would refuse; with both clocks right it claims exactly inside the window; a skew holds exactly when the clocks are more than 2 min apart. The cases include a millisecond either side of both edges and clocks 2 min and 2 min plus 1 ms apart, and the tests state the plan's numbers as literals, so each of 22 mutations of `claim.ts` and `clock.ts` (the min, the max, either edge, the skew check and limit, the retry times, the window and `Date` checks, the 15 s limit and `nextTick`) fails at least one test.
- **Retries.** A simulated scheduler around the claim (clocks off by up to two days, reads of up to 10 s that may fail, the hub starting before or anywhere in the window) never claims early while either clock is right, nor late while the hub clock is right; with a right upstream and a slow hub the `Date`'s lag can make it late by less than 1 s plus the latency, as above. Per item it makes at most four pre-claim reads plus one per 15 s of the window, at most one plus one per 15 s while the clocks are more than 2 min apart, and claims within 12 while they are within 2 min of each other and no read fails.
- **Timers.** `setTimeout(fn, 2**31)` fires almost at once with a `TimeoutOverflowWarning`, as do `setInterval`, `timers/promises`' `setTimeout` and `scheduler.wait`, and `AbortSignal.timeout`; 2^31−1 ms waits without a warning. `clock.after` throws a `RangeError` above 15,000 ms, before arming anything. Ticks of at most 15 s reach items 2^31−2, 2^31−1 and 2^31 ms and 30 days ahead exactly when due, never before.
- **Temporal.** Present on 26.5.1 and 26.12.0, both ICU 78.3, with tzdata 2026b and 2026e. In 2026 and 2027 each zone has two transitions a year, New York and London by an hour and Lord Howe by 30 minutes; `reject` throws for every wall time inside a gap or an overlap (the first, middle and last minute) and resolves the minute before and after and noon the day before.
- **jiff and Temporal agree.** On every transition, on each of the 72 wall times under `compatible`, `earlier`, `later` and `reject`, and on the `localWallTime` and offset of 96 instants around the transitions (each transition, a minute either side, and windows from 30 min before it ending at each lateness), with no difference on either Node. Node 26.5.1's tzdata 2026b differs from jiff-tzdb's 2026e, but not for these zones and years. jiff's `earlier`, `later` and `compatible` follow Temporal's semantics, and jiff reports the kind (`Gap` or `Fold`) directly. A transition only one side has is listed, with every case around it, instead of failing the run (`test/dst.test.ts`); only a Node with jiff's tzdata version must agree exactly.
- **Slack.** Claim-time `conversations.info` is Tier 3 and outside the 2025-05-29 change; the `conversations.replies` or `conversations.history` read since the watermark (`limit` 20) relies on the internal-app exemption (`spikes/s06-slack/notes/rate-limits.md`, "The facts, stated once", facts 1–5). Whether an app the owner builds from DraftYak's manifest counts as internal customer-built (fact 5) is open until Slack answers the 2026-10-17 request; M0.25 checks the exemption on the owner's app and ADR 0008 records it.

### For M1.18 (schedule and DST vectors)
`spikes/sched-clock/evidence/dst-win32-x64.json` is the input, as `data`:
- `jiff` (crate versions, `tzdbVersion`, `database`, `defaultDatabase`) and `nodes` (each Node's role, version, `icuVersion`, `tzVersion`, `sameTzdataAsJiff` and its count of differences);
- `transitions` (`zone`, `epochMs`, `offsetBefore`, `offsetAfter`, `shiftMinutes`);
- `walls` (`zone`, `wall` as `YYYY-MM-DDTHH:mm`, `kind` of `unique`, `gap` or `fold`, and the UTC milliseconds for `compatible`, `earlier` and `later`, with `reject` null where Temporal throws);
- `instants` (`zone`, `epochMs`, `localWallTime` in §9.3's format, `offset`);

## Fallback
- **Temporal missing** on some build (Homebrew, musl, Chainguard): new schedules fail with `SCHEDULING_UNAVAILABLE`, calendar lookups are off and approved items still send, as §3 says; `release-guard` keeps Temporal in the bundled Node and the Docker image. The classification above doesn't depend on the error text, so a Node that tells the two kinds apart changes nothing.
- **Biome's plugin breaks or changes** on a bump (a failing `test/grit.test.ts` is the trigger): the outbox rule becomes a unit test that scans `apps/hub/src/outbox/` for the same names and modules, as §9.3's import scan does for ticket minting.
- **jiff and Temporal disagree** (a tzdata release changes a zone, or the two pins drift): the approval window flags the `localWallTime` mismatch (§8), the vectors name both versions and list each difference, and `release-guard` fails a desktop build whose bundled Node and jiff answer differently.
- **No second clock** for a claim (a failed pre-claim read, no valid IMF-fixdate `Date`): no claim, a retry one tick later, and past `deliverBy` the item goes to NEEDS_REAPPROVAL (`missed`), as §3 says for a failed read.
- **The Slack exemption doesn't hold** (ADR 0008, M0.25 or Slack's reply is the trigger): `rate-limits.md`, "If the exemption doesn't hold", applies. `conversations.replies` and `conversations.history` would allow one call a minute per workspace and 15 objects, below the pre-claim read's `limit` 20, so claims due in the same minute queue a minute apart per method; a read that can't be made in time never lets a claim through, and past `deliverBy` the item is missed, which caps a burst of due items at about 15 per method within the default 15-minute lateness. Socket Mode events would carry sync; `conversations.info` stays unaffected.
