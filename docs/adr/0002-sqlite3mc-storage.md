# ADR 0002: S1 SQLite3MC storage: prebuilds, cipher, FTS5, migrations, rotation

- **Status:** proposed
- **Date:** 2026-10-17
- **Spike:** S1
- **Plan:** §2 Storage, §3 Storage (Open 1–4, Migrations, Key rotation), §3 Data lifecycle, §9.2 (theft of disk, backups or logs), §15 S1
- **Owner decision:** yes

## Context
§3 keeps all hub state in one SQLite3MC file. It is opened with `PRAGMA cipher='chacha20'` and `PRAGMA hexkey=HKDF(MK,"draftyak/v1/db")`, and the key is proved with `SELECT count(*) FROM sqlite_master`, because `PRAGMA key` reports success even with a wrong key. The connection then runs with WAL, `busy_timeout=5000`, foreign keys, `secure_delete=ON`, `trusted_schema=OFF` and `auto_vacuum=INCREMENTAL`. FTS5 tables use `secure-delete=1`, and the bundled addon loads through `nativeBinding`. Migrations are plain `NNNN_*.sql` files per namespace, run by Kysely's `Migrator` through a `SqlDirMigrationProvider` that executes each file with raw `exec()` inside a transaction, because FTS5 triggers contain `BEGIN…END`. Key rotation writes a new database file in maintenance mode, so no WAL salt is reused, and a disconnect purges the account in batches. §9.2 asks for canary scans of the db, -wal and -shm. §15 S1 asks that the prebuilds load on every target (win-arm64 and musl included) and in Docker, through `nativeBinding` from the bundle; that chacha20 with `hexkey` fail closed on a wrong key; that FTS5 with `secure-delete=1` and its triggers go through the raw-exec migrator; that no plaintext canary reach the db, -wal or -shm; and that the spike measure the `secure_delete` cost and rotate into a new file.

The spike ran better-sqlite3-multiple-ciphers 13.0.3, which bundles SQLite3 Multiple Ciphers 2.4.0 and SQLite 3.53.4, with kysely 0.29.6 (M0.9 for the prebuilds and the load matrix, M0.10 for the rest). The cipher, FTS, migrator, canary and rotation tests are unit tests: they ran on the Windows 11 x64 dev box under Node 26.12.0, and CI's `cheap` job runs them on Linux x64. Each load in the load matrix also runs a keyed round trip: §3's open with every setting read back, the core migration run whole, an FTS5 secure delete, a scan of the files and a wrong key. That covers all 8 targets on 26.5.1 and 26.12.0: win32-x64 natively and linux-x64 and linuxmusl-x64 in Docker on the dev box, and darwin-arm64, darwin-x64, linux-arm64 (natively and in Docker), linuxmusl-arm64 (in Docker) and win32-arm64 on GitHub runners through `pnpm spikes:run` (runs 39084986728 and 39086300546). The benchmark took the kit's machine lock and passed its idle check; it runs only on developer machines (`requires:bench-host`), not on CI runners.

The following build/source facts come from the package's own build files, `deps/defines.gypi` and `src/objects/database.cpp`, and from the bundled amalgamation. Retained test results support the conservative settings; the broader plain-`VACUUM` and musl temporary-file observations identified below were one-off observations without retained experiments:
- The build sets `SQLITE_USE_URI=0`, and better-sqlite3 opens connections without `SQLITE_OPEN_URI`, so `file:` URIs are plain file names, in `ATTACH` and `VACUUM INTO` too.
- chacha20 is the build's default cipher. It keeps a random 16-byte salt where the `SQLite format 3` header would be, reserves 32 bytes per page for its nonce and Poly1305 tag, and runs the key through PBKDF2-HMAC-SHA256 with 64,007 iterations (`kdf_iter`) on every open and `ATTACH`, unless the key is given in one of SQLite3MC's raw-key forms (`raw:…` or `x'…'`).
- SQLite3MC encrypts the database file, its rollback journal and its WAL, but not SQLite's temporary files: its VFS leaves their cases out (`#if 0`), and a statement journal is opened without a name, so no codec finds it. Unless `temp_store=MEMORY`, a sort or the TEMP database (TEMP tables, a plain `VACUUM`'s copy) that outgrows the page cache (16 MB by default in this build), and a statement journal over 64 KiB, go to the OS temp folder in plaintext. The build sets no `SQLITE_TEMP_STORE`, so they default to files.
- `SQLITE_DEFAULT_WAL_SYNCHRONOUS=1`: a WAL connection runs with `synchronous=NORMAL` unless it sets `synchronous` itself. A commit is then not synced, and the last commits can be lost on power loss or an OS crash.
- SQLite takes an empty file for a new database: it keys it with whatever key it is given, and its first read deletes a -wal found beside it.
- `recursive_triggers` is off by default, and then `REPLACE` deletes the row it replaces without firing that table's delete triggers.
- `PRAGMA rekey` works on a WAL database in SQLite3MC 2.4.0, but keeps the cipher salt (the cipher's key generation skips the new salt in WAL mode).
- FTS5 marks its tables `SQLITE_VTAB_INNOCUOUS`.

## Options
- **Prebuilds** (V11):
  - Copy the 8 N-API prebuilds the npm package ships. Their bytes are pinned by the lockfile's sha512, and no install script, fetch or `allowBuilds` entry is needed.
  - Fetch release assets, with a lock file and checksums of our own.
  - Build from source with node-gyp, which needs an `allowBuilds` entry and a C++ toolchain on every target.
- **ABI:** one N-API (`NAPI_VERSION=10`) binary per target for both Nodes, or per-ABI builds for each Node.
- **Temporary files:** SQLite's default, files in the OS temp folder, which SQLite3MC writes in plaintext; `temp_store=MEMORY`, which keeps sorts, statement journals and the TEMP database in RAM; or a temp folder on an encrypted volume, which the hub can't ensure.
- **Durability:** the build's `synchronous=NORMAL` under WAL, or `FULL`, which syncs the WAL at every commit.
- **`REPLACE` and FTS5:** `recursive_triggers=ON`, or a rule that the hub never writes `REPLACE`.
- **Rotation into a new file:**
  - (a) §3's literal `VACUUM INTO 'file:…?cipher=chacha20&hexkey=…'`.
  - (b) `VACUUM source INTO <new file>` from a maintenance connection whose main database is an empty key-holder file keyed with the new key, with the current file attached by `ATTACH … KEY`. `VACUUM INTO`'s output takes the main database's key and the key holder's fresh salt.
  - (c) An `ATTACH … KEY` copy: the new file is the main database, the current one is attached with its key, and SQL recreates the schema, copies the rows and rebuilds each FTS5 index.
  - (d) `PRAGMA rekey` in place.
- **Migration transactions:** Kysely's own `SqliteAdapter`, which reports `supportsTransactionalDdl: false`, so the Migrator runs SQLite migrations in autocommit mode; a dialect that reports `true`, so all pending files and their `_migrations_<ns>` rows run in one transaction; or a `SAVEPOINT` per file, which can't put the migration row in the same transaction.
- **Deleted text:** `secure_delete` and FTS5 `secure-delete` each on or off; for the -wal, leaving it to checkpoints, capping it with `journal_size_limit`, or ending each purge with `wal_checkpoint(TRUNCATE)`.

## Decision
Go

Plan changes:
- §3 Open: three settings join Open 3 and are read back with the others: `temp_store=MEMORY`, since SQLite3MC writes temporary files in plaintext (large sorts and statement journals then cost RAM instead); `synchronous=FULL`, since the build's WAL default `NORMAL` can lose committed transactions, an outbox claim among them, on power loss; and `recursive_triggers=ON`, so `REPLACE` keeps FTS5 in step. A missing or empty database file is refused unless the hub is creating it
- §3 Open: under `trusted_schema=OFF`, FTS5's maintenance triggers run, but `MATCH` and FTS5's auxiliary functions are refused inside views and triggers, so searches stay top-level statements
- §3 Migrations: the hub's Kysely dialect reports `supportsTransactionalDdl: true`, so a migration run commits whole or not at all, and a failed run reports none of its files as applied. Foreign keys are off for the run, because SQLite ignores the pragma inside a transaction and a table rebuild's `DROP TABLE` would cascade, and `foreign_key_check` must pass after each file. A file not named `NNNN_<name>.sql`, or one with a top-level `BEGIN`, `COMMIT`, `END`, `ROLLBACK`, `SAVEPOINT`, `RELEASE`, `PRAGMA`, `ATTACH`, `DETACH` or `VACUUM`, fails the run before any file runs
- §3 Key rotation: option (a) can't run with this build. Rotation uses option (b), keeping option (c) as the fallback. Both refuse a missing or empty source, leave it untouched and check the new file before it is used: `integrity_check`, the source's schema and row counts, a fresh cipher salt, and `SQLITE_NOTADB` under the old key. Option (b) also refuses a key holder without a key
- §3 Data model: an external-content FTS5 table uses an `INTEGER PRIMARY KEY` as its `content_rowid`, because `VACUUM` and `VACUUM INTO` may renumber implicit rowids
- §3 Data lifecycle and §9.2: deleted text leaves the database only with both `secure_delete=ON` and FTS5 `secure-delete=1`, and leaves the -wal only once the purge ends with `wal_checkpoint(TRUNCATE)`, retried while a reader holds the WAL. Space comes back through `incremental_vacuum`: under `temp_store=MEMORY` a plain `VACUUM` keeps a whole copy of the database in RAM. `db.serialize()` returns a plaintext image and must never reach disk; `db.backup()` refuses to copy an encrypted database into an unkeyed file

### §3 Open, in full
1. `PRAGMA cipher='chacha20'`, then `PRAGMA hexkey='<key>'`, or `db.key(<32 raw bytes>)`, the same `sqlite3_key` call, which keeps the key out of SQL text. The key is HKDF-SHA256 over the master key (at least 32 bytes) with an empty salt and the info `draftyak/v1/db` (an extension module's file uses `draftyak/v1/ext/<id>`): 32 bytes, written as 64 lowercase hex digits. For a master key of 32 bytes of `0x0b` it is `7591d208acdbd734a4274a32f4d157fced5ee25d2f84dccdf69a32510077786e`.
2. `SELECT count(*) FROM sqlite_master`. A wrong or missing key, another cipher and a plaintext file all throw `SQLITE_NOTADB` here, and the connection is closed.
3. `temp_store=MEMORY`, `auto_vacuum=INCREMENTAL` (it takes effect only before the first table), `journal_mode=WAL`, then `synchronous=FULL`, `busy_timeout=5000`, `foreign_keys=ON`, `recursive_triggers=ON`, `secure_delete=ON` and `trusted_schema=OFF`, each read back; any difference closes the connection.

### Results
- **Prebuild sourcing and ABI:** the npm package's N-API 10 prebuilds, copied by realpath into `bundle/prebuilds/` and loaded through the main entry's `nativeBinding`, which needs an absolute `.node` path (M0.9). One binary per target loads on both Nodes, so no per-ABI builds are needed. The retained historical complete matrix records all 8 targets on Node 26.5.1 and 26.12.0, 16 target/Node cells, each passing the keyed round trip. The historical dev-box routes included win32-x64 natively and linux-x64 (glibc 2.36) and linuxmusl-x64 in Docker; the other native/Docker routes are distinguished in Context and the recorded host entries. These are recorded results, not a fresh validation of current runners or the packaged hub.
- **Cipher:** a wrong key, another cipher configured with the right key, a plaintext file and a connection given no key each fail with `SQLITE_NOTADB` while the verify query is prepared (preparing it loads the schema). Where a key was given, `PRAGMA hexkey` had answered `ok` all the same. `openEncrypted` then closes the connection and leaves the file byte-for-byte unchanged. A missing or empty file is refused before SQLite opens it, unless the caller asks to create the database. An in-memory database can't be keyed.
- **Settings:** reopened without them, a WAL file runs `synchronous=NORMAL`, `temp_store` 0 (files) and no recursive triggers; `openEncrypted` sets and reads back all ten.
- **Temporary files:** the kept temporary-file test defines sort-spill, purge statement-journal and TEMP-table checks, including the subject, body, sender and `SQLite format 3` header canaries, with plaintext disk controls and checks under `temp_store=MEMORY` on supported temp-file-scan platforms. The broader plain `VACUUM` observation on a 35 MB database and the musl temporary-file observations were unretained one-off observations; neither the kept three-operation test nor the keyed Docker round trip contains those experiments. This does not establish `VACUUM` safety or a musl difference. The conservative `temp_store=MEMORY` and `incremental_vacuum` choices remain.
- **Rotation:**
  - (a) fails with `SQLITE_CANTOPEN`, because SQLite takes the URI as a file name. SQLite's message repeats that URI, new key included, so the rotation error keeps only the code.
  - On a 10.4 MB file with 10,000 messages, (b) took 162 ms to copy and 172 ms to verify, (c) 253 ms and 154 ms (`bench-win32-x64.json`).
  - (b) is SQLite's own `VACUUM` copy: every table is copied as stored, FTS5's shadow tables included, with no schema-specific code. From a main database without a key, it writes the source in plaintext, so the key holder is checked first.
  - (c) needs code for each kind of object: it replays each FTS5 table's configuration and rebuilds its index, and it refuses other virtual tables.
  - (d) keeps the cipher salt under WAL, which is the reuse §3 avoids.
- **Migrations:** Kysely's own adapter makes the Migrator run without a transaction, so a failing multi-statement file would keep its earlier statements, with no record; the provider refuses to run that way. With the override, a failing batch leaves no table, trigger or `_migrations_core` row behind, and neither does SQLite's own rollback after `SQLITE_FULL`. Statements are told apart the way `sqlite3_complete()` does it, so trigger bodies, strings, quoted names and comments don't count. With foreign keys on, rebuilding `conversations` the way SQLite documents it (new table, copy, drop, rename) deleted every message through `ON DELETE CASCADE`, and the run still succeeded; with them off for the run, as that procedure's first step asks, the messages and their FTS5 rows stay, and a file that leaves orphans fails `foreign_key_check`. Whole-file `exec()` is required: Kysely runs one statement per query, and splitting on `;` cuts the first trigger at its inner `;` (`incomplete input`).
- **FTS5 and `REPLACE`:** without recursive triggers, `INSERT OR REPLACE` left the replaced words in the index and FTS5's integrity-check failed; with them, the index follows `REPLACE` and `ON CONFLICT … DO UPDATE` alike.
- **Canaries:** with the database open and canaries in WAL frames and the FTS5 index, the db, -wal and -shm hold neither the `SQLite format 3` header nor any canary, master-key or key bytes. The same holds after a checkpoint, after an update and once closed. The scanner itself finds every canary in a plaintext control database. It looks for each canary's random tail, because FTS5 stores a term only after the bytes it shares with the previous term.
- **Deleted text in the -wal:** a deleted row stays in older -wal frames, under the same key. A copy of the files, its -wal cut where the insert's commit ended, opened under the key with the row back, and a `PASSIVE` checkpoint left the -wal as it was. A plaintext control kept the deleted text in its -wal after two checkpoints and the WAL's restart. `wal_checkpoint(TRUNCATE)` empties the -wal; it reports busy while a reader holds an older snapshot.
- **secure_delete cost** (10,000 messages of 60 words, deleted in batches of 500; medians of 3 runs on the shared dev box; the kit checked its accepted idle window before measurement, and the post-run snapshot showed 9% CPU and zero processes matching its listed build-tool names. Load was sampled before and after, not continuously during the measurement):

  Configurations ran in a fixed order: `secure_delete=OFF` before `ON` within each table setup, and the `NORMAL` comparison after the `FULL` cases. Three repeats were reduced to medians; individual repeat spread was not retained. These fixed-order measurements do not supply an isolated or repeatable causal cost estimate.

  - The recorded delete medians for the 10,000 rows were 39 ms OFF versus 47 ms ON without FTS, and 182 ms versus 187 ms with FTS5's own secure-delete off (20% and 3% differences). Recorded WAL sizes were 35–42% higher for the ON configurations. These fixed-order comparisons do not isolate the setting's timing effect from uncontrolled variation.
  - The larger observed difference was with FTS5's `secure-delete` enabled: both settings ON recorded 3.5 s versus 0.19 s (19 times, about 0.35 ms per message), and 35 MB versus 14 MB of WAL. With FTS5 `secure-delete` enabled, SQLite `secure_delete` OFF/ON recorded 4.2 s/3.5 s. The reversed timing direction does not establish a speedup, a specific cause or a quantified noise level; repeat spread was not retained.
  - The cost grows with the index: deleting the oldest 5,000 messages took 0.41 ms a message from 10,000 messages and 0.61 ms from 50,000, writing 20 MB and 58 MB of WAL.
  - The first secure delete moves the index to FTS5 format 5, which FTS5 builds from before `secure-delete` refuse to read.
  - `incremental_vacuum` then returns the freed pages in 2 to 14 ms.
- **synchronous=FULL:** the recorded insert/delete medians for 10,000 rows in 40 commits were 191 and 47 ms with `FULL`, against 191 and 53 ms with `NORMAL`, which ran later. These observations do not establish zero or repeatable causal overhead. The `FULL` durability choice is unchanged.
- **Open:** opening the 10,000-message file took 23 ms (median of 5), including the PBKDF2 step SQLite3MC runs on every open.
- **Targets:** the historical matrix records all 8 package prebuilds loading from the bundle on N-API 10 and passing the keyed round trip on both recorded Nodes, without a source build for those recorded cells. M10 still verifies the packaged hub and release CI.

## Fallback
- **A target fails to load, or fails the keyed round trip:** that target is built from source in CI (node-gyp, with an `allowBuilds` entry the owner approves), or it is dropped from the release with the owner's decision. The trigger is a `failed` cell in `load-matrix.json` after the `spikes-run` jobs.
- **Option (b) stops working** in a later SQLite3MC, or the key-holder file causes trouble: switch to option (c). The kept rotation test covers both and fails on either.
- **URI filenames are enabled** in a later build: §3's literal `VACUUM INTO` becomes possible. The kept test, which expects `SQLITE_CANTOPEN`, fails and points at the change.
- **SQLite3MC starts encrypting temporary files:** the kept test's control, which expects plaintext in them, fails and points at the change; `temp_store=MEMORY` can stay.
- **FTS5 loses `SQLITE_VTAB_INNOCUOUS`**, or `trusted_schema` starts refusing its triggers: maintain the FTS5 index from the store code inside the same transaction. An authenticated, encrypted file can't have its schema altered without the key, so `trusted_schema=ON` remains a second option.
- **FTS5 secure deletes are too slow** for a large purge (disconnect, the 90-day cap): purge in smaller batches between other work, and keep `secure-delete`. Without it the index keeps every deleted token.
