# ADR 0009: S7 Sign in with ChatGPT

- **Status:** proposed
- **Date:** 2026-10-21
- **Spike:** S7
- **Plan:** §15 S7, §4, §5
- **Owner decision:** no

## Context
§5 drafts with the owner's ChatGPT plan through `ai-responses-api` in mode `siwc`: the `openai` SDK over a clean-room implementation of OpenAI's documented open-source flow. A first sign-in registers through `dynamic_agent_client` and gets an issued client back. Each hub has one `ext_agent_host_id`, the app name is `agent_name_hint: "DraftYak"`, and refreshes are serialized. Structured output is the strict function tool `submit_draft`, never executed, while S7 tests `text.format`. §4 adds:
- the sign-in callback on fixed port 1455, after a check that nothing else holds it;
- the headless-hub transfer: the desktop signs in with the hub's host ID and registration, hands the tokens over L2 and forgets them;
- the `chatgpt.tokens.use.direct` check, with an explicit API-key offer when it is missing;
- refresh under a per-credential mutex, and revocation at OpenAI on disconnect;
- the SIWC request allowlist.

Below, "the plan route" means Responses API requests made with the Sign in with ChatGPT access token, which draw on the ChatGPT plan's usage limits.

§15 S7 asks for the documented credential transfer, `text.format` against `submit_draft`, streaming through host chunks, the port 1455 collision check and the error shapes.

`spikes/s07-siwc` answers in two parts:
- **M0.26 (S7a)** built the flow from OpenAI's public documentation alone and tested it against loopback fakes. `spikes/s07-siwc/notes/sources.md` is the clean-room record: every page read, when, its SHA-256 and what it settled, and what was not read or run.
- **M0.27 (S7b)** ran it live, with M0.27b (tool-call shapes, listed models and ID-token facts in the evidence) and M0.27c (the step after expiry, and this ADR's decision rule, fixed in `spikes/s07-siwc/notes/session.md` before the session).

The live test, `test/siwc.live.test.ts`, runs `test/live-session.ts`, the procedure the rehearsals run against the fakes:
1. It signs in through the system browser, with the callback on `127.0.0.1:1455`, a new registration and a `urn:uuid:` host ID.
2. It drafts once with `text.format`, then once with `submit_draft` in each of three places: a namespace, an `additional_tools` input item and the top level.
3. It hands the session to a second process on the same PC and forgets it. That process stands in for the hub (`test/transfer-child.ts`) and takes only a credential for its own host ID. The hub drafts once, refreshes, revokes and forgets. With `DRAFTYAK_S7_DEFERRED_MIN` set, it waits after its refresh until 3 minutes after that access token has expired, then drafts once more with a token from `Session.accessToken()`, which refreshes first, as the product will, and only then revokes.
4. It drafts twice with an API key, if one is set.
5. It deletes every `DY_LIVE_SIWC_*` entry and writes `evidence/live.json`: names, shapes, sizes, codes and timings, never a token, prompt, draft, account ID or e-mail address.

Every draft goes through the spike's broker, which checks the request against the allowlist, injects the token and hands the streamed body to the SDK in 4,096-byte host frames.

Three runs, all on 2026-10-21 (times in CDT), on the Windows 11 x64 dev box with Node 26.12.0, from the session checkout at 77be2468, with the owner's ChatGPT account and its plan:
- **Run 1** started at 03:31 with the step after expiry (`DRAFTYAK_S7_DEFERRED_MIN=70`) and took 3,870 s.
- **Run 2** started at 09:00 without that step, because run 1 had answered its question, and took 221 s.
- **Run 3** started at 09:21 without that step, after the owner had changed a ChatGPT usage setting (Usage limits, below), and took 57.6 s. Its file is `evidence/live.json`.

No API key was set, so API-key mode ran in none of them.

## Options
- **Structured output on the plan route** (spike choice 2):
  - `text.format` with a strict json_schema, as API-key mode drafts (§5). One request shape serves both modes, and no tool goes into the request. In run 3 its one draft took 11,033 ms and used 178 reasoning tokens, with no `reasoning` field in the request.
  - The never-executed function tool `submit_draft`: in a `draftyak` namespace or as an `additional_tools` input item, the placements OpenAI's Preview limitations name, or as a top-level tool with a forced `tool_choice`, which they don't name. In run 3 each took 4,589–4,971 ms with no reasoning tokens. Each needs a tool and `tool_choice` past the verifier, and a check of the call's name and namespace, which the live route's `response.completed` didn't carry.
- **The callback port** (choice 1): fixed `127.0.0.1:1455`, with a connect probe before the bind and `PORT_IN_USE` on a collision (§4); or another free port on reauthorization, which the docs allow but the broker can't block ahead of time.
- **The host ID** (choice 6): a random `urn:uuid:` UUIDv4 made once per hub; an RFC 9278 thumbprint of a key the hub already holds, which the docs recommend, though OpenAI doesn't verify possession of the key; or a `did:key:`.
- **When the hub refreshes** (choice 3): on demand, in `Session.accessToken()` from 2 minutes before expiry, with `earliest_refresh_at` holding back only a still-valid token; or on a timer ahead of expiry, which keeps an idle session in use at the cost of refreshes no draft needed.
- **Headless and VPS hubs:** the documented transfer (§4 Credential flow, step 2); a sign-in on the hub's own host only; or API-key mode for such hubs. OpenAI's Self-hosted VMs page says that "Host-specific usage attribution and revocation of ChatGPT plan access for transferred sessions are not yet available."
- **Ending a session:** revoke the refresh token at OpenAI and count on that to end the access token, which the docs don't promise; or also delete the access token on the hub at once, and treat any copy as usable until it expires.

## Decision
Go

Plan changes:
- §5 (the Sign in with ChatGPT row, structured output), §4 (AI request verifiers) and §1 (TB6): the plan route took every structure in run 3: `text.format` with a strict json_schema, and `submit_draft` in a `draftyak` namespace, as an `additional_tools` input item and as a top-level tool (`drafts[].outcome` `draft`). M7 drafts with `text.format` in both modes of `ai-responses-api`. §5's "Strict function tool `submit_draft`, never executed (S7 tests `text.format`)" becomes "`text.format` json_schema strict, `store:false`, as with a key (S7)". §4's SIWC allowlist becomes `model`, `instructions`, `input`, `text`, `reasoning`, `stream:true`, `store:false`, without `tools=[submit_draft]` and `tool_choice`; "Responses API with a key: the same, with `store:false`" takes that list too, so neither mode sends a tool. TB6's "SIWC's `submit_draft` is schema-only and never executed" becomes "no tool reaches a model; `submit_draft` comes back only under Fallback 1, schema-only and never executed". `submit_draft` in the namespace is Fallback 1
- §4 Egress broker, step 6: the broker always blocks loopback port 1455 too, beside 47613–47615 and 9229, as §1's listener table already says. The sign-in's authorization code arrives there (`port` 1455 in every run). M2 stream 2b's broker carries it, since plan §12 builds the broker's port blocks there, as ADR 0003 also says; `notes/session.md` (item 7), `notes/sources.md` (choice 7) and S2's broker stub name M9 instead. S2's `brokerDecision` (M0.12) refuses 9229 and 47613–47615 but not 1455 yet, while the kit's port picker already reserves it
- §4 Host channel (`host/fetch` streams through `host/stream.chunk`): each upstream chunk goes on as it arrives, split only above the frame limit and never held back to fill a frame. The spike's broker held each partial frame back until 4,096 bytes or the end had arrived (`toFrames()` in `src/stream.ts`), so a delta waited until its frame filled or the stream ended. In run 3 the upstream sent each draft in 25–51 chunks of 26–4,773 bytes (medians 251–504), the first 945–1,997 ms after the request (`drafts[].upstream[].chunks`), and the SDK got each body in 6–8 data frames plus an end frame (`brokered[].frames` 7–9). `drafts[].events.firstDeltaMs` (3,202–9,135 ms) is measured after those frames, and the evidence has no arrival time per chunk, so it can't separate the frame wait from the model's own time to its first delta
- §4 AI request verifiers (SIWC) and guardrail 4: besides `POST /v1/responses` with the fields above, the SIWC verifier allows a bodiless `GET /v1/models`, the documented way to list the plan's models (`src/verify.ts`). Every run picked its model that way (`brokered[0]`, verdict `ok`). Guardrail 4's "Use the Responses API only" becomes "Use the Responses API and its model list only"
- §4 Credential flow, step 2: `prompt=consent` goes out only when the owner turns plan usage on for a saved account, including after a decline (`src/auth.ts`), never on an ordinary sign-in. The docs say an app "should not force consent on every ordinary sign-in" (`notes/sources.md`, Consent), while the plan sends it "until OpenAI confirms the deployment". This wasn't exercised live: every run was a first registration (`signIn.attempts[].registration` `new`), and in run 2 OpenAI showed the access screen without it

### Why Go
The rule in `notes/session.md` ("What ADR 0009 records"), fixed before the session, run by run:
- **Runs 1 and 2:** `signin: ok`, but both structure lines read `fails(USAGE_LIMIT)`. The rule calls for another run once the limit allows, not `Not run`. Their `transfer: ok` means the hub took the session and refreshed it, in run 1 after expiry too. The hub's drafts failed with the same `USAGE_LIMIT` as the desktop's, and the line counts a failed hub draft only when the desktop's draft of the same structure worked. That is also why run 1's line isn't `fails(deferred-draft:…)`, a form that needs the hub's first draft to have worked.
- **Run 3:** `signin: ok`, `text.format: ok` and `submit_draft: ok`, with all three placements drafting. That is `Go`, with the paths in plan change 1, and it meets the run's part of M0.27's acceptance (`transfer: ok`, `revoked: yes`); `pnpm adr` must still pass.
- **The transfer** (run 3): the hub took the session for its own host ID after the desktop had forgotten it (`transfer.desktopForgot`), drafted with `text.format` in 9,752 ms, refreshed (200, rotated) and revoked. `transfer: ok` shows that the documented transfer works technically. A headless or VPS hub may use it only if OpenAI says yes.
- **After expiry** (run 1): `refreshed true (…), draft USAGE_LIMIT` is the rule's "draft fails after a working refresh". `USAGE_LIMIT` refuses neither the refreshed token, the account nor the route, so it answers the refresh question, and the draft is judged as a desktop draft's would be: another run once the limit allows. Runs 2 and 3 were those runs. They left the step out, as reruns do once an earlier run has answered the refresh question, and run 3, after the setting change, drafted five times. So neither the rule's Inconclusive nor its Not tested branch applies, and `Go` needs no condition from it. The next section says what it leaves open.
- **`revoked: yes`** in all three runs.

Headless-hub use of a transferred session is a separate owner decision at the M0 gate (M0.41 §2), not part of this one, so the header reads `Owner decision: no`.

### The refresh after expiry, from run 1
M0.27c added the step for question s07-02 of the M0 gate review, held before the session: does a session outlive its first access token? Before it, the hub refreshed only minutes after the sign-in, while the product refreshes on demand once the one-hour access token has expired. Third-party reports, not OpenAI's, say a refresh fails after one access-token lifetime, or only after more than two hours without a request. Run 1 alone ran the step. Its facts, from its `transfer.deferred` and its detail `after expiry: refreshed true (rotated true, 180 s after expiry, idle 63 min), draft USAGE_LIMIT`:
- The hub's session sat idle for 63 minutes after its forced refresh (`idleMs` 3,780,015). `Session.accessToken()` then refreshed 180 s after the access token had expired (`msAfterExpiry` 180,015), as it will before a real draft.
- OpenAI answered 200 in 1,350 ms with a full token answer (`refresh.shape`): a new access token (`refreshed` true), a new refresh token (`rotated` true) and an `id_token`, with `expires_in` 3600, `earliest_refresh_at` 3,240 s ahead, and all six scopes. `chatgpt.tokens.use.direct` was among them, so plan usage stayed on.
- The draft whose token request ran that refresh then got a 200 stream that failed with `USAGE_LIMIT` (`subscription_sharing_usage_limit_exceeded`) and no delta. With the refresh, it took 2,742 ms (`draft`). Every other draft of runs 1 and 2 failed the same way.

So a session outlives its first access token after 63 minutes idle, and the refreshed token opened a stream on the plan route. Two things are not shown. No draft of any run completed on a refreshed token: every draft that worked, the hub's in run 3 included, used the sign-in's access token, since the hub drafts before its refresh. And a refresh after more than two idle hours stays open. M7 checks both live.

### Revocation
In every run the hub revoked its newest refresh token (200, `transfer.revocation`). That token was refused when tried again: a 400 whose body has the string fields `error`, `error_description` and `error_reason`, with `error` `invalid_grant` (`transfer.afterRevoke`). The newest access token, tried right after on the model list, got 401 in runs 2 and 3 but 200 in run 1. In run 1 it came from the refresh after expiry and had just been used for the draft after it; in runs 2 and 3 it came from the hub's forced refresh and hadn't been used. The evidence doesn't show why run 1's still worked. The docs don't say revocation ends access tokens, and run 1 shows that it doesn't always do so at once. The two 401s differ too (`transfer.afterRevoke.models.code`): run 2's carried an error object with a `code` field, which the spike reads as `API_ERROR`, and run 3's didn't, which it reads as `ADMISSION_REFUSED`. Both map to `AUTH_EXPIRED` (sign in again).

### Usage limits (runs 1 and 2)
Every draft of runs 1 and 2 was refused: the desktop's four, the hub's, and run 1's draft after expiry. Each got a 200 whose stream failed with `subscription_sharing_usage_limit_exceeded` (`USAGE_LIMIT`) before any delta; none came as the 429 that `notes/sources.md`'s error table gives for that code. In the desktop's drafts, the refusal came after `response.created`, `response.in_progress` and `response.metadata` (`drafts[].error.shape` `event`).

After run 2 the owner read ChatGPT's usage page: the plan had 0% of its weekly limit left, used up by other use of the same plan, not by DraftYak, whose drafts had all been refused. The owner then turned on "Allow other apps to use credits after reaching your usage limit", and all five drafts of run 3 worked, the desktop's four and the hub's. So plan drafting by another app draws on the plan's own limits, and once they are used up, such an app is refused unless the owner allows other apps to use credits. The evidence can't show whether run 3's drafts drew on credits.

### Consent
The owner relayed the screens' wording during run 2, leaving out the account's name and e-mail address:
1. **Account chooser:** an app logo labelled "DraftYak logo"; the title "Use ChatGPT to sign in to DraftYak"; "Choose an account to sign in with ChatGPT"; and a "Select account" button for each account.
2. **Naming:** "Connect your DraftYak to ChatGPT"; "First, what should we call your agent?"; and a "Name" field filled in with "DraftYak", the spike's `agent_name_hint`. It lists no access.
3. **Access:** "Connect DraftYak to ChatGPT"; "Identity", with the account's name and e-mail address; "ChatGPT plan: Allow DraftYak to consume usage from your ChatGPT Plan's limits."; and the buttons "Continue" and "Back". Nothing else is listed: no chat history, files or other access. Staying signed in isn't an item of its own, although every grant held `offline_access` and a refresh token.
4. **DraftYak's callback page:** "DraftYak received the sign-in. You can close this tab."

The owner approved this section's wording for publication on 2026-10-21, after approving run 1's wording of the naming prompt and the callback page: "First, what should we call your agent? Name: DraftYak" and "DraftYak received the sign-in. You can close this tab."

The access screen offered no option to turn plan usage off, as the owner confirmed afterwards: the plan item came with the sign-in, and the only choices were Continue and Back. Every grant held `chatgpt.tokens.use.direct` (`signIn.planScope.granted` in all three runs), so a grant without plan usage, which the spike turns into `PLAN_USAGE_DISABLED`, wasn't seen live. The docs describe declining plan usage (`notes/sources.md`, Consent and Plan permission), so M7 still handles such a grant.

Once, in run 2, OpenAI showed an error page after Continue instead of the callback: "Oops, an error occurred!" and "The server had an error processing your request. Sorry about that! You can retry your request, or contact us through our help center at help.openai.com if you keep seeing this error. (Please include the request ID … in your email.)", with the buttons "Try again" and "Diagnostics". One "Try again" completed the sign-in. Run 2's evidence shows a single sign-in attempt (202,335 ms), so the retry stayed within OpenAI's pages, and the spike's 8-minute sign-in wait covered it. The cause isn't known.

### The seven spike choices (`notes/sources.md`)
1. **Port** (`port`, `lock`): in every run the callback listened on `127.0.0.1:1455`, with no collision and no wait for the kit's machine-wide lock (`lock.waitedMs` 0), and OpenAI redirected there for each new registration. No live run met a collision. The refusal is shown offline: `test/rehearsal.test.ts` ("a port another program holds stops the run before any browser opens") and M0.26's `test/port.heavy.test.ts` (port 1455 held on `127.0.0.1` or `0.0.0.0` gives `PORT_IN_USE`). M7 keeps the fixed port, the connect probe and `PORT_IN_USE` (§4), on reauthorization too, where the docs would let "only the port" vary: a fixed port is one the broker can block (plan change 2). Its likeliest holder is a Codex sign-in, which listens on `localhost:1455` by default (`notes/sources.md`, row 20). The M0 gate review (s07-05) found that the spike's probe of `127.0.0.1` misses a listener on `::1`, where Node's `localhost` binds on this PC, so M7's probe also tries `[::1]:1455`. Every run was a first registration (`signIn.attempts[].registration` `new`), so reauthorization wasn't exercised.
2. **`submit_draft` placement** (`drafts[]`): in run 3 all three placements drafted: the namespace with `tool_choice: "required"`, the `additional_tools` item with `tool_choice: "required"`, and the top level with `tool_choice` naming the function. `text.format` with a strict json_schema drafted too. Each tool draft streamed its arguments in 49–59 `response.function_call_arguments.delta` events inside one output item. Which name and namespace the calls came back under isn't in the evidence: `response.completed` held no output items, so `events.completed.functionCalls` is empty, and the spike's name check had nothing to read. M7 takes `text.format` (plan change 1).
3. **Refresh details** (`signIn.token.earliestRefreshAt`, `transfer.refresh.shape`, `transfer.afterRevoke.refreshShape`): `earliest_refresh_at` is a number of Unix seconds, 3,239–3,240 s ahead in every token answer of every run, against `expires_in` 3600, so 6 minutes before expiry. The hub's forced refresh went out less than a minute after the sign-in, long before that time, and got 200 in all three runs, so OpenAI didn't refuse a refresh sent before it. The spike's rule stands: refresh from 2 minutes before expiry, with `earliest_refresh_at` holding back only a still-valid token. Every refresh answer of every run was the full answer: an `access_token`, a new `refresh_token` (`rotated` true each time), an `id_token` (RS256, with the sign-in's claims less `nonce`), `expires_in` 3600 and the same six scopes. A refused refresh is the 400 described under Revocation.
4. **Discovery** (`discovery`, `jwks`, `signIn.token.idToken`), the same in every run: the authorization, token, revocation and JWKS endpoints all share the issuer's origin, `auth.openai.com` (`sameOrigin` true), at `/api/accounts/authorize`, `/api/accounts/oauth/token`, `/api/accounts/oauth/revoke` and `/.well-known/jwks.json`. Discovery lists only `RS256` for ID tokens, and the JWKS held 4 RSA keys (`RS256`, `sig`). The ID token was RS256 with a `kid`. Its `aud` is an array holding the issued client ID, without `dynamic_agent_client` or the resource; it has no `azp`; and `iss` is the issuer. Discovery's `scopes_supported` lists only `email`, `offline_access`, `openid` and `profile`, although `resource.invoke` and `chatgpt.tokens.use.direct` were granted, so M7 never checks requested scopes against it. The spike's checks hold as written, and M7 keeps them.
5. **Streaming** (`drafts[].upstream[]`, `drafts[].events`, the header names): in run 3 each draft's response head came 942–1,995 ms after the request, and its first body chunk 2–3 ms later. The body then came in 25–51 chunks of 26–4,773 bytes (medians 251–504), 21,057–29,615 bytes in all, and each draft took 4,589–11,033 ms. `response.completed` held no output items in any of run 3's desktop drafts (`repeatsOutput` false), though it carried `usage`. With `store: false` the stream is the only copy of the output, and the spike's check that the stream and the final output agree never applied. In every run the request-ID header is `x-oai-request-id` on `api.openai.com`, and `x-request-id` on `auth.openai.com`'s discovery and token answers; the JWKS answer had neither. No desktop draft's answer carried a `content-type`, rate-limit or `retry-after` header.
6. **Host-ID format:** OpenAI accepted the `urn:uuid:` (UUIDv4) host ID in all three runs (`signin: ok`; the evidence doesn't hold the ID). M7 keeps that form: one random UUIDv4 per hub, stored before its first sign-in. An RFC 9278 thumbprint of a key the hub holds would add no proof, since "OpenAI does not verify possession of the private key", and would tie an ID that must stay stable to a key the hub may rotate.
7. **The callback port in the broker:** plan change 2.

Beyond the seven, in every run: every token answer held the six scopes the spike asks for (`signIn.token.scopes`), and `Session.accessToken()`'s plan check passed (`signIn.planCheck` `ok`). The plan's model list (`models`) held 9 models, 7 of them marked `visibility: "list"`, and the drafts used the first, `gpt-6.1-sol`. The desktop's broker passed every request it recorded (`brokered[]`, verdict `ok`): the four drafts, with only allowlisted fields and the header names `accept`, `authorization`, `content-type`, `user-agent` and `x-stainless-retry-count`, and the model list, with the same names less `content-type`. `revocation` and `leftovers` show nothing else to revoke or clean up: no tokens from a failed sign-in (`orphan` null), no access-only grant (`accessOnly` false), no revocation by the desktop in the hub's place (`fallback` null), no `DY_LIVE_SIWC_*` entry left (`remaining` empty) and no earlier run's tokens (`leftovers.found` false).

### For M7
- **A tool call, if Fallback 1 is taken:** read its name and namespace from `response.output_item.done`. The live route's `response.completed` held no output items (run 3), while M0.26's fakes repeat the output there, so the spike's name check and its stream-against-final check never ran live.
- **Request IDs:** keep `x-oai-request-id` from `api.openai.com`. The spike reads only `x-request-id` and `openai-request-id`, so none of its API calls kept one.
- **Usage limits:** in runs 1 and 2 the limit arrived inside a 200 stream before any delta, and no header warned ahead; M7 also handles the documented 429. The message makes Manage usage the primary action, as OpenAI's UI guidelines ask (`notes/sources.md`, row 11), and says that ChatGPT's usage settings can let other apps use credits after the plan's limit. DraftYak's plan-usage disclosure says that drafts may draw on the account's credits while that setting is on. DraftYak never changes the setting or switches billing itself.
- **Event types:** a `response.metadata` event came in every desktop draft of every run. The stream reader ignores types it doesn't know, as the spike does.
- **The model list** is 567,356 bytes in every run (9 models with 52 field names among them; 139 data frames and an end frame). M7 fetches it seldom and keeps only `slug`, `display_name` and `visibility`.
- **Registrations:** each first sign-in adds a DraftYak entry to the account; the usage page listed two after runs 1 and 2, though both read `revoked: yes`. Every later sign-in reuses the issued client, as `src/auth.ts` does, and disconnecting tells the owner to remove the entry in ChatGPT's settings (the docs name Settings > Security and login > Sign in with ChatGPT; the screens may differ by version).
- **Sign-out:** delete the hub's access token at disconnect as well as revoking the refresh token, and treat a copied access token as usable until it expires, at most an hour (`expires_in` 3600). After revocation the access token's 401 came as `API_ERROR` in run 2 and `ADMISSION_REFUSED` in run 3 (Revocation), so M7 reads either as an ended session.
- **Reasoning effort:** run 3's `text.format` draft used 178 reasoning tokens of its 241 output tokens and took 11,033 ms, with no `reasoning` field in the request, against no reasoning tokens and 4,589–4,971 ms for the tool drafts. That is one draft each, so M7 sets `reasoning.effort` and measures before it picks a default.
- **Still to check live:** a draft that completes on a refreshed token, after expiry above all; a refresh after more than two idle hours; the time to the first delta with each chunk passed on as it arrives (plan change 3); reauthorization with the saved client; API-key mode; a grant without plan usage, which the docs describe but this access screen didn't offer; and, if Fallback 1 is taken, that `response.output_item.done` carries the call's name and namespace.

## Fallback
1. **The plan route refuses `text.format`** (`UNSUPPORTED_CAPABILITY`, or a 400 whose `param` names `text`): SIWC drafts switch to `submit_draft` in the `draftyak` namespace with `tool_choice: "required"`, which drafted in run 3. The SIWC allowlist then takes back `tools` holding that namespace alone, and `tool_choice: "required"`, and the plugin checks the call's name and namespace from `response.output_item.done`. Trigger: that refusal in M7's live check or in use.
2. **Plan usage is unavailable** (`NOT_ELIGIBLE`, `ROUTE_NOT_SUPPORTED`, `SCOPE_NOT_AUTHORIZED`, a grant without `chatgpt.tokens.use.direct`, or the end of plan usage for open-source apps): `ai-responses-api` in `api-key` mode, offered to the owner explicitly and never switched to silently (§4 Credential flow, step 3; §5). API-key mode didn't run here (no key was set), so M7 runs it live. `USAGE_LIMIT` is no trigger: drafting stops with Manage usage, and the owner decides.
3. **A session doesn't outlive a longer idle time, or a refreshed token can't draft** (in M7's live check or in use: a refresh after more than two idle hours fails; a later refresh after expiry is refused as unusable, with `REAUTH_REQUIRED` from `invalid_grant` and the like, or `INVALID_CLIENT`; or a draft on a token refreshed after expiry is refused with `PLAN_USAGE_DISABLED` or a code that refuses the token, the account or the route, such as `ADMISSION_REFUSED`, `API_ERROR` with a 401 or 403, `INVALID_USER`, `SCOPE_NOT_AUTHORIZED`, `NOT_ELIGIBLE` or `ROUTE_NOT_SUPPORTED`, once traced to OpenAI rather than to DraftYak's refresh): the decision becomes `Go with fallback`, and the owner decides before plan usage ships in M7. M7 keeps sessions alive another way, such as a refresh before that idle time runs out, and shows it before plan usage ships; otherwise the owner signs in again, with the saved client, when a draft needs it. Auto-draft stays off for SIWC either way (§5).
4. **OpenAI doesn't allow the transfer on headless or VPS hubs:** plan usage only on a hub that signs in on its own host, and API-key mode for the others. Trigger: OpenAI's answer, or the owner's call at the gate.
