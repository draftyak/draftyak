# ADR 0003: S2 plugin sandbox and host channel

- **Status:** proposed
- **Date:** 2026-10-18
- **Spike:** S2
- **Plan:** §4 Process model (Flags, No inheritance, Transport, Environment, Health), §4 Egress broker, §4 Before every spawn, §9.2 (sandbox escape, inspector and memory rows), §15 S2
- **Owner decision:** yes

## Context
§4 runs every plugin as its own Node process under the permission model. The supervisor builds its argv only from an allowlist (`--permission --allow-fs-read=<pluginDir> --no-experimental-sqlite --disable-sigusr1 --disallow-code-generation-from-strings --max-old-space-size=256`, plus read and write on a node plugin's own data dir, or a second read grant and `--wasm-max-mem-pages=8192` for python), never passes `--allow-net`, `--allow-child-process`, `--allow-worker`, `--allow-addons`, `--allow-wasi`, `--allow-inspector`, `--allow-ffi`, `--allow-openssl-store` or `--inspect*`, scrubs the environment and refuses Node below 26.5.1. MCP runs on stdin/stdout and the JSON-RPC host channel on Node's IPC channel on fd 3 (`stdio[3]='ipc'`, JSON serialization, no handles), because since 26.11 adopting any other inherited fd as a socket needs `--allow-net`; tagged frames on stdin/stdout are the named fallback. Before every spawn the hub re-hashes the bundle and refuses any link, and a hub-side watchdog samples each plugin's RSS every 5 s and kills it above 512 MiB.

§15 S2 asks, on Windows, Linux and macOS and on both 26.5.1 and the bundled 26.12.0: that a child with the production flags under an unpermissioned parent fails every escape attempt, including a Worker with `execArgv: []`, hard links, junctions, prefix siblings of each read grant, a `ctx.fetch` to `127.0.0.1:9229`, and V8 flags changed at runtime through `v8.setFlagsFromString`, with `--freeze-flags-after-init` tested if V8 can be weakened; that `process._debugProcess(hubPid)` and POSIX `SIGUSR1` open no inspector on a `--disable-sigusr1` hub; that `NODE_OPTIONS` isn't inherited and the spawned argv equals the allowlist; that the fd-3 channel works on every OS and `new net.Socket({fd: 3})` fails without `--allow-net` on 26.11 and later; that fuzzing the channel, Node's internal `NODE_*` shapes included, never gets a handle accepted; that the template plugin runs under `--disallow-code-generation-from-strings`; and what RSS sampling and the per-spawn re-hash cost.

`spikes/s02-plugin-sandbox` answers it in three items: M0.11 built the argv, the spawn and the escape suite (21 hostile fixtures, each run in two argv variants, A without and B with the data-dir grant); M0.12 the host channel, the broker stub, the V8, inspector and template-plugin probes and the measurements; M0.13 the cross-OS runs and this ADR. Every case spawns its fixture the way the hub would (`spawnPlugin`: the allowlist argv, checked again before use, the scrubbed environment, the plugin dir as cwd, no shell) from an unpermissioned parent, and aims at canary files in a fake profile outside every grant. The real Startup folder and shell rc files are only probed with `process.permission.has`.

Where each target runs:
- **On the dev box, recorded for this ADR:** Windows 11 x64, with Developer Mode on, so the symlink cases run there too; and Linux x64 in Docker (the digest-pinned `node:26.12.0-bookworm-slim`, `--network none`, a read-only root, uid 65534, on Docker Desktop's WSL2 kernel). Both Nodes in each.
- **Through `pnpm spikes:run`:** run 39090775204, green on both Nodes, covered native Linux x64 (`ubuntu-24.04`) and native Linux arm64 and Docker arm64 (`ubuntu-24.04-arm`, whose Docker suites use the same image: its pinned index has a `linux/arm64/v8` entry). Run A1, 39091096373 on `macos-15`, covered macOS arm64: the escape, V8 and inspector suites passed there, and two tests failed, the host-channel fuzz (The host channel) and the benchmark (Measurements). The macOS rerun is pending; the decision rule at the end of the Decision says how its results change the outcome.

## Options
- **Host channel:**
  - (a) Node's IPC on both ends, the plan's `stdio[3]='ipc'`.
  - (b) Node's IPC in the plugin, with the hub reading fd 3 as a plain pipe through a decoder of its own.
  - (c) The plan's fallback: tagged host frames on stdin/stdout beside MCP.
  - (d) A raw socket on an inherited fd 3, which needs `--allow-net` from 26.11 on.
- **V8 flags:** the plan's argv, or the plan's argv plus `--freeze-flags-after-init`.
- **`node:sqlite`:** rely on the permission model to gate `ATTACH`, or keep the module out with `--no-experimental-sqlite`.
- **VFS** (`node:vfs`, behind `--experimental-vfs`): keep `--experimental-vfs`, `--allow-fs-vfs` and `--vfs-load` off the allowlist, or also name them on the never-list.
- **Links:** rely on the permission model's path checks, or refuse every link (symlink, junction, hard link) in the bundle before each spawn and build the argv from real paths.
- **Main entry:** rely on the read grant to keep the manifest's entry inside the plugin dir, or resolve the entry and refuse it unless it is a file there.
- **Memory reading:** per OS, a new process for each sample (`tasklist`, `ps`), one long-lived reader (a Windows PowerShell answering a pid per line, its script passed encoded, as plain text or as a file), or `/proc` on Linux; on Windows, the working set or private bytes; in Linux, resident pages alone or with swapped-out ones.
- **Memory peaks:** the plan's 5 s tick; a shorter tick; or also a limit the OS enforces, such as a per-plugin Windows Job Object with a process memory limit (`JOB_OBJECT_LIMIT_PROCESS_MEMORY`), which the desktop sidecar (M4), whose job already holds the plugins, could set, or a Linux cgroup v2 `memory.max` (for example through `systemd-run --user --scope`) where the system has one. S2 measured the readings and the tick, not the OS limits.
- **Windows symlink cases:** on the dev box with Developer Mode on, or on a `windows-2025` runner.

## Decision
Go with fallback

Fallback 1, tagged host frames on stdin and stdout, on every OS. Rule (d) of the decision rule below fired in run A1: on macOS the stand-in hub's descriptor count grew when a plugin sent a handle over fd 3. The working hypothesis is that the hub took in the plugin's descriptor, which the macOS rerun's descriptor listing will confirm or refute (The host channel). Everything else S2 tested holds on every target run so far. That run never reached 26.12.0's host-channel cases, and its benchmark failed on a busy machine (rule (a)), so the macOS rerun completes both and names the new descriptors; the owner picks among the remedies at the gate (For the owner at the gate, item 3). Fallback 1 is not a stronger descriptor barrier than fd 3 — a plugin can reinstate `process.send` over stdout (The host channel), so Fallback 1's safety rests on the same hub-side read fd 3 relied on, which must be re-checked on macOS; its gain is one transport, not descriptor-proofness.

Plan changes:
- §4 Flags: every plugin also gets `--freeze-flags-after-init`. Without it, `v8.setFlagsFromString('--allow-natives-syntax')` followed by natives compiled through `node:vm`, which `--disallow-code-generation-from-strings` doesn't block, weakened V8 on both Nodes; with it, the plugin aborts at that call
- §4 Flags: the never-list also names `--experimental-ffi`, `--experimental-sqlite`, `--allow-fs-vfs`, `--experimental-vfs` and `--vfs-load`, and the supervisor's check refuses them, `--debug-port` and any `--inspect*` before a spawn
- §4 Flags and Before every spawn: the supervisor resolves the plugin, data and runtime dirs to their real paths once and builds the grants and the entry from them. Node resolves the entry's real path before loading it, and reading a link on the way that lies outside the grants is denied, so a link above the plugin dir (macOS's `/var` and `/tmp`, a relocated profile folder) fails every spawn with `ERR_ACCESS_DENIED`; the pre-spawn scan refuses a root that isn't its own real path. The same goes for everything else that spawns plugins: M1.14b's testkit process mode, and the contract suites and template smoke that spawn through it (M1.15–M1.17)
- §4 Flags and Before every spawn: Node loads the main entry, and lets it read itself, whatever `--allow-fs-read` says, so the supervisor refuses an entry whose real path isn't a regular file inside the real plugin dir before it builds the argv; a python plugin's entry is exactly `<runtimeDir>/shim.mjs`. The read grant, the link scan and the spike's `buildArgv`, which only wants an absolute path, don't cover it (The main entry, below)
- §4 Transport (Fallback 1): host frames travel tagged on stdin and stdout beside MCP, on every OS. The hub opens no fd 3 and sets no `NODE_CHANNEL_*`, so a plugin starts with no IPC channel: `process.send` and `process.channel` are undefined, and under `--permission` `process.binding`, the public `child_process` API and `Worker` are denied on both Nodes (checked for this ADR on Windows x64 and in Linux x64 Docker). That is not a full barrier: `child_process._forkChild(fd)`, an internal function the permission model does not gate, reinstates `process.send` over any inherited pipe, stdout included, so a plugin can still try to pass a handle. The descriptor barrier is therefore the same hub-side read as fd 3's — the hub reading the pipe as a plain, non-IPC stream — not the absence of an API. That read drops the descriptor on Linux (the hub's count was unchanged across the attempt on both Nodes) and crashes the plugin before the handle is sent on Windows (`UV_HANDLE_NON_OVERLAPPED_PIPE`), and it is the open question on macOS, exactly as for fd 3. A kept control (`fallback1` in `ipc.heavy`, with its own `fallback1-<target>.json`) exercises this on every OS. The decoder's rules carry over (below). S2 measured the design this replaces: fd 3 as a plain pipe (`'overlapped'`, which Windows needs) with `NODE_CHANNEL_FD=3` and `NODE_CHANNEL_SERIALIZATION_MODE=json`, read by the hub's own decoder. It holds on Windows and Linux, but on macOS a plugin that sends a handle grows the hub's descriptor count. The hub never uses Node's own `stdio 'ipc'` either way: its parent side crashes the hub on one malformed line or a fake `NODE_HANDLE_ACK` and, on POSIX, accepts every descriptor a plugin passes
- §4 Environment: on Windows, libuv copies `HOMEDRIVE`, `HOMEPATH`, `LOGONSERVER`, `PATH`, `SYSTEMDRIVE`, `TEMP`, `USERDOMAIN`, `USERNAME`, `USERPROFILE` and `WINDIR` from the hub into a child environment that lacks them, so the supervisor sets each: `TEMP` and `USERPROFILE` (with `TMP`, `APPDATA` and `LOCALAPPDATA`) to the data dir, the rest empty, beside `SystemRoot`
- §4 Health: the watchdog reads Linux `/proc/<pid>/status` (VmRSS plus VmSwap, from the one read), macOS `ps -o rss=` and Windows private bytes rather than the working set, which misses memory a plugin has committed but not touched. It fails closed: a reading it can't take restarts the reader, and a plugin it still can't read is killed. Its 5 s tick bounds sustained use, not peaks: between two ticks a plugin can allocate as much as the machine will commit. The fastest grower allocated 5,352 MiB/s on Windows, 3,783 MiB/s in Docker on the dev box and 8,879 MiB/s on the native Linux x64 runner, about 26, 18 and 43 GiB per tick, and stopped at 1.5 GiB only because that was its own ceiling. How far to bound peaks is the owner's decision (below; §9.2 memory row)
- §4 Egress broker, step 6: unspecified addresses (`0.0.0.0/8`, `::`) count as local, IPv4-mapped and IPv4-compatible IPv6 literals as their IPv4 address, and a hub bound to a wildcard address treats every local interface address as its own

### For the owner at the gate
Go with fallback is proposed; the owner settles these at the gate (m0-gate.md §4):
1. **The Windows memory reader.** Private bytes needs a long-lived `powershell.exe` that the hub starts (3.1 ms a reading, against `tasklist`'s 130 ms). Is that acceptable, with `tasklist`'s working set as the fallback where PowerShell is blocked? The other choices are `tasklist` alone, which misses memory a plugin has committed but not touched, or the desktop sidecar's native reading (M4), which only desktop hubs have.
2. **Memory peaks.** Accept that a plugin can allocate up to the machine's commit limit before the next tick kills it (a kill counts as a crash, and five in 10 minutes disable the plugin); shorten the tick (a reading costs 0.007–0.018 ms through `/proc` and 3.1 ms through the Windows reader, while `tasklist` and `ps` start a process each time: 130 ms, and 4.8–7.2 ms on the Linux runners); or add an OS limit where there is one (Options, Fallback 5). A tick alone can't bound an unthrottled grower: even sampling every 150 ms, growers adding 64 MiB every 60 ms passed the limit by up to 238 MiB before the kill.
3. **The host channel on macOS** (rule (d), run A1; The host channel). The remedies, and what each costs M1.12 (`@draftyak/sdk`'s host channel) and the items after it:
   - (a) **Fallback 1 on every OS**, as rule (d) says; recommended, because it keeps one transport everywhere and removes fd 3, the channel the leak was measured on. It does not by itself stop a plugin from trying to pass a descriptor — `child_process._forkChild` reinstates `process.send` over stdout (The host channel) — so its descriptor safety rests on the same hub-side plain-pipe read as fd 3, which the `fallback1` control re-checks on macOS. M1.12 replaces `ipcHost()` over `process.send` with a host on stdin and stdout: a tagged-line framing in `spec/host-channel-v1.md`, a splitter in front of the MCP stdio transport in `serve`, and its fuzz test run over a spawned child's stdio rather than a `fork()`ed child's IPC channel; it stays an L item. The hub's decoder loses the Windows libuv frames and the `NODE_*` checks and gains the tag check; M1.14b's process mode spawns `['pipe','pipe','pipe']` with no `NODE_CHANNEL_*`; M1.15b's conformance bridge strips host frames before the MCP client sees them; M2c's Python shim leaves `process.send` too.
   - (b) **Fallback 1 on macOS only**, fd 3 elsewhere: the SDK, the testkit and the supervisor carry both transports, chosen per OS and tested on every OS. That is (a)'s work plus keeping the fd-3 code, with no gain where it fails.
   - (c) **A higher Node floor on macOS:** no release is known to fix it. Both pinned Nodes ship libuv 1.52.1 (26.8.0 added only a Windows fs-events patch), and libuv 1.53.0 and its current v1.x branch still read a non-IPC stream with `read(2)`; on the working hypothesis that the leak is in that read path this needs an upstream libuv change first, which the rerun's descriptor listing should confirm. M1.12 would be unchanged.
   - (d) **A reader that closes passed descriptors** on macOS: the hub reads fd 3 with `recvmsg` and closes whatever arrives. Node offers that only through its own IPC parent, rejected above, so it takes native code: an addon in the hub, or the desktop sidecar (M4), which headless hubs don't have. M1.12 would be unchanged; M2 stream 2b gains the addon and its darwin-arm64 and darwin-x64 builds.
   - (e) **Accept it on macOS:** the decoder kills the plugin at the first `NODE_HANDLE` line, so each start leaks the descriptors that arrived with that read (the run A1 count is consistent with one) plus the hub's end of the pipe a leaked descriptor duplicates, which then never closes. libuv spawns with `posix_spawn` and `POSIX_SPAWN_CLOEXEC_DEFAULT` on macOS, so later plugins don't inherit it, and five kills in 10 minutes disable the plugin. M1.12 would be unchanged, but the plan's S2 bar (no handle ever accepted) fails on macOS, and the supervisor must treat `exit`, not `close`, as a plugin's end.
4. **The pending runs:** if the macOS rerun hits rule (c), (e) or (f) below, the outcome that rule names.

### The final argv
In this order, with each path a real path:

```
node plugin:   --permission --allow-fs-read=<pluginDir>
               [--allow-fs-read=<dataDir> --allow-fs-write=<dataDir>]
               --no-experimental-sqlite --disable-sigusr1 --disallow-code-generation-from-strings
               --freeze-flags-after-init --max-old-space-size=256 <entry> [args]
python plugin: --permission --allow-fs-read=<pluginDir> --allow-fs-read=<runtimeDir>
               --no-experimental-sqlite --disable-sigusr1 --disallow-code-generation-from-strings
               --freeze-flags-after-init --max-old-space-size=256 --wasm-max-mem-pages=8192
               <runtimeDir>/shim.mjs <pluginDir>
```

`src/argv.ts` builds it and `test/argv.test.ts` pins it as an inline snapshot. A grant value must be an absolute path with no `*`, `?`, `,` or `=` and no leading `-` (Node reads `*` as everything, and `,` and `=` split one flag into several paths), and the data or runtime dir may neither equal nor sit inside the plugin dir. The VFS flags are never-listed although none is on the allowlist: on both Nodes `--experimental-vfs` alone loads `node:vfs` and constructs a `VirtualFileSystem`, and only mounting it still needs `--allow-fs-vfs` (`ERR_INVALID_STATE` without it). Under the final argv `node:vfs` doesn't load at all.

The real-path rule comes from reproducing macOS's layout for this ADR on both Nodes, in Linux Docker with a symlink and on Windows with a junction: with a plugin dir below a linked folder, an entry named through the link failed to load with `ERR_ACCESS_DENIED` whether the grant named the linked or the real path (in Linux the denied resource was the link itself), and the plugin loaded normally when the argv used the real path throughout. An entry given by its real path with the grant through the link loaded, but every other file of the plugin was denied. It isn't a kept test yet; M2 stream 2b adds one.

### The main entry
The read grant doesn't apply to the main entry: Node loads the file argv names and grants read on that one file, wherever it is. Probes for this ADR, through the spike's `spawnPlugin` with the production argv on both Nodes, on Windows and in Linux Docker:
- An entry at `<pluginDir>/../outside/x.mjs`, or at an absolute path outside every grant, ran and could read itself (`process.permission.has('fs.read', <entry>)` was true), while a file and a module beside it were denied. From inside the plugin dir, the control, both were allowed.
- A file that isn't JavaScript, given as the entry, failed with a `SyntaxError` whose message on stderr quoted its first line.
- Reads and imports at run time stayed inside the grants.

So the supervisor checks the entry itself (plan change above). The spike's `src/` doesn't yet, and M2 stream 2b keeps a test that an entry outside the plugin dir, by `..` or by an absolute path, is refused before the spawn, while a control shows Node alone would load it.

### The host channel
As S2 tested it, the plugin side is Node's IPC on fd 3; the hub side reads newline-delimited JSON on POSIX and, on Windows, libuv's 16-byte frame header (flags, reserved, length, reserved) in front of each JSON line, and writes the same framing. Every byte is treated as hostile, because a plugin can always write raw bytes to fd 3 (`fs.writeSync(3)` isn't gated), and on Windows it can also adopt the IPC fd as a socket. A parse error, invalid UTF-8, a message over 1 MiB (finished or not), a bad frame header, a socket-transfer frame, any `NODE_*` message or anything other than a JSON-RPC 2.0 envelope ends the channel, rejects pending requests and SIGKILLs the plugin. Writes to an exited plugin are dropped and counted, never thrown.

What the probes showed, on both Nodes:
- Node's own parent side (the control, `stdio 'ipc'`) died on one malformed line (`SyntaxError` thrown from the pipe callback) and on a fake `NODE_HANDLE_ACK` (`ERR_INTERNAL_ASSERTION`). In Linux it took all 10 handles a plugin sent: the hub's open descriptors went from 19 to 30 in Docker and from 24 to 35 on the runners, and `close` never fired. JSON serialization is therefore no handle barrier; the decoder is.
- With the decoder, the hub survived every hostile input (10 on Windows, 8 in Linux, natively and in Docker, on x64 and arm64). Each one that reached it ended in the expected violation and a SIGKILL, with nothing dispatched after it; one per OS never got there, because the OS stopped it in the plugin (Windows refuses to pass a pipe handle, `ENOTSUP`; Linux refuses to adopt the IPC fd as a socket, `EEXIST`). In Linux the hub's descriptor count stayed at 19 in Docker and 24 on the runners: reading fd 3 as a plain pipe lets the kernel close, unread, any descriptor a plugin passes.
- **macOS (run A1) is where that fails.** On 26.5.1 the stand-in hub's descriptors went from 13 to 15 in `handle-send`, where the plugin sends its own stdout pipe ten times with `process.send`, and the test stopped at that case, so 26.5.1's last case and all of 26.12.0's never ran. The six cases before it, on the same spawn, pipes and decoder, kept 13; `node-internal`, which sends `NODE_HANDLE` lines with no descriptor attached, among them. The count is the same `/dev/fd` listing in every case, so the change came with the descriptor, not the count. libuv makes each stdio pipe a socketpair (`uv_socketpair` in `uv__process_init_stdio`) and reads the hub's end of fd 3 like any non-IPC stream, with plain `read(2)` (`uv__read`); Linux drops a descriptor attached to bytes read that way, and the working hypothesis is that macOS installs it in the reader's table instead — which the rerun's lsof listing confirms or refutes. Two new descriptors would be what one received descriptor makes when it is the plugin's end of its own stdout pipe: that descriptor, and the hub's end of the pipe, which can't reach end-of-file while the hub holds the other end. Node's IPC parent shows the same shape in Linux (10 handles, 11 more descriptors, no `close`). The timing fits too: the test took 16.5 s, the six cases before account for about 7 s (each probe takes well under a second there, and `raw-socket`'s plugin exits on its own after 3 s), and the 10 s left is the stand-in hub's wait for a `close` that never came. Both pinned Nodes ship libuv 1.52.1, so 26.12.0 should do the same. The decoder still kills the plugin at the first `NODE_HANDLE` line, which bounds the leak per start, but rule (d) counts a growing descriptor count as a failed channel, and the plan's S2 bar is that no handle is ever accepted. The rerun runs every case on both Nodes before it fails, and its failure names each new descriptor with lsof's type, address and peer, which should show the hub holding both ends of the plugin's stdout pipe.
- A non-IPC fd 3 adopted as a socket (`new net.Socket({fd: 3})`) is denied with `ERR_ACCESS_DENIED` on 26.12.0 and adopted on 26.5.1, which predates the 26.11 gate. That costs nothing here: the hub's spawn passes a plugin only fds 0–3, and fd 3 is its IPC channel, which Windows lets a plugin adopt on both Nodes and Linux refuses (`EEXIST`).
- A JSON-RPC round trip works over fd 3, and the broker stub refuses `ctx.fetch` to `127.0.0.1:9229` and to 47613–47615, also spelled as `[::ffff:127.0.0.1]`, `0.0.0.0` and `localhost.`, and lets an ordinary HTTPS URL through. It checks the literal URL; M2 stream 2b's broker applies the same rule to the IP it resolves and connects to.
- **The Fallback-1 control** (added by this item; `fallback1` in `ipc.heavy`, writing `fallback1-<target>.json`). It spawns the plugin with three pipes and no `NODE_CHANNEL_*` — the layout the recommended remedy uses — and the plugin calls `child_process._forkChild(1)` to reinstate `process.send` over stdout, then passes a handle ten times. The permission model gates the public `child_process` API and `Worker`, but not the internal `_forkChild`, so `process.send` comes back; the barrier is the hub-side read, not the API. It held where it was run for this ADR: in Linux x64 Docker the hub's descriptor count was unchanged on both Nodes (19 → 19), and on Windows x64 the plugin aborted in libuv (`UV_HANDLE_NON_OVERLAPPED_PIPE`) before the handle was sent (no `/dev/fd` there, so only hub survival is checked). The native Linux and macOS legs run in the next spikes runs; the macOS leg decides whether Fallback 1 closes the leak there or shares fd 3's.

### What the escape suite showed
On Windows x64 (80 cases: 20 fixtures × 2 Nodes × 2 variants), in Linux x64 Docker (76 cases) and on the runners (76 cases each natively on Linux x64, Linux arm64 and macOS arm64, and in Docker on arm64), every fixture was refused with its expected code and leaked no canary: 0 escapes. That covers the reads outside the grants (the master-key stand-in through six read APIs, the fake profile, prefix siblings of the plugin and data dirs), the writes (the fake Startup folder and `.bashrc`; the real ones probe as not writable), links made at runtime in the writable data dir (absolute and relative symlinks, a hard link, a junction), `child_process`, a Worker with `execArgv: []`, addons, WASI, the inspector, FFI, the OpenSSL store, `node:sqlite`, a `node:vfs` mount, TCP, named pipes and UNIX sockets. The expected codes differ by Node only where the API differs: 26.5.1 has no `node:ffi` and doesn't take a `file:` URL as a key source. Also:
- **Links planted before the spawn:** a symlink, junction or hard link in the bundle makes the spawn refuse (`DY_REFUSED_SPAWN`). With the scan bypassed, the control read the secret through each one on both Nodes: the permission model follows links, so the scan is what holds.
- **The writable data dir:** a link planted there before the spawn is followed too. Only a process running as the same user could plant one, which guardrail 9 already places out of scope, so the data dir isn't scanned and this stays documented.
- **`node:sqlite`:** with `--experimental-sqlite` (the control), `ATTACH` read a database outside every grant on both Nodes; the permission model doesn't see it. `--no-experimental-sqlite` keeps the module out, and it is the defence.
- **Environment and argv:** `NODE_OPTIONS` set in the hub didn't reach the plugin, the plugin's `process.execArgv` equalled the allowlist exactly, and it started no process. A probe for this ADR found the plugin's environment held only `scrubEnv`'s names on both Nodes (Node drops its `NODE_CHANNEL_*` pair at startup): on Windows the ten libuv names among them, in Linux `HOME`, `TMPDIR` and the two ids. The kept suite doesn't check the names yet; M2 stream 2b's argv report adds them.
- **Residuals, documented:** `fs.realpathSync` resolves a path outside the grants, so it reveals whether a file exists (`ENOENT` otherwise) but none of its content; `os.userInfo()` and `os.hostname()` return the hub's user and host names, whatever the environment says (a probe for this ADR, on both Nodes and both OSes; no kept test records it).
- **Not in the suite:** DNS (`dns.lookup`, a `Resolver`'s `resolve4`), UDP (`dgram` bind and send) and the diagnostic writers (`process.report.writeReport`, `v8.writeHeapSnapshot`, `trace_events`) aimed outside the grants. Probes for this ADR with the production argv, on both Nodes and both OSes, got `ERR_ACCESS_DENIED` for each and wrote nothing, but no kept test guards them, so M2 stream 2b adds them as hostile plugins (Kept test).

### V8 flags, inspector and template plugin
- **V8:** under the final argv the attack aborts on both Nodes at `setFlagsFromString`, with V8's `Check failed: !IsFrozen()` (Windows exit code 2147483651, Linux and macOS `SIGTRAP`); natives were refused before it. Without `--freeze-flags-after-init` the same plugin ran natives after the call.
- **Inspector:** against a `--disable-sigusr1` hub, `process._debugProcess(hubPid)` threw on Windows (its remote-thread path), and in Linux and on macOS both it and `SIGUSR1` went through and opened nothing; each time the hub kept answering. A hub without the flag (the control) got its inspector opened.
- **Template plugin:** the MCP server 2.3.1 with the cfWorker validator and zod 4.6.7 in jitless mode answers `server/discover`, `tools/list` and valid and invalid `tools/call` under the final argv. The SDK's default Ajv validator fails there with `EvalError`, so §4 Validators stands.

### Measurements
On the dev box and the Linux runners, under the kit's bench lock after its idle check (the five samples before each benchmark peaked at 16.1% and 12.1% CPU on the dev box, and at 1% or less on the runners):
- **Reading a plugin's memory** (the median of 25 reads of an idle plugin, after a first read):
  - Windows: `tasklist` (CSV, the working set) took 130 ms (87–169 ms; 148 ms for the first read); one long-lived Windows PowerShell answering a pid per line (private bytes) took 3.1 ms (13 ms for the first).
  - Linux: `/proc/<pid>/statm` and `/proc/<pid>/status` took 0.007 ms each in Docker on the dev box and 0.011–0.018 ms on the runners; `ps -o rss=`, which the slim image lacks, took 7.2 ms on the x64 runner and 4.8 ms on the arm64 one.
  - macOS: `ps -o rss=`, not measured yet: run A1's benchmark failed with machine-busy (rule (a), below), so the rerun measures it.
- **What a reading sees:** a plugin holding a 768 MiB `ArrayBuffer` it never touched reads as 35 MiB in `tasklist`'s working set and 788 MiB in private bytes on Windows, and as 42–52 MiB resident in Linux, where `/proc` and `ps` agree. On Windows that memory is committed and counts against the system's commit limit, so only private bytes shows what the plugin holds; in Linux it isn't backed until it is touched.
- **The kill:** sampling every 150 ms, `ArrayBuffer` and `WebAssembly.Memory` growth (64 MiB every 60 ms) was killed with SIGKILL at peaks of 676–750 MiB on Windows and 552–629 MiB in Linux, 0.6–0.9 s after the spawn, all of it beyond `--max-old-space-size=256`. At the plan's 5 s, an unthrottled plugin reached its own 1,536 MiB ceiling in 287–600 ms on Windows and 173–732 ms in Linux (at up to 8,879 MiB/s, on the x64 runner) and was killed at the first sample, 5.0–5.7 s in, 1,058–1,077 MiB over the limit. That overshoot is the fixture's ceiling, not a bound: at the measured rates a 5 s tick leaves room for about 26 GiB on Windows and 18–43 GiB in Linux (`projectedMiBPerPlanInterval`); the dev box has 32 GB of RAM and a 50 GB commit limit.
- **Re-hash before a spawn** (lstat every entry, refuse links, SHA-256 every file; the median of 7 runs): on Windows 7.7 ms for 2 MiB in 16 files, 17.3 ms for 16 MiB in 16 files, and 323 ms for the template-plugin bundle (948 files, 13.3 MiB: the MCP server, its core and zod copied whole); on the Linux runners 2.2–2.9 ms, 14.6–24.4 ms and 32.5–36.6 ms. File count, not size, dominates on Windows, so a plugin bundled into a few files costs tens of milliseconds there.

So the watchdog reads, per OS: Linux `/proc/<pid>/status`, with no process started; macOS `ps -o rss= -p <pids>`, one process per tick for every plugin; Windows private bytes, for every plugin in one round per tick. Two readings have gaps of their own. VmRSS leaves out pages swapped out under memory pressure, which VmSwap in the same file adds (S2 measured VmRSS). macOS's resident size leaves out pages the memory compressor holds, which the task's `phys_footprint` counts, so a native reading through the desktop sidecar (M4) is the fuller one there; until then that gap is documented.

The spike's Windows reader is a long-lived `powershell.exe` started with `-NoProfile -NonInteractive -EncodedCommand`. Security tools often flag `-EncodedCommand`, and the same script works as plain `-Command` text in an environment holding only `SystemRoot` (checked once on the dev box), so M2 stream 2b passes it that way or as a script shipped with the hub, unless the sidecar reads the counter natively. M2 stream 2b also checks the reader on machines with application control (AppLocker, Constrained Language Mode) and falls back to `tasklist` where PowerShell is unavailable (Fallback 3). The spike's watchdog skips a reading it can't take, so a dead reader would never kill; M2's fails closed instead (plan change above). Every kill in the evidence used `tasklist`, so M2 stream 2b repeats the kill with the private-bytes reader when it absorbs `measure.heavy.test.ts`.

## Fallback
1. **Tagged host frames** (§4's named fallback). Host-channel messages travel on stdin/stdout beside MCP, each line tagged so the hub can separate them, and fd 3 isn't opened. The decoder's rules carry over: JSON-RPC only, 1 MiB per message, and any violation kills the plugin. Trigger: rule (d), which fired on macOS in run A1 (Decision).
2. **No plugins on that target.** The hub refuses to spawn plugins on that OS (or Node), as it refuses Node below 26.5.1, until the escape is closed or an OS-sandboxed `isolated` level exists (deferred, §12). Every channel is a plugin, so this keeps DraftYak's channels off that OS, which is the owner's call at the gate. Trigger: rule (e) with no fix.
3. **Another memory reading for that OS.** Windows falls back to `tasklist`'s working set, which misses memory a plugin has committed but not touched; Linux to `ps`. macOS has only `ps`. If that fails, plugins on macOS have no memory bound at all: `--max-old-space-size` doesn't cover ArrayBuffers, node plugins get no wasm cap, and a python plugin's cap covers only its wasm heap. The owner then accepts that gap until the desktop sidecar (M4) reads memory natively, or keeps plugins off macOS until then. Trigger: rule (f), or a reading too slow for the tick.
4. **A Node release changes the model** (the plan's risk table): S2 reruns on every Node bump. A new refusal code, a crash, V8 weakened despite `--freeze-flags-after-init`, or the flag gone fails the kept tests, and plugins stay off that Node release until the change is understood.
5. **A limit the OS enforces** (Options), if the owner wants peaks bounded: per plugin, a Windows Job Object memory limit set by the desktop sidecar (M4), or a Linux cgroup v2 `memory.max` where the system has one. The watchdog stays as the floor everywhere else. Trigger: the owner's decision on memory peaks (Decision).
