# ADR 0003: S2 plugin sandbox and host channel

- **Status:** proposed
- **Date:** 2026-10-19
- **Spike:** S2
- **Plan:** §4 Process model (Flags, No inheritance, Transport, Environment, Health), §4 Egress broker, §4 Before every spawn, §9.2 (sandbox escape, inspector and memory rows), §15 S2
- **Owner decision:** yes

## Context
§4 runs every plugin as its own Node process under the permission model. The supervisor builds its argv only from an allowlist (`--permission --allow-fs-read=<pluginDir> --no-experimental-sqlite --disable-sigusr1 --disallow-code-generation-from-strings --max-old-space-size=256`, plus read and write on a node plugin's own data dir, or a second read grant and `--wasm-max-mem-pages=8192` for python), never passes `--allow-net`, `--allow-child-process`, `--allow-worker`, `--allow-addons`, `--allow-wasi`, `--allow-inspector`, `--allow-ffi`, `--allow-openssl-store` or `--inspect*`, scrubs the environment and refuses Node below 26.5.1. MCP runs on stdin/stdout and the JSON-RPC host channel on Node's IPC channel on fd 3 (`stdio[3]='ipc'`, JSON serialization, no handles), because since 26.11 adopting any other inherited fd as a socket needs `--allow-net`; tagged frames on stdin/stdout are the named fallback. Before every spawn the hub re-hashes the bundle and refuses any link, and a hub-side watchdog samples each plugin's RSS every 5 s and kills it above 512 MiB.

§15 S2 asks, on Windows, Linux and macOS and on both 26.5.1 and the bundled 26.12.0: that a child with the production flags under an unpermissioned parent fails every escape attempt, including a Worker with `execArgv: []`, hard links, junctions, prefix siblings of each read grant, a `ctx.fetch` to `127.0.0.1:9229`, and V8 flags changed at runtime through `v8.setFlagsFromString`, with `--freeze-flags-after-init` tested if V8 can be weakened; that `process._debugProcess(hubPid)` and POSIX `SIGUSR1` open no inspector on a `--disable-sigusr1` hub; that `NODE_OPTIONS` isn't inherited and the spawned argv equals the allowlist; that the fd-3 channel works on every OS and `new net.Socket({fd: 3})` fails without `--allow-net` on 26.11 and later; that fuzzing the channel, Node's internal `NODE_*` shapes included, never gets a handle accepted; that the template plugin runs under `--disallow-code-generation-from-strings`; and what RSS sampling and the per-spawn re-hash cost.

`spikes/s02-plugin-sandbox` answers it in three items: M0.11 built the argv, the spawn and the escape suite (21 hostile fixtures, each run in two argv variants, A without and B with the data-dir grant); M0.12 the host channel, the broker stub, the V8, inspector and template-plugin probes and the measurements; M0.13 the cross-OS runs and this ADR. Four follow-ups came out of the macOS runs: M0.13r added the Fallback-1 control, the descriptor diagnostics and the busy report; M0.13s the FIFO-stdio control (remedy (f), below) and Fallback 1's round trip on spawn's own pipes; M0.13t made the hub end each FIFO at the plugin's exit, because, as read from libuv's and XNU's source, macOS's kqueue never reports a FIFO's end-of-file to Node, and added diagnostics with which the next macOS run would confirm or refute that reading; and M0.13u records that run, rerun 3, which bore the reading out and in which (f) held. Every case spawns its fixture the way the hub would (`spawnPlugin`: the allowlist argv, checked again before use, the scrubbed environment, the plugin dir as cwd, no shell) from an unpermissioned parent, and aims at canary files in a fake profile outside every grant. The real Startup folder and shell rc files are only probed with `process.permission.has`.

Where each target runs:
- **On the dev box, recorded for this ADR:** Windows 11 x64, with Developer Mode on, so the symlink cases run there too; and Linux x64 in Docker (the digest-pinned `node:26.12.0-bookworm-slim`, `--network none`, a read-only root, uid 65534, on Docker Desktop's WSL2 kernel). Both Nodes in each. The FIFO-stdio control runs in the Docker leg; Windows has no FIFOs.
- **Through `pnpm spikes:run`:** run 39090775204, green on both Nodes, covered native Linux x64 (`ubuntu-24.04`) and native Linux arm64 and Docker arm64 (`ubuntu-24.04-arm`, whose Docker suites use the same image: its pinned index has a `linux/arm64/v8` entry). Run A1, 39091096373 on `macos-15`, covered macOS arm64: the escape, V8 and inspector suites passed there, and two tests failed, the host-channel fuzz (The host channel) and the benchmark (Measurements). Rerun 1, 39111041411 on `macos-15` at 8ea0594, passed the escape, V8 and inspector suites again and recorded them, and failed three tests: the host-channel fuzz on both Nodes, the Fallback-1 control, and the benchmark. Rerun 2, 39153457591 on `macos-15` at 1235580 with Spotlight indexing off, passed the escape, V8 and inspector suites and the benchmark and recorded all four, and failed three tests: the fuzz and the Fallback-1 control, as designed (rule (d)), and the FIFO-stdio control, in which, in every mode on both Nodes, a FIFO the plugin writes hadn't closed when the 10 s limit expired (The host channel). Rerun 3, 39223233852 on `macos-15` at 10f9ebf, ran the host-channel file alone (`--tests test/ipc.heavy.test.ts`, M0.42): the FIFO-stdio control passed on both Nodes and wrote `fifo-darwin-arm64.json`, the fuzz and the Fallback-1 control failed again, as designed (rule (d)), and the other ten macOS tests in the file passed, the held-writer control and both lsof self-checks included (its 24 Windows, Linux and Linux Docker tests skip on the macOS runner).

## Options
- **Host channel:**
  - (a) Node's IPC on both ends, the plan's `stdio[3]='ipc'`.
  - (b) Node's IPC in the plugin, with the hub reading fd 3 as a plain pipe through a decoder of its own.
  - (c) The plan's fallback: tagged host frames on stdin/stdout beside MCP.
  - (d) A raw socket on an inherited fd 3, which needs `--allow-net` from 26.11 on.
  - Under (b) or (c), on Linux and macOS: libuv's socketpairs, which Node's spawn makes for every `'pipe'`, or named FIFOs the hub makes itself. A FIFO is one-way and not a socket, so it carries no descriptor, and no IPC channel either: only (c) runs on FIFOs.
- **V8 flags:** the plan's argv, or the plan's argv plus `--freeze-flags-after-init`.
- **`node:sqlite`:** rely on the permission model to gate `ATTACH`, or keep the module out with `--no-experimental-sqlite`.
- **VFS** (`node:vfs`, behind `--experimental-vfs`): keep `--experimental-vfs`, `--allow-fs-vfs` and `--vfs-load` off the allowlist, or also name them on the never-list.
- **Links:** rely on the permission model's path checks, or refuse every link (symlink, junction, hard link) in the bundle before each spawn and build the argv from real paths.
- **Main entry:** rely on the read grant to keep the manifest's entry inside the plugin dir, or resolve the entry and refuse it unless it is a file there.
- **Memory reading:** per OS, a new process for each sample (`tasklist`, `ps`), one long-lived reader (a Windows PowerShell answering a pid per line, its script passed encoded, as plain text or as a file), or `/proc` on Linux; on Windows, the working set or private bytes; in Linux, resident pages alone or with swapped-out ones.
- **Memory peaks:** the plan's 5 s tick; a shorter tick; or also a limit the OS enforces, such as a per-plugin Windows Job Object with a process memory limit (`JOB_OBJECT_LIMIT_PROCESS_MEMORY`), which the desktop sidecar (M4), whose job already holds the plugins, could set, or a Linux cgroup v2 `memory.max` (for example through `systemd-run --user --scope`) where the system has one. S2 measured the readings and the tick, not the OS limits.
- **Windows symlink cases:** on the dev box with Developer Mode on, or on a `windows-2025` runner.

## Decision
Go with fallback

Fallback 1, tagged host frames on stdin and stdout, on every OS, carried on FIFOs instead of socketpairs on Linux and macOS (remedy (f)), for the owner to confirm at the gate, where (d) and (e) remain the alternatives (For the owner at the gate, item 3). Rule (d) of the decision rule below fired in run A1, and rerun 1 (39111041411) confirmed it on both Nodes and named the cause (The host channel): libuv makes every pipe to a plugin a socketpair, the hub reads it with plain `read(2)`, and macOS installs a descriptor sent with those bytes in the reader's table, where Linux drops it. The same rerun showed that Fallback 1 alone doesn't close it: its control reinstated `process.send` over stdout with `child_process._forkChild` and grew the hub's count from 13 to 23; reruns 2 and 3 showed both again on both Nodes. So the evidence supports Fallback 1 as the channel (its round trip and the template plugin pass on Windows pipes, on Linux and macOS socketpairs and on Linux and macOS FIFOs), but not as the descriptor barrier; on macOS the barrier has to be the pipe itself. A FIFO is not a socket, so a plugin's handle-bearing write fails in the plugin (`ENOTSOCK`) whichever stream carries it, fd 3 or a stdout or stderr the plugin made its channel, and in Linux Docker the hub read none of those bytes and its count held across every hostile mode on both Nodes (the FIFO-stdio control). On macOS, rerun 2 (39153457591) ran that control on both Nodes: the hub's count held in all six modes, but in every mode a FIFO the plugin writes hadn't closed when the 10 s limit expired, so the verdict's later checks (the reinstatement, the sends, the bytes read, the `NODE_*` kills and the round trip) never ran. A reading of libuv's and XNU's source explained that without the sandbox: macOS's kqueue never reports a FIFO's last writer closing, and libuv reads a stream only when kqueue says it can (The host channel). So the hub treats the plugin's exit as the end of its FIFOs and reads what is left without blocking. Rerun 3 (39223233852) ran the control again on both Nodes, and (f) held on macOS: `_forkChild` brought `process.send` back over the FIFO stdout and stderr, every handle send ended `ENOTSOCK` in the plugin, over fd 3 and over the reinstated stdout and stderr, the hub read no byte from the FIFO each went over, the decoder killed the `NODE_*` lines, the hub's count held in all six modes, and Fallback 1's round trip and the template plugin worked over FIFOs. Apart from the one the hub closed at a violation, every FIFO the plugin wrote ended at its exit through the drain and none through libuv, as the source reading predicts (The host channel). By the rule set before that run, (f) would have failed on macOS only if a handle send succeeded, the hub read a byte from the FIFO a send went over, a `NODE_*` line wasn't killed, the hub's descriptor count grew, or Fallback 1's round trip or the template plugin didn't work over FIFOs; none of those happened. Everything else S2 tested holds on every target run so far, and with Spotlight indexing off, rerun 2 recorded the macOS benchmark (Measurements).

Plan changes:
- §4 Flags: every plugin also gets `--freeze-flags-after-init`. Without it, `v8.setFlagsFromString('--allow-natives-syntax')` followed by natives compiled through `node:vm`, which `--disallow-code-generation-from-strings` doesn't block, weakened V8 on both Nodes; with it, the plugin aborts at that call
- §4 Flags: the never-list also names `--experimental-ffi`, `--experimental-sqlite`, `--allow-fs-vfs`, `--experimental-vfs` and `--vfs-load`, and the supervisor's check refuses them, `--debug-port` and any `--inspect*` before a spawn
- §4 Flags and Before every spawn: the supervisor resolves the plugin, data and runtime dirs to their real paths once and builds the grants and the entry from them. Node resolves the entry's real path before loading it, and reading a link on the way that lies outside the grants is denied, so a link above the plugin dir (macOS's `/var` and `/tmp`, a relocated profile folder) fails every spawn with `ERR_ACCESS_DENIED`; the pre-spawn scan refuses a root that isn't its own real path. The same goes for everything else that spawns plugins: M1.14b's testkit process mode, and the contract suites and template smoke that spawn through it (M1.15–M1.17)
- §4 Flags and Before every spawn: Node loads the main entry, and lets it read itself, whatever `--allow-fs-read` says, so the supervisor refuses an entry whose real path isn't a regular file inside the real plugin dir before it builds the argv; a python plugin's entry is exactly `<runtimeDir>/shim.mjs`. The read grant, the link scan and the spike's `buildArgv`, which only wants an absolute path, don't cover it (The main entry, below)
- §4 Transport (Fallback 1, on FIFOs): host frames travel tagged on stdin and stdout beside MCP, on every OS, and on Linux and macOS the plugin's stdin, stdout and stderr are named FIFOs rather than spawn's socketpairs (remedy (f)). The hub opens no fd 3 and sets no `NODE_CHANNEL_*`, so a plugin starts with no IPC channel: `process.send` and `process.channel` are undefined, and under `--permission` `process.binding`, the public `child_process` API and `Worker` are denied on both Nodes (checked for this ADR on Windows x64 and in Linux x64 Docker). That is not a full barrier: `child_process._forkChild(fd)`, an internal function the permission model does not gate, reinstates `process.send` over any inherited pipe, stdout and stderr included, so a plugin can still send `NODE_*` lines and try to pass a handle. The decoder's rules therefore cover both lanes of stdout, `NODE_*` lines included (below), and the descriptor barrier is the pipe. On a socketpair a handle-bearing write succeeds and the hub's plain read decides: Linux drops the descriptor (the hub's count was unchanged on both Nodes), Windows crashes the plugin before the handle is sent (`UV_HANDLE_NON_OVERLAPPED_PIPE`), and macOS installs it in the hub (rerun 1: 13 → 23). On a FIFO the write itself fails with `ENOTSOCK`, over fd 3 and over a reinstated stdout or stderr alike, the hub reads none of its bytes, and nothing the hub reads can carry a descriptor (the FIFO-stdio control: Linux x64 Docker on the dev box, and macOS arm64 in rerun 3). So the plan's "a plugin that sends a handle is killed" holds only where the attempt reaches the hub: on a FIFO it fails inside the plugin and the hub never sees it (no kill, no audit entry, no crash count); on Windows the plugin aborts in libuv before anything is sent, an exit the supervisor counts as a crash; on a socketpair (Linux, if FIFOs are used on macOS only) the message arrives as a `NODE_HANDLE` line and the decoder kills the plugin. What the hub kills on every pipe is a `NODE_*` line on either lane of stdout. The hub makes the FIFOs with `mkfifo -m 600` in a fresh 0700 directory under a folder of its own, opens each one's reader first so no open blocks, unlinks them before the spawn, passes the plugin's ends as integer stdio fds and closes its copies once the spawn returns (`src/fifo-stdio.ts`). The FIFOs' end is the plugin's exit, not their end-of-file, which, as read from libuv's and XNU's source, macOS's kqueue never reports to Node (The host channel; rerun 3 bore that reading out, and this rule holds either way): at the exit the hub reads what is left in each FIFO without blocking, until `read` returns 0, which a FIFO does only once no writer is left, hands it to the decoders, checks before every `read` that a decoder hasn't closed the FIFO at a violation, and closes the FIFO; one that still has a writer (`EAGAIN`) is closed anyway and logged. While the plugin runs, a decoder that falls behind pauses the hub's reads, and then the plugin's writes, so a plugin can't grow the hub's memory by flooding a FIFO. The supervisor never waits for a FIFO's end-of-file, never relies on a plugin seeing its stdin end (by the same reading, the gap applies inside the plugin, so it stops a plugin with a host frame or a signal), and closes its stdin writer at the exit, because, by the same reading, kqueue doesn't report a FIFO's reader closing either. Windows keeps libuv's pipes, which hand no descriptor to a reader that doesn't ask for one. A FIFO is one-way, so Node's IPC channel on fd 3, which needs one descriptor both ways, can't run on FIFOs; Fallback 1 can. The kept controls cover both pipes, each with its own evidence file: `fallback1` in `ipc.heavy` (spawn's pipes: the hostile reinstate, Fallback 1's round trip and the template plugin) on every OS, and `fifo` on Linux and macOS, since Windows has no FIFOs. S2 measured the design this replaces: fd 3 as a plain pipe (`'overlapped'`, which Windows needs) with `NODE_CHANNEL_FD=3` and `NODE_CHANNEL_SERIALIZATION_MODE=json`, read by the hub's own decoder. It holds on Windows and Linux, and on macOS a plugin that sends a handle grows the hub's descriptor count. The hub never uses Node's own `stdio 'ipc'` either way: its parent side crashes the hub on one malformed line or a fake `NODE_HANDLE_ACK` and, on POSIX, accepts every descriptor a plugin passes
- §4 Environment: on Windows, libuv copies `HOMEDRIVE`, `HOMEPATH`, `LOGONSERVER`, `PATH`, `SYSTEMDRIVE`, `TEMP`, `USERDOMAIN`, `USERNAME`, `USERPROFILE` and `WINDIR` from the hub into a child environment that lacks them, so the supervisor sets each: `TEMP` and `USERPROFILE` (with `TMP`, `APPDATA` and `LOCALAPPDATA`) to the data dir, the rest empty, beside `SystemRoot`
- §4 Health: the watchdog reads Linux `/proc/<pid>/status` (VmRSS plus VmSwap, from the one read), macOS `ps -o rss=` and Windows private bytes rather than the working set, which misses memory a plugin has committed but not touched. It fails closed: a reading it can't take restarts the reader, and a plugin it still can't read is killed. Its 5 s tick bounds sustained use, not peaks: between two ticks a plugin can allocate as much as the machine will commit. The fastest grower allocated 4,770 MiB/s on Windows, 2,543 MiB/s in Docker on the dev box, 8,879 MiB/s on the native Linux x64 runner and 13,241 MiB/s on the macOS runner, about 23, 12, 43 and 65 GiB per tick, and stopped at 1.5 GiB only because that was its own ceiling. How far to bound peaks is the owner's decision (below; §9.2 memory row)
- §4 Egress broker, step 6: unspecified addresses (`0.0.0.0/8`, `::`) count as local, IPv4-mapped and IPv4-compatible IPv6 literals as their IPv4 address, and a hub bound to a wildcard address treats every local interface address as its own

### For the owner at the gate
Go with fallback is proposed; the owner settles these at the gate (m0-gate.md §4):
1. **The Windows memory reader.** Private bytes needs a long-lived `powershell.exe` that the hub starts (3.6 ms a reading, against `tasklist`'s 132 ms). Is that acceptable, with `tasklist`'s working set as the fallback where PowerShell is blocked? The other choices are `tasklist` alone, which misses memory a plugin has committed but not touched, or the desktop sidecar's native reading (M4), which only desktop hubs have.
2. **Memory peaks.** Accept that a plugin can allocate up to the machine's commit limit before the next tick kills it (a kill counts as a crash, and five in 10 minutes disable the plugin); shorten the tick (a reading costs 0.005–0.018 ms through `/proc` and 3.6 ms through the Windows reader, while `tasklist` and `ps` start a process each time: 132 ms, 4.8–7.2 ms on the Linux runners and 2.9 ms on the macOS runner); or add an OS limit where there is one (Options, Fallback 5). A tick alone can't bound an unthrottled grower: even sampling every 150 ms, growers adding 64 MiB every 60 ms passed the limit by up to 228 MiB before the kill.
3. **The host channel on macOS** (rule (d), run A1 and reruns 1 to 3; The host channel). Rerun 1 settled the cause: macOS hands the hub any descriptor a plugin sends over a socketpair the hub reads, so the leak follows the pipe, not the channel, and Fallback 1 on socketpairs shares it; reruns 2 and 3 showed it again on both Nodes. What (f) has shown on macOS, in rerun 3 on both Nodes (`fifo-darwin-arm64.json`): every handle send ended `ENOTSOCK` in the plugin, ten each over fd 3 and over a stdout and a stderr reinstated with `_forkChild`, and the hub read no byte from the FIFO each went over; the decoder killed the `NODE_*` lines (the `handle` violation and a SIGKILL within about 50 ms); the hub's descriptor count held at 13 in all six modes; every end was an unlinked FIFO at each spawn; the round trip and the template plugin worked over FIFOs; and each FIFO the plugin wrote ended at its exit through the drain, apart from the one the hub closed at a violation. Those are all the checks by which (f) could have failed there (Decision), so (f) meets S2's bar on macOS, as it does in Linux x64 Docker on the dev box. The choice among the remedies below stays the owner's. The remedies, and what each costs M1.12 (`@draftyak/sdk`'s host channel), M2 stream 2b (the supervisor) and the items around them:
   - (a) **Fallback 1 on socketpairs, on every OS**, as rule (d) says. It keeps one transport everywhere and removes fd 3, but rerun 1's control grew the hub's count on macOS (13 → 23), so on its own it fails S2's bar there; it stays the channel under (f). M1.12 replaces `ipcHost()` over `process.send` with a host on stdin and stdout: a tagged-line framing in `spec/host-channel-v1.md`, a splitter in front of the MCP stdio transport in `serve`, and its fuzz test run over a spawned child's stdio rather than a `fork()`ed child's IPC channel; it stays an L item. The hub's decoder loses the Windows libuv frames, gains the tag check and keeps the `NODE_*` checks on both lanes (a plugin can reinstate `process.send` over stdout); M1.14b's process mode spawns `['pipe','pipe','pipe']` with no `NODE_CHANNEL_*`; M1.15b's conformance bridge strips host frames before the MCP client sees them; M2c's Python shim leaves `process.send` too.
   - (b) **Fallback 1 on macOS only**, fd 3 elsewhere: no longer a remedy, since Fallback 1 on socketpairs leaks on macOS as fd 3 does.
   - (c) **A higher Node floor on macOS:** no release fixes it, and none will until libuv changes. Both pinned Nodes ship libuv 1.52.1 (26.8.0 added only a Windows fs-events patch), and libuv's v1.x branch (1.53.1-dev) still makes every stdio pipe with `uv_socketpair` and reads a non-IPC stream with `read(2)`; a fix needs libuv to read with `recvmsg` and close what arrives, or to make stdio pipes with `pipe(2)`.    - (d) **A reader that closes passed descriptors** on macOS: the hub reads with `recvmsg` and closes whatever arrives. Not through Node: its IPC-mode reader hands JS only socket handles, asserts on a file or TTY descriptor and leaves others queued (The host channel), and it is what the hub refuses above. So it takes native code: an addon in the hub, or the desktop sidecar (M4), which headless hubs don't have. M1.12 would be unchanged; M2 stream 2b gains the addon and its darwin-arm64 and darwin-x64 builds.

M1.12 would be unchanged, but S2's bar (no handle ever accepted) fails on macOS, and the supervisor must treat `exit`, not `close`, as a plugin's end.
   - (f) **FIFO stdio under Fallback 1, on Linux and macOS** (recommended; it held on macOS in rerun 3 and in Linux x64 Docker on the dev box): the supervisor makes the plugin's stdin, stdout and stderr named FIFOs instead of spawn's `'pipe'` (The host channel). No native code. At run time it needs `/usr/bin/mkfifo` on the hub's machine (macOS, Debian, Ubuntu and Alpine's busybox all ship it) and a folder the hub can write at every spawn, where it makes that spawn's 0700 directory: the spike uses the system temp dir, but the hub passes a folder under its own data dir (the helper takes it as a parameter), so a read-only setup with no private temp dir, such as M10's hardened service units, can't stop every plugin. M1.12: nothing beyond (a), because the plugin side reads `process.stdin` and writes `process.stdout` as before and Node wraps a FIFO as it wraps a socketpair; but `serve` must not wait for stdin to end before it exits, since, read from the source, a plugin on macOS FIFOs never sees that end. The FIFO spawn needs one home that M1.14b and M2 stream 2b both import, because packages can't import a spike and M2 comes after M1.14b: proposed, `@draftyak/protocol/plugin-stdio`, a Node-only module beside D7's `plugin-argv` (an m1 backlog change like D7, for the owner). Using FIFOs on macOS alone is possible, but leaves a transport that only paid macOS runs test.

   Recommendation: (f) under Fallback 1. It waited on the next macOS run writing `fifo-darwin-arm64.json`, and rerun 3 wrote it, with every finding true on both Nodes. The alternatives are unchanged: (d), native code on macOS, and, until that exists, (e) or no plugins on macOS (Fallback 2).
4. **The pending runs:** none on macOS. ### The final argv
In this order, with each path a real path:

```
node plugin:   --permission --allow-fs-read=<pluginDir>
               [--allow-fs-read=<dataDir> --allow-fs-write=<dataDir>]
               --no-experimental-sqlite --disable-sigusr1 --disallow-code-generation-from-strings
               --freeze-flags-after-init --max-old-space-size=256 <entry> [args]
python plugin: --permission --allow-fs-read=<pluginDir> --allow-fs-read=<runtimeDir>
               --no-experimental-sqlite --disable-sigusr1 --disallow-code-generation-from-strings
               --freeze-flags-after-init --max-old-space-size=256 --wasm-max-mem-pages=8192
               <runtimeDir>/shim.mjs <pluginDir>
```

`src/argv.ts` builds it and `test/argv.test.ts` pins it as an inline snapshot. A grant value must be an absolute path with no `*`, `?`, `,` or `=` and no leading `-` (Node reads `*` as everything, and `,` and `=` split one flag into several paths), and the data or runtime dir may neither equal nor sit inside the plugin dir. The VFS flags are never-listed although none is on the allowlist: on both Nodes `--experimental-vfs` alone loads `node:vfs` and constructs a `VirtualFileSystem`, and only mounting it still needs `--allow-fs-vfs` (`ERR_INVALID_STATE` without it). Under the final argv `node:vfs` doesn't load at all.

The real-path rule comes from reproducing macOS's layout for this ADR on both Nodes, in Linux Docker with a symlink and on Windows with a junction: with a plugin dir below a linked folder, an entry named through the link failed to load with `ERR_ACCESS_DENIED` whether the grant named the linked or the real path (in Linux the denied resource was the link itself), and the plugin loaded normally when the argv used the real path throughout. An entry given by its real path with the grant through the link loaded, but every other file of the plugin was denied. It isn't a kept test yet; M2 stream 2b adds one.

### The main entry
The read grant doesn't apply to the main entry: Node loads the file argv names and grants read on that one file, wherever it is. Probes for this ADR, through the spike's `spawnPlugin` with the production argv on both Nodes, on Windows and in Linux Docker:
- An entry at `<pluginDir>/../outside/x.mjs`, or at an absolute path outside every grant, ran and could read itself (`process.permission.has('fs.read', <entry>)` was true), while a file and a module beside it were denied. From inside the plugin dir, the control, both were allowed.
- A file that isn't JavaScript, given as the entry, failed with a `SyntaxError` whose message on stderr quoted its first line.
- Reads and imports at run time stayed inside the grants.

So the supervisor checks the entry itself (plan change above). The spike's `src/` doesn't yet, and M2 stream 2b keeps a test that an entry outside the plugin dir, by `..` or by an absolute path, is refused before the spawn, while a control shows Node alone would load it.

### The host channel
As S2 tested it, the plugin side is Node's IPC on fd 3; the hub side reads newline-delimited JSON on POSIX and, on Windows, libuv's 16-byte frame header (flags, reserved, length, reserved) in front of each JSON line, and writes the same framing. Every byte is treated as hostile, because a plugin can always write raw bytes to fd 3 (`fs.writeSync(3)` isn't gated), and on Windows it can also adopt the IPC fd as a socket. A parse error, invalid UTF-8, a message over 1 MiB (finished or not), a bad frame header, a socket-transfer frame, any `NODE_*` message or anything other than a JSON-RPC 2.0 envelope ends the channel, rejects pending requests and SIGKILLs the plugin. Writes to an exited plugin are dropped and counted, never thrown.

What the probes showed, on both Nodes:
- Node's own parent side (the control, `stdio 'ipc'`) died on one malformed line (`SyntaxError` thrown from the pipe callback) and on a fake `NODE_HANDLE_ACK` (`ERR_INTERNAL_ASSERTION`). In Linux it took all 10 handles a plugin sent: the hub's open descriptors went from 19 to 30 in Docker and from 24 to 35 on the runners, and `close` never fired. JSON serialization is therefore no handle barrier; the decoder is.
- With the decoder, the hub survived every hostile input (10 on Windows, 8 in Linux, natively and in Docker, on x64 and arm64). Each one that reached it ended in the expected violation and a SIGKILL, with nothing dispatched after it; one per OS never got there, because the OS stopped it in the plugin (Windows refuses to pass a pipe handle, `ENOTSUP`; Linux refuses to adopt the IPC fd as a socket, `EEXIST`). In Linux the hub's descriptor count stayed at 19 in Docker and 24 on the runners: reading fd 3 as a plain pipe lets the kernel close, unread, any descriptor a plugin passes.
- **macOS (run A1 and reruns 1 to 3) is where that fails.** In run A1 the stand-in hub's descriptors went from 13 to 15 in `handle-send` on 26.5.1, where the plugin sends its own stdout pipe ten times with `process.send` over fd 3, and the test stopped there. Rerun 1 ran every case on both Nodes: the seven others kept 13 (`node-internal`, which sends `NODE_HANDLE` lines with no descriptor, among them), and `handle-send` grew the count from 13 to 15 on both, with the plugin SIGKILLed at the violation and `close` never firing (10,014 ms on 26.5.1, 10,016 ms on 26.12.0). lsof named both new descriptors (26.5.1; 26.12.0 the same with other addresses): `fd 13: unix 0xd413be4bb14d6413 ->0xd1157e14697746b3, peer fd 14 (the hub's end of the plugin's stdout); fd 14 (the hub's end of the plugin's stdout): unix 0xd1157e14697746b3 ->0xd413be4bb14d6413, peer fd 13`. fd 13 is the plugin's own end of its stdout socketpair, the descriptor it sent; fd 14 is the hub's end of that pipe, which can't reach end-of-file while the hub holds the other end. Rerun 2 repeated it on both Nodes: the seven others passed, and `handle-send` grew the count from 13 to 15 again, with the plugin SIGKILLed at the violation and `close` never firing (10,015 ms on 26.5.1, 10,013 ms on 26.12.0), lsof naming the same pair: the plugin's end of its stdout socketpair and the hub's end, each the other's peer. Rerun 3 repeated that on both Nodes, `close` again never firing (10,011 ms on 26.5.1, 10,007 ms on 26.12.0), with the same pair. That confirms M0.13r's hypothesis: libuv makes each stdio pipe a socketpair (`uv_socketpair` in `uv__process_init_stdio`, `src/unix/process.c`) and reads the hub's end of fd 3 like any non-IPC stream, with plain `read(2)` (`uv__read`, `src/unix/stream.c`); Linux drops a descriptor attached to bytes read that way, and macOS installs it in the reader's table. One descriptor arrived per start, because the decoder kills the plugin at the first `NODE_HANDLE` line. Rule (d) counts a growing descriptor count as a failed channel, and S2's bar is that no handle is ever accepted.
- A non-IPC fd 3 adopted as a socket (`new net.Socket({fd: 3})`) is denied with `ERR_ACCESS_DENIED` on 26.12.0 (on macOS too, in run A1 and reruns 1 to 3) and adopted on 26.5.1, which predates the 26.11 gate. That costs nothing here: the hub's spawn passes a plugin only fds 0–3, and fd 3 is its IPC channel, which Windows lets a plugin adopt on both Nodes and Linux refuses (`EEXIST`).
- A JSON-RPC round trip works over fd 3 (on macOS too: run A1 and reruns 1 to 3, logs), and the broker stub refuses `ctx.fetch` to `127.0.0.1:9229` and to 47613–47615, also spelled as `[::ffff:127.0.0.1]`, `0.0.0.0` and `localhost.`, and lets an ordinary HTTPS URL through. It checks the literal URL; M2 stream 2b's broker applies the same rule to the IP it resolves and connects to.

- **The FIFO-stdio control** (remedy (f); M0.13s: `fifo` in `ipc.heavy`, `src/fifo-stdio.ts`, writing `fifo-<target>.json`). The stand-in hub makes the plugin's stdin, stdout and stderr named FIFOs: `mkfifo -m 600` in a fresh 0700 temp directory, each FIFO's reader opened first so no open blocks (the hub's ends non-blocking, the plugin's blocking, as a socketpair's are), all unlinked before the spawn, which passes the plugin's ends as integer stdio fds; the hub closes its copies of them once the spawn returns. Before each spawn the stand-in hub checks that every end, its own and the plugin's, is a FIFO with no name left (fstat's `nlink` is 0) and that the directory is gone. No socket joins hub and plugin. Under the exact production argv, on both Nodes, it runs: a round trip in Fallback 1's layout (no fd 3, no `NODE_CHANNEL_*`), with an MCP `ping` on untagged lines and the hub's `plugin/echo` and the plugin's eight `host/fetch` calls in host frames tagged with RS (0x1e, the spike's stand-in for M1.12's tag), every line under the decoder's rules; the template plugin on FIFO stdio (`server/discover`, `tools/list`, valid and invalid calls); and the hostile modes `handle-send` and `node-internal` over an fd-3 channel on a fourth FIFO (`NODE_CHANNEL_FD=3`, which the plugin can only write), `reinstate-send` and `reinstate-internal` over a stdout reinstated with `_forkChild(1)`, and `reinstate-stderr` over a stderr reinstated with `_forkChild(2)`, which reports in a host frame on stdout. A mode holds when the hub survives, its descriptor count doesn't move, every FIFO was unlinked before the spawn, the plugin ends by SIGKILL or on its own within 10 s, every FIFO it writes has ended by the end of the exit drain, at end-of-file (through libuv or the drain) or through the hub's close at a violation, with no writer left at the drain (below), the decoder raises exactly the expected violation (none, or `handle` for the `NODE_*` lines), and each of the ten handle-bearing writes ended with `ENOTSOCK` in the plugin while the hub read no byte from the FIFO it went over; a write that fails for another reason, such as `EPIPE`, fails the mode. Windows is skipped with its reason: it has no FIFOs, and its pipes hand no descriptor to a reader that doesn't ask.
- **The FIFO-stdio control on macOS** (rerun 2, 39153457591, at 1235580; log). It failed on both Nodes: all six modes ended with "a FIFO the plugin writes never closed", and the test took 125.6 s, about 10 s for each of its twelve runs. At 1235580 the stand-in hub waited for the plugin's exit and for every FIFO it writes to close, together, under one 10 s timer from the start of that wait, and at the limit SIGKILLed the plugin and recorded the FIFOs as not closed. So each of those lines says only that 10 s into the wait the plugin hadn't exited or a FIFO it writes hadn't closed: the log doesn't say which FIFOs, or whether the plugin had exited on its own or was SIGKILLed at the limit, because the verdict's "plugin ended" check passes either way. Its verdict then checked in order that the hub survived, that its descriptors were counted, that the count didn't move, that the plugin ended and that every FIFO closed, and stopped at the first failure; so in every mode on both Nodes the hub survived and its count held, and as far as that count shows, no descriptor reached the hub. The log's `evidence not recorded (fifo-darwin-arm64.json)` line names three findings false, `roundTripsOnFifoStdio`, `everyHandleSendFailsWithEnotsock` and `decoderKillsNodeMessagesOnFifos`, each of which needs every check of its modes, and not the other three: `hubDescriptorsHold`, `fifosUnlinkedBeforeEverySpawn` (every end an unlinked FIFO, its folder gone, at each spawn) and `templatePluginServesOnFifoStdio`. Data did cross the FIFOs (the template plugin served, and the benchmark's FIFO spawns got the plugin's first byte); their end wasn't seen within the limit.
- **Why the FIFOs didn't close on macOS, as read from the source:** libuv 1.52.1 (`deps/uv` in Node v26.5.1 and v26.12.0, identical) and XNU 11417.140.69, the newest public source in the runner kernel's line. The runner ran macOS 15.7.9 (24G830) on a later build, `xnu-11417.140.69.711.44~1` (the `osName` in `measure-darwin-arm64.json`), whose source isn't published, so this reading assumes its FIFO and kqueue code is unchanged. Node wraps a FIFO as a pipe (`uv_guess_handle` returns `UV_NAMED_PIPE` for `S_ISFIFO`, `src/unix/tty.c`), and on macOS `uv_pipe_open` falls back to a `select()` thread only if a trial `EVFILT_READ` kevent fails with `EINVAL` (`uv__stream_try_select`, `src/unix/stream.c`). It doesn't for a FIFO: `vn_kqfilter` (`bsd/vfs/vfs_vnops.c`) gives an open FIFO the vnode filter, whose `filt_vnode_common` makes an `EVFILT_READ` knote on a FIFO ready only while `fifo_charcount` counts unread bytes, and sets `EV_EOF` only when the vnode is revoked. Nothing makes that knote ready when the last writer closes: `fifo_close_internal` (`bsd/miscfs/fifofs/fifo_vnops.c`) only marks the FIFO's internal socket `SS_CANTRCVMORE` and posts nothing to the vnode's knotes (`fifo_read` and `fifo_write` do, through `lock_vnode_and_post`), and any post re-counts the unread bytes, which are then 0. A socketpair (`filt_soread_common`, `bsd/kern/uipc_socket.c`) and an anonymous pipe (`filt_piperead_common`, `bsd/kern/sys_pipe.c`) do report their writer's close, with `EV_EOF`. libuv reads a stream only when kqueue reports it (`uv__io_poll`, `src/unix/kqueue.c`); after a read that doesn't fill its buffer it waits for the next event, and it ends the stream only when `read` returns 0 (`uv__read`, `uv__stream_eof`). So, if this reading holds, the hub's FIFO stream never makes the `read` that would return 0, though `fifo_read` returns 0 once no writer is left and the FIFO is empty. libuv says as much: `uv__io_check_fd` (`src/unix/kqueue.c`, libuv PR #4513, in 1.52.1 and on its v1.x branch) refuses FIFOs for `uv_poll` because "the disconnection from the last writer won't trigger an event for kqueue", while streams on FIFOs still use kqueue. In Linux, epoll reports the writer's close, which is why the same control passes in Docker.
- **What else could keep a FIFO open, and how rerun 3 told them apart.** A writer that outlives the plugin would also hold the end back: the hub's copy of the plugin's end, another child that inherited one, or the plugin still running. The stand-in hub closes its copies as soon as the spawn returns, before any wait (`releasePluginEnds`); Node opens every file close-on-exec (`uv__fs_open`) and libuv spawns with `POSIX_SPAWN_CLOEXEC_DEFAULT` on macOS, so no other child inherits a hub descriptor; a plugin may not spawn (no `--allow-child-process`); rerun 2's control ran no `lsof` (it lists descriptors only when the count changes); and the hostile modes exit after 3 s and the round trip 500 ms after its report, well inside the 10 s. libuv's `select()` fallback isn't used for a FIFO, and would have seen the end (`fifo_select` asks the internal socket, which is readable once `SS_CANTRCVMORE` is set). The control now waits for the plugin's exit (`killedAtTimeout` and `exitMs` record whether it was still running at 10 s), gives each FIFO a second more to end through libuv, and then drains each one: a `read` of 0 means no writer was left, which settles the reading above, and `EAGAIN` means one still held the FIFO. Only for such a FIFO does it list the holders: every descriptor on it in the processes of the hub's user, so an inherited or passed copy is named too, matched by device and inode in Linux and by inode on macOS, whose lsof prints no device for a FIFO (one it does print and that differs is marked). It lists every failing check, not just the first, and prints one content-free line per Node, pass or fail: how the FIFOs ended, what the drains returned with the bytes they read, and any mode killed at the limit. If the reading above was right, the next run would show every FIFO ended by the drain with a `read` of 0; a writer that outlived the plugin would show as `EAGAIN`, with its holder named if it ran as the hub's user. Rerun 3 showed the former (below).
- **The fix: the plugin's exit ends its FIFOs** (`drain()` in `src/fifo-stdio.ts`). Once the plugin has exited, the hub reads what is left in each FIFO straight from its descriptor, without blocking, hands it on in order (what libuv read before a pause first) and ends the stream when `read` returns 0; a FIFO that still has a writer (`EAGAIN`) stays open and fails the mode. Each chunk reaches the decoders as it is read, and a decoder may close the FIFO at a violation, which closes its descriptor, so the drain checks before every `read` that the FIFO is still open: a closed descriptor's number can be reused, and a `read` of another file could take its bytes, or, from a UNIX socket on macOS, its descriptors. Only an end-of-file ends a stream; a failed `read` closes it as a failure, which fails the mode. While the plugin runs, the hub's stream passes a slow consumer's backpressure back to libuv, as spawn's own pipes do. Where libuv sees the end (Linux) the stream has usually ended by then and the drain does nothing, so one code path serves both OSes. Every security property stays: a FIFO still carries bytes only, the drained bytes go through the same decoders, the exit comes from the kernel, and the reads never block and stop at 4 MiB.
- **The held-writer control** (`fifo-held` in `ipc.heavy`, on Linux and macOS and in Linux Docker; recorded as `heldWriter` beside the FIFO control's runs, but no finding of that file depends on it). The stand-in hub opens a second write end of a benign plugin's stdout FIFO (through `/proc/self/fd` or `/dev/fd`, so it is the same FIFO) and keeps it past the plugin's exit, as an inherited copy would be kept. The drain must find that writer (`EAGAIN`), the holders must be exactly the hub's read end and that writer, and once the hub closes it, the next drain must end the FIFO with a `read` of 0. In Linux, where libuv ends the FIFO control's FIFOs before its drain, this is the one heavy test that takes those paths, so they run on every target before a paid run relies on them. In Linux x64 Docker on the dev box it passed on both Nodes (`heldWriter` in `fifo-docker-linux-x64.json`): the first drain gave `EAGAIN`, the holders were exactly `hub fd 18 r` and `hub fd 24 w`, and the drain after the hub closed its writer read 0 and ended the FIFO. On macOS, in rerun 3, it passed on both Nodes too (`heldWriter` in `fifo-darwin-arm64.json`): `EAGAIN`, then exactly `hub fd 12 r` and `hub fd 18 w`, then a `read` of 0 that ended the FIFO.
- **The FIFO-stdio control on macOS, rerun 3** (39223233852, at 10f9ebf; `fifo-darwin-arm64.json`). It held on both Nodes, and every finding in the file is true. Before each spawn every end was an unlinked FIFO and the folder was gone. `_forkChild` brought `process.send` back over the FIFO stdout and stderr, and all ten handle sends of each sending mode ended `ENOTSOCK` in the plugin, over fd 3, the reinstated stdout and the reinstated stderr, while the hub read 0 bytes from each of those FIFOs. `node-internal` and `reinstate-internal` ended in the `handle` violation and a SIGKILL within about 50 ms. The hub's count held at 13 in every mode. The round trip (the MCP `ping`, `plugin/echo` and the eight `host/fetch` calls, with the broker's verdicts) and the template plugin passed. Each Node's summary line read `ended eof 0, drain 13, hub 1, error 0, open 0; drains eof 13 (0 bytes), closed 1 (0 bytes); killed at 10 s: none` (log), and the file agrees: every FIFO the plugin writes ended through the exit drain (`endedBy` `drain`, its drain `eof`, `holders` null), each about a second after the plugin's exit, when the control's one-second wait for libuv ran out, except `node-internal`'s fd-3 FIFO, which the hub closed at the violation (`hub`). So libuv ended no FIFO on macOS, and every drain's `read` returned 0, so no writer outlived the plugin: what the source reading above predicts, and not a writer left behind. Both lsof self-checks passed (log), the new one listing exactly the hub's two descriptors on a FIFO, matched by inode.
- **Why a FIFO can't carry a descriptor**, from the libuv 1.52.1 both pinned Nodes ship (identical in 26.5.1 and 26.12.0) and Apple's man pages. A handle leaves a plugin only through `uv_write2` on an IPC pipe, and `uv__try_write` sends it with `sendmsg()` and an `SCM_RIGHTS` control message (`src/unix/stream.c`); descriptors pass only as `SCM_RIGHTS` ancillary data on `AF_UNIX` sockets (`recv(2)`), and `sendmsg()` on anything else fails with `ENOTSOCK` (`sendmsg(2)`: "The argument socket is not a socket"), which `uv__write` records as the request's error, so neither the descriptor nor the message's bytes leave the plugin. Nothing refuses the FIFO earlier: `uv_pipe_open` takes any descriptor and sets readable and writable from its `F_GETFL` mode (`src/unix/pipe.c`), `uv__check_before_write` accepts a send handle on any IPC pipe, and Node 26.12.0's `PipeWrap::Open` exempts fds 0–2 and the IPC channel's fd from the `--allow-net` gate (`LibuvStreamWrap::IsProcessStdioOrIPCChannel`), so a plugin's `process.stdin` and `process.stdout` wrap FIFOs as they wrap socketpairs and `_forkChild(1)` still reinstates `process.send` (26.5.1 has no gate). The hub reads its FIFO ends with the same `read(2)`, and a FIFO delivers bytes only. On macOS `kqueue` accepts FIFOs, so libuv needs no `select` thread for them, but, by the source reading above, it reports their data and not their end.
- **Other no-native options the source suggests, weighed and not adopted:** an IPC-mode reader in the hub (`process.binding('pipe_wrap')`, which reads with `recvmsg`) could close the socket handles it receives, but Node hands JS only TCP, pipe and UDP descriptors, asserts on a file or TTY descriptor (`LibuvStreamWrap::OnUvRead`, `CHECK_EQ(type, UV_UNKNOWN_HANDLE)` after `uv_guess_handle`) and leaves any other queued in libuv until the stream closes, through a deprecated internal binding; an anonymous `pipe(2)` pair would do what an unlinked FIFO does, but Node has no API for one (spawn's `'pipe'` is always a socketpair); and a relay process per plugin only moves the leak into the relay. FIFOs are the soundest no-native option found: the kernel refuses the descriptor in the plugin's own system call.

### What the escape suite showed
On Windows x64 (80 cases: 20 fixtures × 2 Nodes × 2 variants), in Linux x64 Docker (76 cases) and on the runners (76 cases each natively on Linux x64, Linux arm64 and macOS arm64, and in Docker on arm64), every fixture was refused with its expected code and leaked no canary: 0 escapes. That covers the reads outside the grants (the master-key stand-in through six read APIs, the fake profile, prefix siblings of the plugin and data dirs), the writes (the fake Startup folder and `.bashrc`; the real ones probe as not writable), links made at runtime in the writable data dir (absolute and relative symlinks, a hard link, a junction), `child_process`, a Worker with `execArgv: []`, addons, WASI, the inspector, FFI, the OpenSSL store, `node:sqlite`, a `node:vfs` mount, TCP, named pipes and UNIX sockets. The expected codes differ by Node only where the API differs: 26.5.1 has no `node:ffi` and doesn't take a `file:` URL as a key source. Also:
- **Links planted before the spawn:** a symlink, junction or hard link in the bundle makes the spawn refuse (`DY_REFUSED_SPAWN`). With the scan bypassed, the control read the secret through each one on both Nodes: the permission model follows links, so the scan is what holds.
- **The writable data dir:** a link planted there before the spawn is followed too. Only a process running as the same user could plant one, which guardrail 9 already places out of scope, so the data dir isn't scanned and this stays documented.
- **`node:sqlite`:** with `--experimental-sqlite` (the control), `ATTACH` read a database outside every grant on both Nodes; the permission model doesn't see it. `--no-experimental-sqlite` keeps the module out, and it is the defence.
- **Environment and argv:** `NODE_OPTIONS` set in the hub didn't reach the plugin, the plugin's `process.execArgv` equalled the allowlist exactly, and it started no process. A probe for this ADR found the plugin's environment held only `scrubEnv`'s names on both Nodes (Node drops its `NODE_CHANNEL_*` pair at startup): on Windows the ten libuv names among them, in Linux `HOME`, `TMPDIR` and the two ids. The kept suite doesn't check the names yet; M2 stream 2b's argv report adds them.
- **Residuals, documented:** `fs.realpathSync` resolves a path outside the grants, so it reveals whether a file exists (`ENOENT` otherwise) but none of its content; `os.userInfo()` and `os.hostname()` return the hub's user and host names, whatever the environment says (a probe for this ADR, on both Nodes and both OSes; no kept test records it).
- **Not in the suite:** DNS (`dns.lookup`, a `Resolver`'s `resolve4`), UDP (`dgram` bind and send) and the diagnostic writers (`process.report.writeReport`, `v8.writeHeapSnapshot`, `trace_events`) aimed outside the grants. Probes for this ADR with the production argv, on both Nodes and both OSes, got `ERR_ACCESS_DENIED` for each and wrote nothing, but no kept test guards them, so M2 stream 2b adds them as hostile plugins (Kept test).

### V8 flags, inspector and template plugin
- **V8:** under the final argv the attack aborts on both Nodes at `setFlagsFromString`, with V8's `Check failed: !IsFrozen()` (Windows exit code 2147483651, Linux and macOS `SIGTRAP`); natives were refused before it. Without `--freeze-flags-after-init` the same plugin ran natives after the call.

A hub without the flag (the control) got its inspector opened.
- **Template plugin:** the MCP server 2.3.1 with the cfWorker validator and zod 4.6.7 in jitless mode answers `server/discover`, `tools/list` and valid and invalid `tools/call` under the final argv, on spawn's pipes in S2's layout and in Fallback 1's (the Fallback-1 control) and on FIFO stdio (the FIFO-stdio control). The SDK's default Ajv validator fails there with `EvalError`, so §4 Validators stands.

Both rise with the dev box's load (M0.13s's recording, on a busier box, read 206 ms and 6.0 ms), so the gap between them, 34 to 43 times across S2's recordings, is the steadier figure.
  - Linux: `/proc/<pid>/statm` and `/proc/<pid>/status` took 0.005 and 0.007 ms in Docker on the dev box and 0.011–0.018 ms on the runners; `ps -o rss=`, which the slim image lacks, took 7.2 ms on the x64 runner and 4.8 ms on the arm64 one.
  - macOS: `ps -o rss=` took 2.9 ms (2.4–8.6 ms; 14 ms for the first read) in rerun 2, with Spotlight indexing off; the benchmarks of run A1 and rerun 1 had failed with machine-busy (rule (a), below).
- **What a reading sees:** a plugin holding a 768 MiB `ArrayBuffer` it never touched reads as 35 MiB in `tasklist`'s working set and 788 MiB in private bytes on Windows (both Nodes), as 42–52 MiB resident in Linux, where `/proc` and `ps` agree, and as 52–53 MiB in `ps` on macOS. On Windows that memory is committed and counts against the system's commit limit, so only private bytes shows what the plugin holds; in Linux it isn't backed until it is touched.
- **The kill:** sampling every 150 ms, `ArrayBuffer` and `WebAssembly.Memory` growth (64 MiB every 60 ms) was killed with SIGKILL at peaks of 674–740 MiB on Windows, 539–629 MiB in Linux and 565–629 MiB on macOS, 0.6–0.9 s after the spawn, all of it beyond `--max-old-space-size=256`. At the plan's 5 s, an unthrottled plugin reached its own 1,536 MiB ceiling in 322–387 ms on Windows, 173–1,025 ms in Linux and 116–621 ms on macOS (at up to 13,241 MiB/s, on the macOS runner) and was killed at the first sample, 5.0–5.2 s in, 1,058–1,078 MiB over the limit. That overshoot is the fixture's ceiling, not a bound: at the measured rates a 5 s tick leaves room for about 23 GiB on Windows, 12–43 GiB in Linux and 65 GiB on macOS (`projectedMiBPerPlanInterval`); the dev box has 32 GB of RAM and a 50 GB commit limit.
- **Re-hash before a spawn** (lstat every entry, refuse links, SHA-256 every file; the median of 7 runs): on Windows 2.72 ms for 2 MiB in 16 files, 12.4 ms for 16 MiB in 16 files and 76.8 ms for the template-plugin bundle (948 files, 13.3 MiB: the MCP server, its core and zod copied whole); on the Linux runners 2.2–2.9 ms, 14.6–24.4 ms and 32.5–36.6 ms; on the macOS runner 1.4, 9.8 and 28.1 ms. File count, not size, dominates on Windows (the bundle took about six times as long as 16 MiB in 16 files), and the box's load more than either: M0.13s's recording, on a busier box, took 650 ms for the bundle. A plugin bundled into a few files costs milliseconds there.
- **FIFO stdio's spawn cost** (remedy (f); 9 spawns of each kind, alternating which goes first, on the bundled Node, with the production argv, until the plugin's first byte on stdout): in Docker on the dev box the FIFOs' own setup (spawning `mkfifo`, the opens and the unlinks) took 1.62 ms (median; 1.35–2.48 ms), within the spread of a plugin's start, which took 32 ms on FIFOs and 27 ms on socketpairs (medians; 25–59 ms and 23–32 ms). On the macOS runner (rerun 2) setup took 2.4 ms (2.3–4.7 ms), and a start 35 ms on FIFOs and 31 ms on socketpairs (medians; 32–43 ms and 30–41 ms); it waits for the plugin's exit, not the FIFOs' end-of-file, so the FIFO ends rerun 2 didn't see didn't touch it. Windows has no FIFOs; native Linux isn't measured yet. The measurement is best-effort: if FIFO stdio fails on a target, the benchmark records the failure's code in its place and still records the sampler costs and its findings.

So the watchdog reads, per OS: Linux `/proc/<pid>/status`, with no process started; macOS `ps -o rss= -p <pids>`, one process per tick for every plugin; Windows private bytes, for every plugin in one round per tick. Two readings have gaps of their own. VmRSS leaves out pages swapped out under memory pressure, which VmSwap in the same file adds (S2 measured VmRSS). macOS's resident size leaves out pages the memory compressor holds, which the task's `phys_footprint` counts, so a native reading through the desktop sidecar (M4) is the fuller one there; until then that gap is documented.

The spike's Windows reader is a long-lived `powershell.exe` started with `-NoProfile -NonInteractive -EncodedCommand`. Security tools often flag `-EncodedCommand`, and the same script works as plain `-Command` text in an environment holding only `SystemRoot` (checked once on the dev box), so M2 stream 2b passes it that way or as a script shipped with the hub, unless the sidecar reads the counter natively. M2 stream 2b also checks the reader on machines with application control (AppLocker, Constrained Language Mode) and falls back to `tasklist` where PowerShell is unavailable (Fallback 3). The spike's watchdog skips a reading it can't take, so a dead reader would never kill; M2's fails closed instead (plan change above). Every kill in the evidence used `tasklist`, so M2 stream 2b repeats the kill with the private-bytes reader when it absorbs `measure.heavy.test.ts`.

## Fallback
1. **Tagged host frames** (§4's named fallback), on FIFOs on Linux and macOS. Host-channel messages travel on stdin/stdout beside MCP, each line tagged so the hub can separate them, and fd 3 isn't opened. The decoder's rules carry over to both lanes: JSON-RPC only, 1 MiB per message, no `NODE_*` message, and any violation kills the plugin. On Linux and macOS the plugin's stdio are FIFOs (remedy (f)), because on a socketpair macOS hands the hub any descriptor a plugin sends (rerun 1). Trigger: rule (d), which fired on macOS in run A1 and reruns 1 to 3 (Decision). (f) held on macOS in rerun 3; the owner still picks among (d), (e) and (f), or Fallback 2 for macOS, at the gate.
2. **No plugins on that target.** The hub refuses to spawn plugins on that OS (or Node), as it refuses Node below 26.5.1, until the escape is closed or an OS-sandboxed `isolated` level exists (deferred, §12). Every channel is a plugin, so this keeps DraftYak's channels off that OS, which is the owner's call at the gate. Trigger: rule (e) with no fix.
3. **Another memory reading for that OS.** Windows falls back to `tasklist`'s working set, which misses memory a plugin has committed but not touched; Linux to `ps`. macOS has only `ps`. If that fails, plugins on macOS have no memory bound at all: `--max-old-space-size` doesn't cover ArrayBuffers, node plugins get no wasm cap, and a python plugin's cap covers only its wasm heap. The owner then accepts that gap until the desktop sidecar (M4) reads memory natively, or keeps plugins off macOS until then. Trigger: rule (f), or a reading too slow for the tick.
4. **A Node release changes the model** (the plan's risk table): S2 reruns on every Node bump. A new refusal code, a crash, V8 weakened despite `--freeze-flags-after-init`, or the flag gone fails the kept tests, and plugins stay off that Node release until the change is understood.
5. **A limit the OS enforces** (Options), if the owner wants peaks bounded: per plugin, a Windows Job Object memory limit set by the desktop sidecar (M4), or a Linux cgroup v2 `memory.max` where the system has one. The watchdog stays as the floor everywhere else. Trigger: the owner's decision on memory peaks (Decision).
