# ADR 0007: S5 desktop shell, sidecar and keep-awake

- **Status:** proposed
- **Date:** 2026-10-18
- **Spike:** S5
- **Plan:** §7 Pairing (step 6), §7 Bundled sidecar (Spawn, Control protocol, Supervision, Tray, Keep-awake, Autostart, macOS), §7 Master key, §4 Windows desktop, §8 Approval window, §13 Scheduling suite (Desktop), §15 S5
- **Owner decision:** yes

## Context
§7 runs the desktop hub as a sidecar: the official Node binary as Tauri's `externalBin` `draftyak-node`, started from Rust with `std::process::Command` as `draftyak-node --disable-sigusr1 hub.mjs`, on Windows created suspended, put in a kill-on-close Job Object and resumed. The app and the hub talk in length-prefixed JSON frames: on stdin `{masterKey, bootstrapSecret}`, `{power: "resumed"}` after each OS wake and shutdown; on stdout `{ready, l2Port, hubId}` and `{keepAwake: untilMs|null}`; logs only on stderr, and stdin EOF stops the hub. The app checks the hub's health every 10 s and restarts it with a backoff of 1 to 60 s, at most 5 times in 5 minutes. Around it: a tray with Open and Quit, autostart (on by default, starting minimized), the approval window on its own origin with no service worker or storage (§8), the master key from the keychain with a passphrase-wrapped `mk.wrapped` where Linux has no Secret Service, and keep-awake: from T−5 min until `deliverBy` the hub sends `{keepAwake: untilMs}`, and until `null` the app holds a Windows `PowerSetRequest` (SystemRequired), a macOS `IOPMAssertion` (PreventUserIdleSystemSleep) or a Linux logind `idle` block inhibitor (a refusal is logged, not fatal); on wake (Windows `PBT_APMRESUMEAUTOMATIC`, macOS did-wake, logind `PrepareForSleep(false)`) the app sends `resumed` and the hub ticks at once. Pairing (step 6) binds a device's proof to the TLS exporter `EXPERIMENTAL-draftyak-pair-v1` with the pairing id as context, which tokio-rustls on the devices must compute exactly as Node's `exportKeyingMaterial` does on the hub.

§15 S5 asks for all of this with Tauri 2.12 on Windows, macOS and Linux runners. `spikes/s05-desktop` answers it in five items:
- **M0.21 (S5a):** a Rust workspace (`rust/`) with `spike-ekm` (tokio-rustls 0.26.6 on rustls 0.23.46 with `ring` 0.17.14, as TLS 1.3 client with mTLS and as server, against Node 26.12.0, and an aws-lc-rs 1.18.2 trial) and `spike-keyring` (keyring 4.2.0 with the windows-native 1.1.0, zbus-secret-service 1.0.1 and apple-native 1.0.2 stores, and `mk.wrapped`).
- **M0.22 (S5b):** the Tauri 2.12.4 app (`tauri-app/`, identifier `com.draftyak.spike.desktop`, so nothing lands under the product's `com.draftyak.client`) with the supervisor (`src-tauri/src/sidecar.rs`) and a stub hub (`resources/hub.mjs`) that opens SQLite3MC through `nativeBinding` from the bundled prebuild and starts one plugin with S2's flags.
- **M0.23a:** the tray, `tauri-plugin-autostart` 2.7.0 and the approval window on its own custom-protocol origin, checked from Rust through a spike-only control channel (`--spike-control`).
- **M0.23b:** keep-awake and resume (`src-tauri/src/power.rs`); macOS and Linux cases for the backlog's cross-OS checks (the ready frame, the addon, Temporal, containment, a restart, the tray with Open and Quit, closing the main window, autostart, the resume listener and keep-awake); the macOS keychain probe; `ci.json`; and this ADR. Keep-awake and resume use versions the app's and keyring's lockfiles already held, as the census allows: zbus 5.19.0 (Linux), objc2-app-kit and objc2-foundation 0.3.2 with block2 0.6.2 (macOS), and windows-sys 0.61.2 with its `Win32_System_Power` and `Win32_System_SystemServices` features. The spike's control (`{"cmd":"wake"}`) delivers a suspend and resume as far as each OS allows without one: on macOS it posts `NSWorkspaceDidWakeNotification` to NSWorkspace's notification center, which calls the registered block; on Windows it calls the registered callback in-process with each broadcast code; on Linux it calls the wake behind the `PrepareForSleep` filter, while `tests/logind.rs` drives the signal stream itself. Only macOS thus shows the OS's own delivery; on Windows the registration is real, and its delivery waits for the owner's optional real sleep (Evidence).

## Options
- **Main thread resume (Windows):** `ResumeThread` on the primary thread's handle needs `ChildExt::main_thread_handle`, unstable in Rust 1.95 (rust-lang/rust#96723); the alternative is a Toolhelp32 thread snapshot of the new process, then `ResumeThread` on its only thread.
- **Health check:** an echo probe on the hub's L2 port; a `{ping}`/`{pong}` control frame, which extends §7's frame set; or, in M4 where L2 is TLS 1.3, a handshake that must reach ServerHello in time.
- **Containment off Windows:** the hub as leader of its own process group, killed as a group on restart and shutdown, with the hub ending its plugins on stdin EOF; or also `PR_SET_PDEATHSIG` with a reaper on Linux and a parent watcher on macOS, for a hub that stops reading stdin.
- **Keep-awake:** §7's per-OS holds, or `SetThreadExecutionState` on a dedicated thread (Windows), a `caffeinate` or `systemd-inhibit` child process (macOS, Linux), or the desktop session's own inhibitors (`org.freedesktop.ScreenSaver`, GNOME's session manager).
- **When a hold ends:** only on the hub's `null`, as §7 says, or also when `untilMs` passes, when the hub that asked exits and when the app quits.
- **Resume listeners:** `PowerRegisterSuspendResumeNotification` with a callback, or `WM_POWERBROADCAST` on a window of the event loop (Windows); `NSWorkspaceDidWakeNotification`, or `IORegisterForSystemPower` on a run loop (macOS); logind's `PrepareForSleep` signal, or nothing beyond the hub's own wall and monotonic clock check (Linux, §3 Scheduler).
- **Master key store:** the first store that starts, or the store that survives a real write and read, falling back to `mk.wrapped`.
- **Autostart:** `tauri-plugin-autostart` as it ships, the plugin behind an app command that applies an elevation guard and cleans up, or writing the per-user entries directly.
- **Approval window:** a custom protocol registered for every webview, guarded by the webview's label, or a separate origin served from the hub.

## Decision
Go

Plan changes:
- §7 Pairing step 6: none. Nothing in S5 changes the exporter: label `EXPERIMENTAL-draftyak-pair-v1`, context the 16 raw pid bytes, 32 bytes out. rustls's exporter equals Node's in both roles, with `ring` and with aws-lc-rs (Evidence), which is the equality M1.21's pairing draft relies on (its decision D11, accepted)
- §7 Spawn: on Windows the supervisor resumes the suspended hub through a Toolhelp32 thread snapshot and `ResumeThread` until `ChildExt::main_thread_handle` is stable, then one `ResumeThread` on that handle. The hub's environment is an allowlist (`SystemRoot`, `TEMP`, `TMP`, `USERPROFILE`, `LOCALAPPDATA`, `APPDATA`, `HOME`, `TMPDIR`, the four `XDG_*` folders, `LANG`, `LC_ALL`, `TZ`) plus what the app adds, so `NODE_OPTIONS` and `PATH` never reach it. On macOS every Node, the hub and its plugins alike, also has `__CF_USER_TEXT_ENCODING`, which CoreFoundation sets in its own process as it loads, so a check of a Node's environment allows that one name there (Evidence)
- §7 Supervision: the health check needs no new frame: every 10 s a ready hub must answer on L2 within 2 s, and 3 misses in a row restart it; the spike echoes a probe, M4 completes a TLS handshake to ServerHello. A hub that fails the same way at every start (a wrong key) spends the restart budget and stops; M4 may add a "fatal, don't restart" exit code
- §7 Supervision, macOS and Linux: the hub leads its own process group, which restart and Quit kill. When the app itself dies, only stdin EOF ends the hub, so M4 adds `PR_SET_PDEATHSIG` with a reaper on Linux and a parent watcher on macOS (the Evidence's `posixIgnoredEof` case shows the gap: on Linux a hub that ignores EOF, and its plugin, outlived the killed app; macOS's record comes with the B1 rerun)
- §7 Keep-awake: the app also ends a hold when `untilMs` passes, when the hub that asked for it exits and at Quit, so a hub that dies holding it can't keep the machine awake; a refusal is logged and reported, and the next frame tries again. In turn the hub sends `{keepAwake: untilMs}` again at every start (its start tick) while any item is between T−5 min and `deliverBy`, since after a crash and restart in that window nothing holds the machine awake until it does (M2a's scheduler, M4's supervisor)
- §7 Keep-awake, resume: Windows registers with `PowerRegisterSuspendResumeNotification(DEVICE_NOTIFY_CALLBACK)`, which needs no window, and acts only on `PBT_APMRESUMEAUTOMATIC` (`PBT_APMRESUMESUSPEND` follows it only when a user is present, so acting on both would send `resumed` twice); macOS observes `NSWorkspaceDidWakeNotification` on NSWorkspace's notification center; Linux follows logind's `PrepareForSleep` signal on the system bus
- §7 Keep-awake, test hooks: the mocked power layer, `simulate_wake`, the spike's switches (`DRAFTYAK_SPIKE_POWER`, and `DRAFTYAK_SPIKE_KEEP_AWAKE`, which lets any local client make the stub hub send `{keepAwake}` through its L2 port) and `--spike-control` with its `power` and `wake` commands are for tests only; M4 keeps them behind a test-only feature, and `release-guard` checks that release builds lack them, as it does for §7's mock key store
- §7 Tray: Quit destroys every window and waits until they are gone before it exits, because WebView2 holds a window's data folder until its webview is destroyed; closing a window never stops the hub. Off Windows the spike checked the tray through Tauri's menu and its handler only, so M4 also checks the native tray menus on macOS (the status item's menu) and Linux (the indicator under a real panel), beside §8's WKWebView and WebKitGTK checks
- §7 Autostart: never through the plugin's own commands, which skip any guard; the app refuses to enable while elevated, because auto-launch 0.6.0 under `tauri-plugin-autostart` 2.7.0 then writes the machine-wide `HKLM\…\Run`; enable only on the owner's first-run choice (enabling rewrites `StartupApproved` and undoes a Task Manager disable), remove the `StartupApproved` value the plugin leaves behind, quote the Run value and the `.desktop` `Exec` line, and name the entry after the identifier
- §7 Master key: the store is chosen at first start by a real write and read; `NoStorageAccess` or `PlatformFailure` falls back to `mk.wrapped` (or asks again), and later starts use the store that holds the key without choosing again. Windows keeps the key `Local`. On macOS (run B1, prompts off) the login keychain served the ad-hoc-signed build and refused a copy re-signed under another identifier, as an update's new code identity would be, with `errSecAuthFailed`. That is securityd refusing, without UI, a binary the item doesn't trust: with prompts off it never tries a prompt, and both the item's ACL check and its partition-ID check (`validatePartition`) throw `CSSM_ERRCODE_OPERATION_AUTH_DENIED`, which `SecKeychainErrFromOSStatus` maps to `errSecAuthFailed` (Evidence), whether or not a prompt would have been possible. The owner's choice: if an update can be approved through a prompt, §7's "keychain prompts on updates" holds (one prompt per update; Always Allow adds the new binary and its partition) and macOS stays `Go`; if not, Fallback 3. The B1 rerun settles which from the item's access list (rule 3). M4 then checks that prompt on a desktop session, takes Fallback 3 if none comes after a code-identity change, and defines what a read refused after an update leads to
- §8 Approval window: its custom protocol answers only the approval window's label (403 to any other webview), its CSP comes from the response header, it navigates only within its own origin, and it is in-private with its own data folder; windows are built and destroyed off the event loop's handlers. These checks ran on WebView2 only, so M4 runs them on WKWebView and WebKitGTK as well. Tauri's isolation pattern and `freezePrototype`, which §8 asks for, are not proven with this CSP and Trusted Types, so M4 proves them together in both windows before it cites the spike's CSP
- Version pins (the backlog's rule): security-framework 3.7.0 is outside the census, and "no crate in two majors per lockfile" can't hold with tauri 2.12.4. The app's Cargo.lock (456 packages, every target's) holds 22 crate names at two or three majors, none from the power crates: base64, bitflags, getrandom, hashbrown, heck, indexmap, jni-sys, miniz_oxide, png, proc-macro-crate, r-efi, schemars, serde_spanned, syn, thiserror, thiserror-impl, toml, toml_datetime, toml_edit, windows-sys and winnow from tauri's tree, and dirs (6.0.0 from auto-launch beside tauri's 7.0.0). `rust/`'s Cargo.lock holds M0.21's 4: getrandom 0.2.17, untrusted 0.9.0 and windows-sys 0.52.0 through ring, untrusted 0.7.1 through aws-lc-rs, and syn 2 beside 3

### Why Go
On Windows every check of §15 S5 passed: the ready frame, the addon loaded from the bundled resources, Temporal present, the plugin inside the hub's Job Object, a killed hub back within 60 s with the same identity, nothing of the build left once the app is killed, the tray with Open and Quit, autostart's entry created and removed, the approval window's checks, the resume listener registered, and keep-awake held and released as the OS reports it (Evidence). In Linux Docker, the store choice holds in all five Secret Service states. The EKM matches both ways. The xvfb run passed every check that runs on Linux, and run B1 every macOS check but the supervisor's Rust tests, whose three failures were the test's own (Evidence). The B1 rerun completes that cell and settles the macOS keychain: a copy with a new code identity was refused without a prompt, as `errSecAuthFailed`, which securityd returns for a binary the item doesn't trust whenever prompts are off (`validatePartition`, `SecKeychainErrFromOSStatus`), so whether an update can be approved through a prompt is still open. `Go` stands if it can; if not, Fallback 3 makes macOS `Go with fallback` (rule 3).

### Decision rule for run B1 and the xvfb run
1. Every case passes on both: `Go` stands, and the pending cells take their values.
2. A keep-awake hold refused by logind's policy on the runner (`org.freedesktop.DBus.Error.AccessDenied` or `InteractiveAuthorizationRequired`), logged and reported with the app still running, is the plan's own fallback and passes; the case fails on any other refusal. A hold that `systemd-inhibit --list` shows means logind registered the idle inhibitor; whether a desktop's own idle suspend honours it is not tested, and M4 checks it on a GNOME or KDE session.
3. The keychain probe: the binary that made the item reads it with prompts off, and a copy re-signed under another identifier, as an update's new code identity would be, is refused. With prompts off that refusal is `errSecAuthFailed` whether or not securityd could prompt for it (Evidence; M0.23c corrected the `errSecInteractionNotAllowed` this rule first named), so the item's access list decides. If its decrypt entry holds a keychain-prompt subject (`itemAccess.decryptPrompt`), an update gets one prompt, and Always Allow adds the new binary and its partition: §7's "keychain prompts on updates", `Go`. No prompt possible after an update, a prompt even for the binary that made the item, or a round trip that fails even in a temporary keychain makes it `Go with fallback` with Fallback 3. `keyring-macos.json` records each outcome; the case fails only when `security`, `codesign` or `spike-keyring` fails at a step the probe needs, never on reading the access list.
4. The tray, a window or the hub failing on one OS makes it `Go with fallback` for that OS, with the failing check named here and the fix moved to M4.

### The runs, by the rule
- **The xvfb run** (39112591369): every case passed (rule 1). logind registered the `idle` inhibitor rather than refusing it, so rule 2's refusal never arose: `systemd-inhibit --list` showed the hold only while it was held.
- **Run B1** (39113384587): the tray, the windows, the app's hub cases, keep-awake (`pmset -g assertions`), resume, the EKM and the aws-lc-rs trial passed. For the keychain, the binary that made the item needed no prompt and the round trip passed in the login keychain. The re-signed copy was refused, with `errSecAuthFailed` (-25293) on read and `errSecInvalidOwnerEdit` (-25244) on delete, not the `errSecInteractionNotAllowed` (-25308) the probe expected. Apple's `SecKeychainSetUserInteractionAllowed` page doesn't settle what that means: it names `errSecInteractionRequired` for the unlock dialog only and gives no code for an access dialog. Apple's published Security source does: with prompts off the client sends securityd no prompt credential, and securityd denies the binary without trying a prompt (`validatePartition` calls `extendPartition` only for credentials that authorize UI), as `CSSM_ERRCODE_OPERATION_AUTH_DENIED`, which `SecKeychainErrFromOSStatus` maps to `errSecAuthFailed` (Evidence). That code comes whether or not a prompt would have been possible, so run B1 leaves rule 3 open. Rule 4 didn't apply: the three Rust tests that failed did so on the test's own staging and environment check, not on the supervisor or the hub.
- **Pending the B1 rerun** (`pnpm spikes:run --spikes s05 --os macos-15 --node bundled`): the macOS cell for the supervisor's Rust tests, rule 1 if they pass and rule 4 for macOS if the supervisor itself fails; and rule 3, from the item's access list in `keyring-macos.json`. `itemAccess.decryptPrompt` `true` keeps `Go`, with one prompt per update for the owner to confirm; `false`, no prompt possible after an update, takes Fallback 3 for macOS's master key. Apple's source expects `true`: a new item's default access trusts the binary that made it and asks the user about any other (`Access::makeStandard`).

## Fallback
1. **Keep-awake refused or ignored** (polkit refuses the inhibitor, or a desktop's own idle handling doesn't honour logind's): nothing changes for sends; the lateness window and re-approval already cover a sleeping hub, the tray's Quit list warns, and the availability line recommends an always-on hub (§7, §8).
2. **Resume notification missing** (a Linux system without logind, a sandbox without the system bus): the hub's tick after a wall and monotonic divergence over 5 s (§3 Scheduler) still runs, just later.
3. **macOS keychain unusable for an ad-hoc build** (no prompt possible after an update, or a prompt even for the binary that made the item): the master key falls back to `mk.wrapped` with the unlock prompt, as on Linux without a Secret Service, until signed builds (after the MVP).
4. **No death signal or watcher on Linux or macOS** (if M4 can't make them work): the hub's own exit on stdin EOF, which the posix cases check, stays the only guard, and M4's start refuses to run a second hub while one from an earlier launch still holds the store.

Both throw `CSSM_ERRCODE_OPERATION_AUTH_DENIED`, which `SecKeychainErrFromOSStatus` maps to `errSecAuthFailed` (`OSX/libsecurity_keychain/lib/SecBase.cpp`). `errSecInteractionNotAllowed`, the probe's expectation, maps from `CSSM_ERRCODE_NO_USER_INTERACTION`, which securityd raises when a dialog is due in a session without graphic access (`securityd/src/agentquery.cpp`); the client returns it when it needs UI itself, such as for a missing default keychain (`StorageManager.cpp`). So the refusal's code can't say whether a prompt would have come. From M0.23c the probe also records the item's access list in CI (`itemAccess`, from `security dump-keychain -a`, which reads ACLs and decrypts nothing): each entry's authorizations and form, and `decryptPrompt`, whether an entry that authorizes decrypt is in the trusted-app-list form, which always ends in the keychain-prompt subject securityd asks the user through (`OSX/libsecurity_keychain/lib/ACL.cpp`, `ACL::parse`). A new item's default access gives decrypt that form (`Access.cpp`, `makeStandard`), so the B1 rerun is expected to show `decryptPrompt: true` (rule 3).
- **Run B1's three failing tests, and their fix (M0.23c).** In `tests/sidecar.rs`, two tests started the stub hub with its plugin staged under `env::temp_dir()`, which is `$TMPDIR` (`/var/folders/…`), and macOS's `/var` is a link to `private/var`. Node resolves the main entry's real path before loading it, and `fs.realpathSync` stats each link on the way (`binding.stat`, `node:fs:3468`), which the permission model checks against the read grant, so every plugin start died with `ERR_ACCESS_DENIED` on `/var` until the restart budget ran out: ADR 0003's real-path rule. The app's macOS cases passed because they stage below the real path of their temp folder (`fs.realpathSync`). The test now makes its folder in the temp folder and stages below that folder's real path (`fs::canonicalize`, in drive-letter form on Windows), as M2 stream 2b's supervisor builds grants and entries from real paths. With the temp folder reached through a directory symlink, on the dev box and in the pinned Linux image of `rust/Dockerfile`, the old test fails the same way, the denied resource being the link, and the fixed one passes. `test/sidecar.heavy.test.ts`'s Windows cases now stage by real path too; S5's other temp folders give no plugin a grant. The third test found `__CF_USER_TEXT_ENCODING` in the hub's environment. The supervisor clears the environment (`Command::env_clear`: the hub inherits nothing from the app) and adds only `KEEP_ENV` and `Config::env`. CoreFoundation, which Node links on macOS (`node.gypi`: `-framework CoreFoundation`), runs `__CFInitialize` as it loads (`-init ___CFInitialize`), which calls `__CFStringGetUserDefaultEncoding` "to force the potential setenv to occur early": when the variable doesn't already hold this user's value, it sets `__CF_USER_TEXT_ENCODING` (`0x<uid>:…`) in the process itself (Apple's published CoreFoundation source: `CFRuntime.c`, `CFStringEncodings.c`). So every Node on macOS has it, whatever its parent passed; the test allows that one name there and stays strict for every other.
