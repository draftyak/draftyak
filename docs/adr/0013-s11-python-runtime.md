# ADR 0013: S11 Python runtime on Pyodide (M2c go/no-go)

- **Status:** proposed
- **Date:** 2026-10-18
- **Spike:** S11
- **Plan:** §4 Python runtime, §4 Flags, §4 Health, §9.2 (Python rows), §15 S11, §15 Defaults 10
- **Owner decision:** yes

## Context
§4 runs a `python` plugin as unmodified Pyodide 314.0.7 (CPython 3.14.2, ABI `pyemscripten_2026_0`) inside the plugin's own permissioned Node process, as a `standard` plugin with a JS plugin's powers. Its only extra grant is a second `--allow-fs-read=<runtimeDir>`, which the shim drops before plugin code runs, and its argv adds `--wasm-max-mem-pages=8192`, a 512 MiB wasm heap cap. The shim boots in §4's order (a constants-only `process.binding` stub; `loadPyodide` from local wheels only; abort on any loader error or CDN notice; drop both read grants; serve the entry on stdio MCP), and C-extension wheels ship only if they are on the runtime's allowlist: Pyodide builds that load under `--disallow-code-generation-from-strings`. The hub's watchdog kills a `python` plugin above 1 GiB, and the hub kills a plugin whose call still hasn't answered 5 s after its timeout.

§15 S11 asks for (a)–(h) on Windows x64, macOS arm64 and Linux x64 and arm64, each on 26.5.1 and 26.12.0, and makes M2c the owner's call at the gate. Any escape, any new grant, or any budget missed by more than 2× on a native, unloaded run is a FAIL, with the fallback ladder: (1) narrow JS shims in hub code, never new grants or edits to MPL files, fixes upstream; (2) an async-only SDK if JSPI misbehaves; (3) build-id-pinned snapshots or fewer C-extension wheels if budgets are missed; (4) the owner decides whether Python moves after the MVP to an OS-sandboxed `isolated` level.

`spikes/s11-python-runtime` answers it in three items: M0.33 (`fetch-runtime`, the shim, the boot test: (a) and (d)), M0.34 (the escape, audit, print and timeout suites and the tamper cases: (b), (e), (f), (h)) and M0.35 (the allowlist (c), the budgets (g), `ci.json` and this ADR); M0.35b fixed the macOS audit's connection watcher. Every plugin is spawned as the hub would spawn it (S2's `spawnPlugin` through `spawnPythonPlugin`: the runtime copy re-hashed against `runtime.lock.json`, the bundle checked against its lock, the exact production argv with `--freeze-flags-after-init` from ADR 0003, the scrubbed environment, the fd-3 host channel read through S2's decoder), from an unpermissioned parent. That channel is ADR 0003's to decide; Fallback 7 says what changes here if it moves.

Where each target runs:
- **On the dev box, recorded for this ADR:** Windows 11 x64 with Developer Mode on; Linux x64 in Docker (the digest-pinned `node:26.12.0-bookworm-slim`, `--network none`, a read-only root, uid 65534, on Docker Desktop's WSL2 kernel). Both Nodes in each. Budgets count only on native targets, so Docker gives no budget row.
- **On GitHub's runners, through `pnpm spikes:run`:** run 39146936776 tested 50ff9e8, M0.35's commit on m0, natively on Linux x64 (`ubuntu-24.04`) and Linux arm64 (`ubuntu-24.04-arm`), each with a Docker leg on the same pinned image (its index holds a `linux/arm64/v8` manifest); run A2, 39149374954, tested 50ff9e8 on macOS arm64 (`macos-15`); and the macOS rerun, 39182071413, tested 424c827, after M0.35b's watcher fix, with the escape and audit files alone (`spikes:run --tests`). `ci.json` runs the whole S11 `test:heavy` on each runner: boot, audit, escape, prints, timeout, tamper, allowlist and budgets. As every file's fingerprint records, the Linux runners have 2 CPUs (an AMD EPYC 7763 on x64) and the macOS runner is a 3-CPU Apple M1 virtual machine.
- **The dev box runs other builds in parallel,** so the budget test holds the kit's bench lock and passes its idle check (CPU under 20% for 5 s) before it measures, then samples the CPU between plugins while it measures ((g) says when a row counts). On `macos-15` the lock works, but S2's idle check failed there twice: in run A1 (39091096373) at 100% CPU, and in 39111041411, where Spotlight's indexing of the install used about 290% CPU on the 3-CPU runner, so `spikes.yml` now turns indexing off on macOS runners. S11's A2 passed the idle check before measuring but not between plugins ((g)). A failed check here records its CPU samples, the load average and the busiest processes by generic name.

## Options
- **The allowlist:** one list for every hub OS, of the wheels that pass on every target and Node; a list per OS; or, for a wheel that needs code generation, dropping `--disallow-code-generation-from-strings` (ruled out by §4 Packages).
- **cryptography on Windows:** leave it off the list; a narrow shim in hub code (ladder step 1); or patch Pyodide's JavaScript (an MPL edit, ruled out by ladder step 1).
- **A plugin that aborts when stopped** (Windows, Node 26.5.1, right after pyyaml or lxml ran; (c) below): keep both wheels and have the supervisor count an exit after its own stop request as a stop, not a crash; raise the minimum Node for `python` plugins past the bug; or allow those two wheels only on such Nodes.
- **The wasm heap:** `--wasm-max-mem-pages=8192` plus the watchdog, or the watchdog alone if V8 drops the flag.
- **What a cold start counts:** the shim's own boot time only, or everything from the hub's pre-spawn checks (the runtime re-hash and the bundle check) to the answer to the first `tools/list`. The second is what a user waits for, so it is what S11 measures.
- **What the budgets run on:** a plugin without C-extension wheels, as M0.33's boot fixture is, or also plugins that import one when they load. Ladder step 3 ("fewer C-extension wheels") only means something if the second is measured, so S11 measures both: pydantic-core, which the allowlist requires, and numpy, the largest wheel.
- **When a budget run counts:** after the kit's idle check alone; also after a second idle check at the end; or only when the CPU stayed idle between the plugins of the run. Load can only slow a timing, but it can make a resident-memory reading smaller (a trimmed working set, compressed pages).
- **Budget misses:** accept them; ladder step 3, build-id-pinned memory snapshots or fewer C-extension wheels; or, for a miss of more than 2×, Python plugins after the MVP (the no-go path).

## Decision
No-go

Decision rule 4(c), a budget missed by more than 2× on a native, unloaded run: on GitHub's 2-CPU Linux runners the cold start to the first `tools/list` took, at p50, 3.07–3.24 s for py-hello and the pydantic-core plugin and 3.74–3.76 s for the numpy plugin on Linux x64, and 3.11 s for the numpy plugin on Linux arm64, against 1.5 s (2× is 3 s). These rows count: in the pass that measured them every CPU sample between plugins stayed under the kit's 20% (7% and 2.5% at most), so they aren't machine-busy (rule 4(a)). Idle RSS misses there too, by less than 2× (181–259 MiB against 200 MiB; 2 of the 12 Linux rows held). Nothing else failed: on every target and Node there was no escape, no forbidden permission event and no new grant (rule 4(d)), every allowlisted wheel loaded (rule 4(b)), and the wasm cap and the watchdog held (rule 4(e)). So S11 is a no-go on cold-start speed on modest machines, not on the sandbox, and rule 4(c) proposes ladder step 3 for every `python` plugin: choice 1 below.

Plan changes (the first applies with choice 1 (a), the `getuid` shim with choice 3, the others whenever Python ships):
- §15 S11 ladder step 3 for every `python` plugin (choice 1 (a)): M2c starts with build-id-pinned memory snapshots, which the plan's post-MVP Python extras keep "unless S11's budgets need them", and reruns this budget test on `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-15` and the dev box, on both Nodes, before anything else builds on the runtime. Python stays in the MVP if no counted row is then more than 2× over on a native, unloaded run. A plugin whose rows still are decides the rest, by rule 4(c): py-hello's, which no C-extension wheel slows, keep the no-go, and Python plugins move after the MVP; the numpy plugin's take numpy off the allowlist (fewer C-extension wheels); the pydantic-core plugin's go to the owner as in rule (b), who decides whether M2c ships without the SDK's optional pydantic support (V6).
  - Memory snapshots are private API in Pyodide 314.0.7 (`makeMemorySnapshot` is marked `@private`, and `loadPyodide`'s `_makeSnapshot`, `_loadSnapshot` and `_snapshotDeserializer` options `@ignore`), so M2c re-checks them on every Pyodide bump, as it does `_sysExecutable`, and keeps them inside S11's rules. A snapshot comes only from hash-pinned inputs, made one of two ways: at build time from the runtime and allowlisted wheels alone, because running a plugin's import code outside the sandbox would be a hole; or inside the sandboxed plugin, which has no write grant, so the snapshot reaches the hub over the host channel in chunks under its 1 MiB message limit (a builder with a write grant would be a new grant, rule 4(d)). Each snapshot is pinned (the runtime's in `runtime.lock.json`) and verified like the runtime's other files before a spawn, and loading it needs no new grant (the runtime's is read under the existing runtime-dir grant).
- §4 Python runtime, shim boot order step 1: besides the `process.binding` stub, the shim gives Node a `process.getuid` that returns 0 where it has none (Windows), before `loadPyodide`. Pyodide 314.0.7's `getuid` syscall returns `process.getuid()` whenever it runs in Node, unguarded, so on Windows any native code that asks for the uid aborts the runtime (cryptography, below). This is ladder step 1 (a narrow JS shim, no grant, no MPL edit); the fix also goes upstream to Pyodide.
- §4 Packages: the runtime's C-extension allowlist is pydantic-core, orjson, regex, pyyaml, rpds-py, msgspec, lxml and numpy, one list for every hub OS; each loads, imports and runs on Windows x64, Linux x64 and arm64 (natively and in Docker) and macOS arm64, on both Nodes. cryptography joins in M2c if the owner takes the `getuid` shim (choice 3) and S11's allowlist test then passes with it on every target; on Linux and macOS it already passes as it is. How pyyaml and lxml stay on it with Windows Node 26.5.1 is the owner's choice below.
- §4 Health: the `python` watchdog bounds the Python heap too: without `--wasm-max-mem-pages`, a plugin holding 1 GiB in the wasm heap was killed at the first 5 s tick, on every target. If V8 ever drops the flag, Node refuses the argv (an unknown flag is a `bad option`, exit 9, on both Nodes), so the supervisor drops the flag with it and the watchdog alone holds.
- §11 `nightly.yml` and §13 (S11 budgets as regression tests): the budget test runs there with `DRAFTYAK_STRICT_BUDGETS=1`, which makes a counted MISS fail it as well as a FAIL. It needs the kit's bench lock and an idle machine. Until ladder step 3 lands it fails on GitHub's 2-CPU Linux runners, and on the dev box the cold-start margin is thin (p50 1.36–1.43 s for py-hello and the pydantic-core plugin, against 1.5 s), so a shim or SDK change that adds boot time shows there first.

### Owner decision needed: M2c go/no-go
**Recommendation: no-go as measured; let M2c try ladder step 3 first** (choice 1 (a)), and keep Python in the MVP only if ladder step 3 (memory snapshots, then fewer C-extension wheels) leaves no counted budget row more than 2× over, on GitHub's runners and the dev box.

In plain words: Python plugins running on Pyodide stayed inside the same sandbox as JavaScript plugins in every test, on every computer tried: the Windows dev box, GitHub's Linux machines (x64 and ARM, directly and in Docker) and GitHub's Mac, each with both supported Node versions. None of the hostile Python plugins got out, the runtime needed no permission beyond reading its own folder, and that read is gone before plugin code runs. What fails is speed and memory on modest machines: they miss both the start-up and the idle-memory targets. On the fast dev box a simple Python plugin starts and lists its tools in about 1.4 s, inside the 1.5 s target, and one that loads numpy in about 1.7 s. On GitHub's Linux machines, which have 2 processors, the same plugins took 2.5 to 3.8 s: on the x64 one every plugin took more than twice the target, which S11's own rule counts as a failure, and on the ARM one the numpy plugin did. Idle, they also used 181 to 259 MiB against the 200 MiB target (about 145 to 195 MiB on the dev box). GitHub's Mac, a busy 3-processor virtual machine, took 1.5 to 2.1 s and 259 to 303 MiB, but it was too busy for those numbers to count. A 1 MiB call takes 14 to 35 ms everywhere, against 50 ms, and a plugin that grabs too much memory is stopped everywhere, whether the memory sits in Python or in JavaScript. Eight of the nine compiled Python libraries work everywhere tested, including pydantic's core, which S11 requires; the ninth, cryptography, fails only on Windows, because of a one-line Pyodide bug that a one-line shim fixes. Two of the eight, pyyaml and lxml, make a plugin crash as it stops on Windows with the oldest supported Node, a bug in that Node. If you say no-go, Python plugins move after the MVP, and the §4 sandbox fixes ship anyway.

Four choices come with it:
1. **Cold start and idle memory on modest machines.** Counted at p50 on GitHub's 2-CPU Linux runners: py-hello 3.07–3.12 s, the pydantic-core plugin 3.15–3.24 s and the numpy plugin 3.74–3.76 s on x64 (all FAIL), and 2.45–2.47 s, 2.55–2.60 s and 3.11 s on arm64 (MISS, MISS and FAIL), against 1.5 s; idle RSS 181–259 MiB against 200 MiB. On the dev box: 1.36–1.43 s, with numpy 1.67–1.68 s, and 145–196 MiB. Choose one: (a) ladder step 3 first: M2c's first step is build-id-pinned memory snapshots for every `python` plugin, then this budget test again on both Linux runners, `macos-15` and the dev box, and Python stays in the MVP if no counted row is then more than 2× over (if py-hello's still are, Python moves after the MVP; otherwise numpy comes off the allowlist if its plugin's still are, and if the pydantic-core plugin's are, you decide as in rule (b) whether M2c ships without the SDK's optional pydantic support); (b) no-go now: Python plugins move after the MVP; or (c) accept the numbers as they are, so that the 1.5 s and 200 MiB budgets describe fast machines only. The recommendation is (a): snapshots are the plan's own answer to missed budgets (ladder step 3; the post-MVP extras keep them "unless S11's budgets need them"), they need no new grant within the limits of the first plan change, and (a) costs M2c one measured step before anything builds on the runtime. One caveat: Pyodide 314.0.7 offers memory snapshots only as private, undocumented API, which any Pyodide release may change, so M2c re-checks them on every bump. S11 measured no snapshot, so whether snapshots bring a 2-CPU machine within 2× is M2c's first question; misses of up to 2×, such as idle RSS's, keep ladder step 3 in M2c without stopping it. (a) also settles the earlier numpy choice (snapshots, a 2 s budget for numpy plugins, or numpy off the allowlist).
2. **Stopping a plugin right after pyyaml or lxml ran, on Windows with Node 26.5.1.** The plugin then ends with an abort instead of a clean exit, which the hub would count as a crash (five in 10 minutes disable a plugin). It is a bug in that Node, which plain Node shows too and 26.12.0 doesn't; on Linux and macOS every plugin exits cleanly on both Nodes. Choose one: (a) keep both wheels, and the supervisor counts an exit after its own stop request as a stop (M2 stream 2b); (b) raise the minimum Node for `python` plugins past the bug (26.12.0 has it fixed; the first fixed release isn't known); or (c) allow pyyaml and lxml only on Nodes without it. The recommendation is (a): it costs one supervisor rule, and a stop is never a crash whatever the Node.
3. **The `getuid` shim** (a plan change), which lets cryptography join the allowlist in M2c; on Linux and macOS it already passes as it is.
4. **A macOS budget rerun.** macOS's rows that need an unloaded leg didn't count in A2 (rule 4(a)), and a rerun of the budget test alone (`pnpm spikes:run --spikes s11 --os macos-15 --node both --tests 'test/budgets.heavy.test.ts' --yes`) needs your OK: the test took about 15 minutes in A2, so about 160 billed minutes, on a runner that was busy in both of A2's passes. October is past spikes-run's 1,500-minute guard, hence `--yes`: about 1,711 of the month's 2,000 free minutes were billed after the macOS rerun, the org's $0 budget stops all CI at 2,000, and this run's worst case is 301 minutes, so in October it fits only if its job ends within about 28 minutes, less once other runs bill; otherwise it waits until November. The recommendation is not to run it now: the Linux rows already decide, and with choice 1 (a) M2c measures macOS again. Without either, macOS's p50 and idle-RSS rows stay uncounted.

### (c) The C-extension allowlist
Each candidate gets its own bundle (a probe plugin plus the candidate's wheel closure from `runtime.lock.json`, which `node scripts/fetch-runtime.ts --write <names...>` filled from Pyodide's lock) and its own fresh plugin under the production argv. It passes when its wheels load at boot, its native module imports and a small call returns the known answer; the plugin is then stopped, as the hub stops one, by closing its stdin. A probe has 30 s for its discover, import and call together, and the plain-Node control as long, so a candidate that hangs is recorded as `no answer` instead of holding up the others. A failure gets three controls that only say why: the same spawn without `--disallow-code-generation-from-strings`, the production spawn with ladder step 1's shim preloaded, and plain Node with no flags at all. A pass whose plugin doesn't exit cleanly gets the plain-Node control and the same run with a 1 s pause before the stop.

- **When a row counts.** Between plugins the test samples the CPU for 1 s, and a leg (the cold starts, the idle readings or the round trips) is unloaded when every sample stayed under the kit's 20%. A timing row that passed counts from any run that held the lock after the idle check, because load only slows a plugin. A MISS or FAIL counts only from an unloaded leg, and so does an idle RSS reading, PASS included, because memory pressure can shrink a resident reading (Windows trims working sets, and macOS's `ps` leaves out compressed pages). The legs whose rows didn't count are measured once more after a fresh idle check, the first numbers kept as provisional; a row that still doesn't count is `not counted: machine-busy`, and the test fails as machine-busy. If the idle check before the run fails, every row is `not run: machine-busy`.
- **The dev box's run** waited 82 s for the bench lock, which other builds held, and its idle check peaked at 18.9%. In its first pass the samples between plugins reached 20% in 37 of the cold-start leg's 123 (93% at most) and in 1 of the round-trip leg's 3, while all 7 of the idle leg stayed under it (14.6% at most). So the timing PASSes and the idle readings counted, and numpy's p50 (1.71 and 1.73 s in that pass) didn't. ### What M0.34 found
- **Sockets:** the socket row tests the boundary itself, not only the argv: `pyodide_js.useNodeSockFS()` plus asyncio against a live loopback listener, an escape if the listener accepts a connection. Under the production argv it never did (0 accepted on both Nodes, natively and in Docker); the denial is a fatal error in the plugin, so the harness classifies it by the out-of-band accept counter. The default SOCKFS path can only report denials, because Emscripten wraps failures as errno 23.
- **Code generation:** the codegen row (`js.Object.constructor`, which is `Function`) is the positive proof of `--disallow-code-generation-from-strings`: under the flag V8's `EvalError` reaches Python as `JsException`, and M0.34's control without the flag got 42. `run_js` is a second layer (`js.eval` isn't reachable: `ImportError`), not a test of the flag. Both rows, and the socket row, flip on a regression; with them stand boot.heavy's argv pin and the audit's net count.
- The other hostile rows (`os.system`, `subprocess`, off-profile requests, `open()` on the master-key stand-in and home canaries, `js.require('child_process')`, `process.binding('fs')`, writes to the plugin and runtime dirs) were denied too: 11 rows on each Node, 22 attempts per target, 0 escapes. ## Fallback
1. **The `getuid` shim isn't adopted, or a Pyodide bump breaks it:** cryptography stays off the allowlist, and plugins that need it can't ship. Trigger: M2c's allowlist test.
2. **Ladder step 3 leaves a counted row more than 2× over** (choice 1 (a)): if py-hello's is, the no-go stands, Python plugins move after the MVP, and the §4 sandbox fixes ship anyway; otherwise a numpy plugin's row takes numpy off the allowlist, and a pydantic-core plugin's goes to the owner as in rule (b). A miss of up to 2× on a native target keeps ladder step 3 in M2c for that target and plugin, build-id-pinned memory snapshots or fewer C-extension wheels, then a re-measure. Trigger: M2c's first budget runs on `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-15` and the dev box.
3. **JSPI misbehaves on a Node or OS:** ladder step 2, an async-only SDK with no `run_sync`.
4. **An escape or a new grant on any target:** ladder step 4. The owner decides at the gate whether Python moves after the MVP to an OS-sandboxed `isolated` level; Python never ships at `standard` with a known escape or a new grant.
5. **V8 drops `--wasm-max-mem-pages`:** the supervisor stops passing it (Node would refuse the argv) and the watchdog alone bounds the heap, as measured above.
6. **A Node or Pyodide bump:** S11 reruns (`versions.json` and the exact `pyodide` pin are the bump points); a new refusal code, a crash, an unclean exit or a budget change fails the kept tests and holds the bump.
7. **ADR 0003 moves the host channel off fd 3** (after its macOS run it proposes Fallback 1, tagged host frames on stdin and stdout, for the owner at the gate): the shim's host channel, (f)'s reasoning that no print reaches the frames, the 1 MiB round trip's framing and the `ctx.fetch` body limit all rest on fd 3, so S11's suite reruns against the chosen channel before M2c builds on them.
8. **The Windows Node 26.5.1 abort, if choice 2 isn't settled before M2c:** pyyaml and lxml come off the allowlist until the minimum Node is past the bug.
