# ADR 0013: S11 Python runtime on Pyodide (M2c go/no-go)

- **Status:** proposed
- **Date:** 2026-10-18
- **Spike:** S11
- **Plan:** §4 Python runtime, §4 Flags, §4 Health, §9.2 (Python rows), §15 S11, §15 Defaults 10
- **Owner decision:** yes

## Context
§4 runs a `python` plugin as unmodified Pyodide 314.0.7 (CPython 3.14.2, ABI `pyemscripten_2026_0`) inside the plugin's own permissioned Node process, as a `standard` plugin with a JS plugin's powers. Its only extra grant is a second `--allow-fs-read=<runtimeDir>`, which the shim drops before plugin code runs, and its argv adds `--wasm-max-mem-pages=8192`, a 512 MiB wasm heap cap. The shim boots in §4's order (a constants-only `process.binding` stub; `loadPyodide` from local wheels only; abort on any loader error or CDN notice; drop both read grants; serve the entry on stdio MCP), and C-extension wheels ship only if they are on the runtime's allowlist: Pyodide builds that load under `--disallow-code-generation-from-strings`. The hub's watchdog kills a `python` plugin above 1 GiB, and the hub kills a plugin whose call still hasn't answered 5 s after its timeout.

§15 S11 asks for (a)–(h) on Windows x64, macOS arm64 and Linux x64 and arm64, each on 26.5.1 and 26.12.0, and makes M2c the owner's call at the gate. Any escape, any new grant, or any budget missed by more than 2× on a native, unloaded run is a FAIL, with the fallback ladder: (1) narrow JS shims in hub code, never new grants or edits to MPL files, fixes upstream; (2) an async-only SDK if JSPI misbehaves; (3) build-id-pinned snapshots or fewer C-extension wheels if budgets are missed; (4) the owner decides whether Python moves after the MVP to an OS-sandboxed `isolated` level.

`spikes/s11-python-runtime` answers it in three items: M0.33 (`fetch-runtime`, the shim, the boot test: (a) and (d)), M0.34 (the escape, audit, print and timeout suites and the tamper cases: (b), (e), (f), (h)) and M0.35 (the allowlist (c), the budgets (g), `ci.json` and this ADR). Every plugin is spawned as the hub would spawn it (S2's `spawnPlugin` through `spawnPythonPlugin`: the runtime copy re-hashed against `runtime.lock.json`, the bundle checked against its lock, the exact production argv with `--freeze-flags-after-init` from ADR 0003, the scrubbed environment, the fd-3 host channel read through S2's decoder), from an unpermissioned parent. That channel is ADR 0003's to decide; Fallback 7 says what changes here if it moves.

Where each target runs:
- **On the dev box, recorded for this ADR:** Windows 11 x64 with Developer Mode on; Linux x64 in Docker (the digest-pinned `node:26.12.0-bookworm-slim`, `--network none`, a read-only root, uid 65534, on Docker Desktop's WSL2 kernel). Both Nodes in each. Budgets count only on native targets, so Docker gives no budget row.
- **Through `pnpm spikes:run` after this item merges, still to run:** native Linux arm64 plus Docker arm64 (`ubuntu-24.04-arm`; the pinned image index `sha256:2989926…` holds a `linux/arm64/v8` manifest, checked in the local image store, and S2's Docker arm64 suites ran on it in run 39090775204), native Linux x64 (`ubuntu-24.04`) and macOS arm64 (`macos-15`, run A2). `ci.json` runs the whole S11 `test:heavy` there: boot, audit, escape, prints, timeout, tamper, allowlist and budgets.
- **The dev box runs other builds in parallel,** so the budget test holds the kit's bench lock and passes its idle check (CPU under 20% for 5 s) before it measures, then samples the CPU between plugins while it measures ((g) says when a row counts). On `macos-15` the lock works, but S2's idle check failed there twice: in run A1 (39091096373) at 100% CPU, and in 39111041411, where Spotlight's indexing of the install used about 290% CPU on the 3-CPU runner, so `spikes.yml` now turns indexing off on macOS runners. A failed check here records its CPU samples, the load average and the busiest processes by generic name.

## Options
- **The allowlist:** one list for every hub OS, of the wheels that pass on every target and Node; a list per OS; or, for a wheel that needs code generation, dropping `--disallow-code-generation-from-strings` (ruled out by §4 Packages).
- **cryptography on Windows:** leave it off the list; a narrow shim in hub code (ladder step 1); or patch Pyodide's JavaScript (an MPL edit, ruled out by ladder step 1).
- **A plugin that aborts when stopped** (Windows, Node 26.5.1, right after pyyaml or lxml ran; (c) below): keep both wheels and have the supervisor count an exit after its own stop request as a stop, not a crash; raise the minimum Node for `python` plugins past the bug; or allow those two wheels only on such Nodes.
- **The wasm heap:** `--wasm-max-mem-pages=8192` plus the watchdog, or the watchdog alone if V8 drops the flag.
- **What a cold start counts:** the shim's own boot time only, or everything from the hub's pre-spawn checks (the runtime re-hash and the bundle check) to the answer to the first `tools/list`. The second is what a user waits for, so it is what S11 measures.
- **What the budgets run on:** a plugin without C-extension wheels, as M0.33's boot fixture is, or also plugins that import one when they load. Ladder step 3 ("fewer C-extension wheels") only means something if the second is measured, so S11 measures both: pydantic-core, which the allowlist requires, and numpy, the largest wheel.
- **When a budget run counts:** after the kit's idle check alone; also after a second idle check at the end; or only when the CPU stayed idle between the plugins of the run. Load can only slow a timing, but it can make a resident-memory reading smaller (a trimmed working set, compressed pages).
- **Budget misses:** accept, or ladder step 3: build-id-pinned memory snapshots or fewer C-extension wheels.

## Decision
Go with fallback

Ladder step 3 for plugins that import numpy as they load: on Windows their cold start was 1.67–1.68 s at p50 against the 1.5 s budget, a MISS of under 2× on a native run whose numpy leg was unloaded ((g) below), while py-hello and the pydantic-core plugin held every budget. Everything else S11 tested on Windows x64 and Linux x64 holds; the runs on the runners decide the other targets (decision rule).

Plan changes:
- §4 Python runtime, shim boot order step 1: besides the `process.binding` stub, the shim gives Node a `process.getuid` that returns 0 where it has none (Windows), before `loadPyodide`. Pyodide 314.0.7's `getuid` syscall returns `process.getuid()` whenever it runs in Node, unguarded, so on Windows any native code that asks for the uid aborts the runtime (cryptography, below). This is ladder step 1 (a narrow JS shim, no grant, no MPL edit); the fix also goes upstream to Pyodide.
- §4 Packages: the runtime's C-extension allowlist is pydantic-core, orjson, regex, pyyaml, rpds-py, msgspec, lxml and numpy, one list for every hub OS. cryptography joins in M2c once S11's allowlist test passes with the `getuid` shim on every target. How pyyaml and lxml stay on it with Windows Node 26.5.1 is the owner's choice below.
- §4 Health: the `python` watchdog bounds the Python heap too: without `--wasm-max-mem-pages`, a plugin holding 1 GiB in the wasm heap was killed at the first 5 s tick. If V8 ever drops the flag, Node refuses the argv (an unknown flag is a `bad option`, exit 9, on both Nodes), so the supervisor drops the flag with it and the watchdog alone holds.
- §15 S11 ladder step 3, for plugins that import numpy as they load (choice 1): M2c gives them build-id-pinned memory snapshots and re-measures, unless the owner accepts their slower start. numpy stays on the allowlist meanwhile; py-hello and a plugin importing pydantic-core hold the 1.5 s budget as they are.
- §11 `nightly.yml` and §13 (S11 budgets as regression tests): the budget test runs there with `DRAFTYAK_STRICT_BUDGETS=1`, which makes a counted MISS fail it as well as a FAIL. It needs the kit's bench lock and an idle machine, and the cold-start margin on Windows is thin (p50 1.36–1.43 s for py-hello and the pydantic-core plugin, against 1.5 s), so a shim or SDK change that adds boot time shows there first.

### Owner decision needed: M2c go/no-go
**Recommendation: go, with ladder step 3 for plugins that load numpy** (choice 1), provided the pending runs on Linux arm64, native Linux x64 and macOS come back clean.

In plain words: Python plugins running on Pyodide stayed inside the same sandbox as JavaScript plugins in every test on Windows and on Linux. None of the hostile Python plugins got out, the runtime needed no permission beyond reading its own folder, and that read is gone before plugin code runs. On Windows a simple Python plugin starts and lists its tools in about 1.4 s, and so does one that loads pydantic, inside the 1.5 s target; one that loads numpy takes about 1.7 s, about 0.2 s over it. Idle, they use about 145, 160 and 195 MiB, under the 200 MiB target, and a 1 MiB call takes about 15 ms. A plugin that grabs too much memory is stopped, whether the memory sits in Python or in JavaScript. Eight of the nine compiled Python libraries work everywhere tested, including pydantic's core, which S11 requires; the ninth, cryptography, fails only on Windows, because of a one-line Pyodide bug that a one-line shim fixes. Two of the eight, pyyaml and lxml, make a plugin crash as it stops on Windows with the oldest supported Node, a bug in that Node. What is still open is the same set of tests on macOS and on Linux arm64, plus the budgets on native Linux; the decision rule below says what each outcome changes. If you say no-go, Python plugins move after the MVP to a future OS-sandboxed `isolated` level (ladder step 4), and the §4 sandbox fixes ship anyway.

Three choices come with it:
1. **numpy plugins' cold start.** A plugin that imports numpy as it loads started in 1.67–1.68 s at p50 on Windows (p95 1.73–1.76 s, against 3 s), about 0.2 s over the 1.5 s budget, and sat at 192–196 MiB idle, just under 200 MiB. Choose one: (a) ladder step 3 in M2c, build-id-pinned memory snapshots, then re-measure; (b) accept their slower start, with a 2 s p50 budget for plugins that load numpy and 1.5 s for the rest; or (c) take numpy off the allowlist (fewer C-extension wheels). The recommendation is (a), with numpy on the allowlist meanwhile: snapshots are the plan's answer to exactly this, and the miss is small.
2. **Stopping a plugin right after pyyaml or lxml ran, on Windows with Node 26.5.1.** The plugin then ends with an abort instead of a clean exit, which the hub would count as a crash (five in 10 minutes disable a plugin). It is a bug in that Node, which plain Node shows too and 26.12.0 doesn't. Choose one: (a) keep both wheels, and the supervisor counts an exit after its own stop request as a stop (M2 stream 2b); (b) raise the minimum Node for `python` plugins past the bug (26.12.0 has it fixed; the first fixed release isn't known); or (c) allow pyyaml and lxml only on Nodes without it. The recommendation is (a): it costs one supervisor rule, and a stop is never a crash whatever the Node.
3. **The `getuid` shim** (the first plan change), which lets cryptography join the allowlist in M2c.

### (c) The C-extension allowlist
Each candidate gets its own bundle (a probe plugin plus the candidate's wheel closure from `runtime.lock.json`, which `node scripts/fetch-runtime.ts --write <names...>` filled from Pyodide's lock) and its own fresh plugin under the production argv. It passes when its wheels load at boot, its native module imports and a small call returns the known answer; the plugin is then stopped, as the hub stops one, by closing its stdin. A probe has 30 s for its discover, import and call together, and the plain-Node control as long, so a candidate that hangs is recorded as `no answer` instead of holding up the others. A failure gets three controls that only say why: the same spawn without `--disallow-code-generation-from-strings`, the production spawn with ladder step 1's shim preloaded, and plain Node with no flags at all. A pass whose plugin doesn't exit cleanly gets the plain-Node control and the same run with a 1 s pause before the stop.

cryptography on Windows, on both Nodes: the import of its Rust extension ends in `panic in a function that cannot unwind`, then Pyodide's fatal error (`RuntimeError: unreachable`). It fails the same way without the codegen flag and in plain Node with no flags, so neither the flag nor the sandbox causes it. The cause is a JavaScript `TypeError` inside the wasm import `__syscall_getuid32_js` (`process.getuid is not a function`): OpenSSL asks for the uid at start-up, Pyodide calls `process.getuid()` whenever it runs in Node, and Windows Node has no `process.getuid`. The exception unwinds into Rust code that can't unwind, which aborts. With `process.getuid` defined as `() => 0` (Pyodide's own answer outside Node) and preloaded under the full production argv, cryptography imports and runs on both Nodes; the test checks this while the plan change stands. In Linux it passes as it is.

pyyaml and lxml on Windows with Node 26.5.1: both import and run, but when the probe stops the plugin right after the call answers, it ends with exit code 3221226505 (0xC0000409, an abort) and `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 94` on stderr: libuv's `uv_async_send` called on a handle that is already closing, so something still posts to the event loop while Node shuts down. Plain Node 26.5.1 with no flags ends the same way after the same calls, the same run with a 1 s pause before the stop exits cleanly, and 26.12.0, Docker Linux and every other candidate exit cleanly. The allowlist test records this one known abort (Windows, Node 26.5.1, that assertion) without failing and fails on any other unclean exit; the budget test applies the same rule to every plugin it starts. Choice 2 above settles what M2c does about it, and the bug goes upstream to Node.

The allowlist holds one list for every hub OS, because a bundle is the same everywhere and a wheel that aborts on a Windows hub can't ship. No candidate needed code generation from strings: every failure was the same with and without the flag.

- **When a row counts.** Between plugins the test samples the CPU for 1 s, and a leg (the cold starts, the idle readings or the round trips) is unloaded when every sample stayed under the kit's 20%. A timing row that passed counts from any run that held the lock after the idle check, because load only slows a plugin. A MISS or FAIL counts only from an unloaded leg, and so does an idle RSS reading, PASS included, because memory pressure can shrink a resident reading (Windows trims working sets, and macOS's `ps` leaves out compressed pages). The legs whose rows didn't count are measured once more after a fresh idle check, the first numbers kept as provisional; a row that still doesn't count is `not counted: machine-busy`, and the test fails as machine-busy. If the idle check before the run fails, every row is `not run: machine-busy`.
- **The committed run** waited 82 s for the bench lock, which other builds held. In its first pass the samples between plugins reached 20% in 37 of the cold-start leg's 123 (93% at most) and in 1 of the round-trip leg's 3, while all 7 of the idle leg stayed under it (14.6% at most). So the timing PASSes and the idle readings counted, and numpy's p50 (1.71 and 1.73 s in that pass) didn't. The second pass, after an idle check that peaked at 11.1%, measured numpy's 40 cold starts again with every sample under 20% (17.4% at most), so its p50 of 1.67 and 1.68 s counts, as a MISS, and the test passed: a counted MISS fails it only with `DRAFTYAK_STRICT_BUDGETS=1`. Four earlier runs of this code never got an unloaded numpy leg and failed as machine-busy; their numbers aren't committed.
- **Cold start** runs from before the hub's pre-spawn checks (the runtime re-hash and the bundle check: medians of 37–56 ms, 20–151 ms in all) to the answer to the first `tools/list`. The shim's own boot is 1.18–1.65 s of it for py-hello, 1.22–2.52 s with pydantic-core and 1.49–1.62 s with numpy. Percentiles are nearest-rank over the 20 runs. The first spawn after the runtime copy is measured apart and left out of the series: py-hello's took 2.50 s (checks 301 ms, the shim's boot 2.00 s), while the first spawns of the other two plugins, on the same copy, took 1.50 s and 1.79 s. A hub pays that once after each runtime install or update, when the freshly written files are first read. M0.33's boot cases saw 2.10–2.35 s on Windows outside the lock.
- **Idle RSS** is the working set on Windows (VmRSS in Linux, `ps` rss on macOS), the median of three readings. Private bytes, which the hub's Windows watchdog reads (ADR 0003), was 164–167 MiB for py-hello, 179–182 MiB with pydantic-core and 215–219 MiB with numpy, with 69% of the dev box's memory in use.
- **The round trip** is `tools/call` with a 1 MiB string that comes back as the result, over stdio MCP: three warm-ups (the first 24.2–26.5 ms, then 14.1–16.7 ms), then 20 runs of 11.2–27.1 ms. It isn't measured over the fd-3 host channel: S2's decoder ends the channel above 1 MiB per message, and a 1 MiB fetch body as base64 is about 1.33 MiB, so a `ctx.fetch` body of more than about 760 KiB can't cross it yet. M2 stream 2b sizes that limit for fetch bodies (M0.12's handoff), on whichever channel ADR 0003 settles.
- **Wasm cap:** both Nodes' V8 lists `--wasm-max-mem-pages` (`node --v8-options`; the default is 4294967295 pages). Under the production argv a 1 GiB Python allocation raised `MemoryError`; without the flag the same allocation succeeded.
- **Watchdog** (S2's 5 s tick, private bytes on Windows): a plugin holding 1 GiB of JS typed arrays under the production argv, which no flag bounds, was SIGKILLed at the first tick, 5.0 s in, at 1,271–1,275 MiB; one holding 1 GiB in the Python heap without the wasm flag was SIGKILLed the same way at 1,287 MiB. The blocks hold random bytes, so no OS can compress them under the limit.
- **Every plugin the test started** exited cleanly when stopped: every first spawn, cold start, idle run and round trip ended with exit code 0.

### What M0.34 found
- **Sockets:** the socket row tests the boundary itself, not only the argv: `pyodide_js.useNodeSockFS()` plus asyncio against a live loopback listener, an escape if the listener accepts a connection. Under the production argv it never did (0 accepted on both Nodes, natively and in Docker); the denial is a fatal error in the plugin, so the harness classifies it by the out-of-band accept counter. The default SOCKFS path can only report denials, because Emscripten wraps failures as errno 23.
- **Code generation:** the codegen row (`js.Object.constructor`, which is `Function`) is the positive proof of `--disallow-code-generation-from-strings`: under the flag V8's `EvalError` reaches Python as `JsException`, and M0.34's control without the flag got 42. `run_js` is a second layer (`js.eval` isn't reachable: `ImportError`), not a test of the flag. Both rows, and the socket row, flip on a regression; with them stand boot.heavy's argv pin and the audit's net count.
- The other hostile rows (`os.system`, `subprocess`, off-profile requests, `open()` on the master-key stand-in and home canaries, `js.require('child_process')`, `process.binding('fs')`, writes to the plugin and runtime dirs) were denied too: 11 rows on each Node, 22 attempts per target, 0 escapes. Extra, modified and hard-linked runtime files refuse the spawn on both Nodes, and symlinked and junction ones (on 26.5.1 on Windows, on both Nodes in Docker) refuse it too, each with its finding (a junction reports as a symlink).

### Decision rule for the pending runs
1. After this item merges: `pnpm spikes:run --spikes s11 --os 'ubuntu-24.04-arm,ubuntu-24.04' --node both` (2 jobs of at most 45 minutes, at most 91 billed minutes with the plan job). Once both pass, run A2: `pnpm spikes:run --spikes s11 --os macos-15 --node both` (at most 30 minutes, 301 billed minutes). On the dev box the budget file alone takes 8–12 minutes and the whole suite about 14, so A2 has macOS's 30-minute maximum rather than the 25 first budgeted, and the Linux jobs 45; billing follows the minutes used, not the cap.
2. The `ubuntu-24.04` job also reruns the Linux x64 Docker legs and writes its `*-docker-linux-x64.json` files over the dev box's. Check that they hold the same findings, then restore the committed ones (`git checkout -- 'spikes/s11-python-runtime/evidence/*-docker-linux-x64.json'`), which this ADR cites.
3. **The decision stands** when every job is green, the artifacts hold `boot`, `escape`, `allowlist` and `budgets` for `linux-x64`, `linux-arm64` and `darwin-arm64`, and `boot`, `escape` and `allowlist` for `docker-linux-arm64`, and every counted budget row is PASS, numpy's cold start aside (a MISS there only adds that target to choice 1). A MISS doesn't turn a job red (the test reports it, and the run shows it as a warning), so read the rows. Then fill in the table, the allowlist's columns and the budget rows, and commit the evidence.
4. Otherwise apply the first rule that fits:
   - (a) **Harness, not runtime:** a timeout; `machine-busy` from the bench lock or from the CPU between plugins (the budget file then records what was busy; S2's run A1 failed its idle check on `macos-15` at 100% CPU); a budget row `not measured`; a setup or fetch error; or the lock path failing on macOS (the budget test then fails at once, naming the lock file). Fix the harness if needed and rerun that job once (macOS with the owner's OK, from the budget's reserve).
   - (b) **A candidate fails on a target:** it comes off the allowlist, with its reason and controls in the ADR. If it is pydantic-core, (c) is a FAIL: try ladder step 1 (a narrow shim, as for cryptography); if that doesn't fix it, the owner decides at the gate whether M2c ships without the SDK's optional pydantic support (V6). A pass whose plugin doesn't exit cleanly, other than the known Windows 26.5.1 abort, goes to the owner like choice 2.
   - (c) **A budget missed by more than 2× on a native, unloaded run:** the decision becomes `No-go`, with ladder step 3 proposed (for the pydantic-core or numpy plugin: snapshots, or that wheel off the allowlist; pydantic-core goes to the owner as in (b)). Missed by up to 2×: `Go with fallback`, ladder step 3 in M2c for that target and plugin.
   - (d) **An escape or a new grant:** the decision becomes `No-go`, with ladder step 4 for the owner.
   - (e) **The wasm cap or the watchdog fails on a target:** that target's memory bound is the owner's decision at the gate, as in ADR 0003's Fallback 3.

## Fallback
1. **The `getuid` shim isn't adopted, or a Pyodide bump breaks it:** cryptography stays off the allowlist, and plugins that need it can't ship. Trigger: M2c's allowlist test.
2. **A budget missed by up to 2× on a native target:** ladder step 3 in M2c, build-id-pinned memory snapshots or fewer C-extension wheels per plugin, then re-measure. More than 2× on a native, unloaded run is a FAIL (decision rule).
3. **JSPI misbehaves on a Node or OS:** ladder step 2, an async-only SDK with no `run_sync`.
4. **An escape or a new grant on any target:** ladder step 4. The owner decides at the gate whether Python moves after the MVP to an OS-sandboxed `isolated` level; Python never ships at `standard` with a known escape or a new grant.
5. **V8 drops `--wasm-max-mem-pages`:** the supervisor stops passing it (Node would refuse the argv) and the watchdog alone bounds the heap, as measured above.
6. **A Node or Pyodide bump:** S11 reruns (`versions.json` and the exact `pyodide` pin are the bump points); a new refusal code, a crash, an unclean exit or a budget change fails the kept tests and holds the bump.
7. **ADR 0003 moves the host channel off fd 3** (after its macOS run it proposes Fallback 1, tagged host frames on stdin and stdout, for the owner at the gate): the shim's host channel, (f)'s reasoning that no print reaches the frames, the 1 MiB round trip's framing and the `ctx.fetch` body limit all rest on fd 3, so S11's suite reruns against the chosen channel before M2c builds on them.
8. **The Windows Node 26.5.1 abort, if choice 2 isn't settled before M2c:** pyyaml and lxml come off the allowlist until the minimum Node is past the bug.
