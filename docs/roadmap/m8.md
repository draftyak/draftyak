# M8: local MCP

M8 exposes the native tool pipeline through a local MCP service and stdio
bridge. It follows the M3 vertical slice; paired-device session acceptance also
requires M4. Contracts belong to M1, native security services to M2, and passive
views to M8b. Product source imports no spike implementation. Package, archive
and synthetic-client checks do not complete installed-client acceptance.

Each item below names its acceptance target. Source paths describe planned or
separately reviewed components, not implementation already on this branch. An
item creates any listed test path or script that does not exist yet before its
acceptance can pass. M2.11 owns the CLI skeleton, file-per-command dispatcher,
shared payload-contract definition and bounded regular-file reader. M8 consumes
those interfaces after they merge; it does not create a second implementation.

## M8.1 Stdio bridge and translator

**Goal:** Serve supported local clients through `draftyak mcp --client <name>`
without giving the bridge native approval or session authority.

**Inputs:** M1.19 contracts, the actual local MCP service, owner-minted agent
credentials, ADR 0004 and ADR 0005, and M2.11's CLI and payload/launch contract.

**Outputs:** Bounded stdio/HTTP relay, protected token loading, era negotiation
and the ADR 0005 translator for eligible local 2025-era clients. The translator
preserves params, principal and hub-issued request state, limits rounds, passes
only permitted declared capabilities, and keeps readable fallback/expiry errors.
It uses its own loopback HTTP agent rather than environment proxies. Diagnostics
use stderr; stdout carries only MCP. Hub approval and current authorization are
rechecked independently of any client dialog.

**Owns:** `apps/cli/src/mcp/**`, `apps/cli/test/mcp/**` and the local bridge guide.
M2.11 owns the shared CLI launch-contract definition; this item owns bridge
consumer tests coordinated with M8.4a and M10. Absorb ADR 0005's
`translate.test.ts` and `stdio.test.ts`,
including state isolation, one-round/delay behavior, malformed-param parity,
header/name bounds, startup refusals, proxy isolation and EOF shutdown.

**Acceptance:** `pnpm --filter @draftyak/cli test -- test/mcp` and
`pnpm --filter @draftyak/cli typecheck`; actual stdio against the native loopback
service in both supported eras, no token/diagnostic on stdout, no proxy disclosure
and no retry with caller-invented state. An eligible real local 2025-era client
completes the account form; otherwise apply ADR 0005's documented fallback.

**Depends on:** M1.19, M2.11, M2 authorization/token services, M3, the approved ADR
handoffs and implementation of the shared launch contract below. The translator
does not authorize URL-mode session prompts or a replacement private
authentication flow.

## M8.2 Tools, agent tokens and native authorization

**Goal:** Expose the planned seventeen tools and scoped agent access to the local
API while preserving the native owner/account/session/routing intersection.

**Inputs:** Merged MCP/tool schemas, real M2 identity/authorization/audit services,
M3 operations and paired-device session approval.

**Outputs:** Dual-era local serving, native tool dispatch, agent-token lifecycle
and local-API scope checks, current grant/session checks, shared budgets and
ID-only audit. Host/Origin, the 1 MiB body cap, header/body matching and protocol
version checks precede principal authorization. HTTP and stdio return JSON-only
MCP responses; neither declares a subscription or SSE transport. Draft or send
requests never consume a PIN, grant approval or skip the native send gate.
Expiry, revocation, account changes and epoch changes invalidate affected use.

The seventeen tools and truthful annotations follow M1.19. Organize access is
unticked by default, denies system labels and respects account mode. Scheduled
`sendAt`/`timeZone` values are proposals bound only by the owner's PIN;
`send_request_status` includes the schedule and truthful state, cancellation
permits only the proposing principal's requests, and a live outbox item causes
`DRAFT_LOCKED`. Revocation offers the owner cancellation of that agent's
scheduled sends without silently cancelling or approving them.

**Owns:** `apps/hub/src/mcp/{server,middleware}.ts`,
`apps/hub/src/mcp/{tools,auth,tokens}/**` and corresponding
`apps/hub/test/mcp/**`; local-API agent-token integration is coordinated with its
M3 route owner and M2's authoritative authorization service.

**Acceptance:** `pnpm --filter @draftyak/hub test -- test/mcp/tools.test.ts
test/mcp/agent-tokens.test.ts` and `pnpm --filter @draftyak/hub typecheck`.
Test every tool/scope intersection and local-API agent route, expired/revoked and
foreign tokens, session/account/epoch changes, budget sharing and browser/agent
approval refusal through actual native adapters. Assert middleware order,
sentinel-decoded `Mcp-Name`/`Mcp-Method` matching and both eras' errors. Apply the
same allowlist/routing/per-tool-class session checks to tools, resources and
local-API agent tokens, including SMS accounts and sensitive-text exclusions.
Share the 120 requests/minute and 10 send proposals/hour counters across MCP
methods and retries, with 2,000 local message bodies/hour; remote use remains
M9-owned. Pages count both representations toward 20,000 estimated tokens and
40,000 characters. Test idempotency, revision conflicts, all scheduling/own-cancel
and lock refusals above; no principal reaches `channel_send` or a device ticket.

**Depends on:** M1.19, M2 identity/authorization/token administration, M3 and M4
for real device-approved session acceptance. SMS-native rows also require M6b
and the owner's S12 decision; they do not pass through synthetic observations.

## M8.3 Resources, prompts, completion and elicitation

**Goal:** Supply first-party read-only conveniences over the same native tool
pipeline, without expanding authority or adding executable model tools.

**Inputs:** M1.19, M8.2, immutable request state and ADR 0004's surface/MRTR
handoffs; M8b supplies separately verified passive view assets.

**Outputs:** The static agent guide and four scoped resource templates; the
`triage_inbox`, `summarize_thread`, `draft_reply` and `prepare_send_request`
prompts; alias/fixed-value-only completion; and capability-gated account-form
elicitation. Resource reads use the native handler, session, budget, page-cap and
audit pipeline. Prompts contain only authored instructions and validated
arguments, never mailbox data. Completion returns at most twenty aliases or
fixed values and has its own sixty-requests/minute bucket.

The account form retains the HMAC-bound `requestState`, ten-minute TTL,
single-use `pendingId` and five-open-state cap. A resumed request rechecks current
authorization. Tampered, expired, replayed, params-swapped or cross-principal
state refuses; auto-acceptance grants nothing. Pending session requests retain
the readable fallback; no URL-mode access-approval prompt is ported. Plugins
contribute no resources, prompts, completion or UI, and these surfaces run no
context lookup or direct send.

**Owns:** `apps/hub/src/mcp/{resources,prompts,completion,elicitation}/**` and
`docs/guides/agents.md` and surface, prompt-hygiene, completion-leakage and MRTR
suites under `apps/hub/test/mcp/**`. These suites absorb ADR 0004's surfaces and MRTR kept
tests; the view integrity/gating adapter coordinates with M8b.

**Acceptance:** `pnpm --filter @draftyak/hub test -- test/mcp/surfaces.test.ts
test/mcp/mrtr.test.ts` and `pnpm --filter @draftyak/hub typecheck`.
Compare direct and bridged results, scope failures, both eras' not-found codes,
raw-URI/params refusals, untrusted-content framing and absence of private
completion data. Pin guide/template/prompt inventories, no mailbox data in
prompts, exact URI and not-found behavior, completion bounds/audit, one-round
state consumption and all readable fallback cases. No passive view may request
a tool or elevate a token; returning a resource or prompt grants no new scope.

**Depends on:** M8.2, merged contracts and approved ADR 0004 decisions. View
acceptance additionally requires M8b's real browser and integrity gates.

## M8.4a Protected MCPB packer and release handoff

**Goal:** Package explicit compiled bridge bytes reproducibly without treating
archive generation as authentication, installation or release approval.

**Inputs:** Reviewed artifact sizes/hashes, fixed repository licensing inputs,
the authoritative Node minimum and an agreed M8.1/M10 payload contract.

**Outputs:** Deterministic MCPB archive, manifest/bootstrap, bounded source
snapshots, no-overwrite atomic local publication and readiness metadata.
Self-containment, actual runtime execution and client acceptance remain separate
checks. The item maintains its lasting contract in `tools/mcpb/README.md`.

**Owns:** `tools/mcpb/**`, its importer in `pnpm-lock.yaml` and coordinated
MCPB-specific checks/tests in `tools/release-guard/**`. The release check inventories the real
compiled payload, refuses dependencies outside it and credential-shaped bytes,
and validates license/notice and runtime/launch compatibility. The release
workflow attaches the checked file to an immutable GitHub Release only after
explicit owner approval; this packer neither uploads nor approves it.

**Acceptance:** `pnpm --filter @draftyak/mcpb typecheck`,
`pnpm --filter @draftyak/mcpb test`, `pnpm verify` and `pnpm guard`.
Independent archive/schema readers check deterministic local/central records,
bounded source snapshots, links/path refusal, partial-write interruption,
per-operation close refusal and no overwrite. Release acceptance also runs
`pnpm --filter @draftyak/release-guard test -- test/mcpb.test.ts` against a real
bridge payload and demonstrates that external dependencies and synthetic
credential canaries refuse before the owner authorizes publication.

**Depends on:** M2.11's CLI, single payload contract and shared bounded reader;
M8.1 and M10 adoption of the shared entry/argv contract for
real-product packaging, M10's release inspection/workflow integration, the
shared bounded-reader handoff below and owner resolution of the host-provided
Node question.

## M8.4b Agent setup and client configuration

**Goal:** Implement `draftyak mcp add` without reading vendor credentials,
running vendor CLIs or silently changing unrelated configuration.

**Inputs:** Native signed admin/PIN verification and agent-token minting,
reviewed client names and M8.1/M8.4a launch configuration.

**Outputs:** An owner-authorized token admin operation and printed MCPB,
`claude_desktop_config.json`, `claude mcp add` and `~/.codex/config.toml`
snippets, with `default_tools_approval_mode="writes"` recommended for the latter.
Every setup path shows the warning that a client with shell access
as the same OS user can read that user's files and bypass MCP restrictions;
stronger isolation requires a separate OS user.

With `--write`, display the exact proposed diff, obtain approval, make a backup
and merge only into `claude_desktop_config.json` or `~/.codex/config.toml`.
Never read or write vendor credential files or other per-user client files, and
never invoke a vendor CLI. Without `--write`, configuration remains untouched.

**Owns:** `apps/cli/src/mcp-config/**`, `apps/cli/test/mcp-config/**`, setup
guides and entries in `tools/vendor-guard/allow.json` for exactly those permitted
configuration paths; no broader credential-directory exception is authorized.

**Acceptance:** `pnpm --filter @draftyak/cli test -- test/mcp-config`,
`pnpm --filter @draftyak/cli typecheck` and `pnpm guard`. Assert every required
snippet/warning, actual native admin refusal without PIN/current rights, exact
diff/backup/merge behavior, preserved unrelated keys, no writes by default and
zero reads/writes or process calls at forbidden paths/vendor commands.

**Depends on:** M2.11's CLI and shared reader, M8.1, M8.2's native token
administration and the accepted packer launch contract. A printed snippet or
local config write grants no authority.

## M8.5a Bounded conformance artifact validation

**Goal:** Evaluate complete local referee outputs in both eras without admitting
unexplained failures, protected-check skips or stale baseline entries. This is
artifact validation; it does not authenticate a tested product or replace M8.5.

**Inputs:** ADR 0004's exact referee pin and baseline policy, M0.14's kept-test
handoff and artifact/count/size guards, and the shared bounded regular-file
reader. The copied S03 baseline still awaits the owner's ADR 0004/M0-gate review.

**Outputs:** A package-local exact referee dependency, a local-output validator,
content-free genuine referee ID/status fixtures, refusal tests, and the receipt
contract in [the artifact appendix](m8-conformance.md). The CLI emits only fixed
findings/counts and uses exit 0 for pass, 1 for evaluated failure, 2 for refusal.

**Owns:** `tools/mcp-conformance/**`, `security/mcp-conformance-baseline.json`,
the conformance importer in `pnpm-lock.yaml`, and `docs/roadmap/m8-conformance.md`.
Until protected ownership rules are installed on the target branches, every
baseline change requires explicit owner review. The file on `m11` does not prove
that a target branch has those protections.
The copied baseline remains unchanged until that review; reviewed changes also
update the S03 copy while its byte-equality test remains, before spike retirement.

**Acceptance:** `pnpm --filter @draftyak/mcp-conformance typecheck`,
`pnpm --filter @draftyak/mcp-conformance test`, `pnpm verify` and `pnpm guard`.
Run the validator over genuine pinned-referee outputs for both eras. Unit cases
exercise the real `$schema`/`$defs` IDs, directory/byte bounds, matching output
destinations, valid linked/duplicate artifact controls, concurrent independent
loads, and CLI exits 0/1/2 including a linked entry. Keep all twelve baseline
entries and their reasons pending the owner's decision; progress in both eras
and legacy SEP-1330 enums need explicit attention.

**Depends on:** This backlog landing before the consumer, M2.11's shared reader,
the locked referee dependency and the owner's baseline review before merge.
M8.5 still owns the product test profile, its release-guard exclusion, runner
lifecycle and workflow, and HTTP/stdio hub/bridge/template coverage. Receipts are
unauthenticated: `conformance.yml` must execute the locally resolved pinned
referee `dist/index.js` and this validator in the same job from reviewed code.
Fixture-profile conformance does not complete those product or client gates.

## M8.6 Installed-client and owner gate

**Goal:** Demonstrate the complete local MCP product with supported installed
clients and real paired-device approval.

**Inputs:** M3/M4, all M8 items, actual built bridge/MCPB payloads, the owner
client matrix and applicable M0 decisions.

**Outputs:** Client installation/deployment guide and the owner gate report.
Connect each supported client, inspect resources/prompts, draft and request a
send, including a scheduled request. Only actual paired-desktop PIN approval
may authorize a send; client dialogs and synthetic tokens never substitute.

**Owns:** `docs/roadmap/m8-gate.md`, client acceptance drivers/guides, the
coordinated `verify:m8` entry in `package.json`,
`tools/verify/{profiles,steps}/m8.ts` and their acceptance tests.

**Acceptance:** The item registers and runs `pnpm verify:m8`, including M8.1–.5
commands, real installed-client observations, revocation/expiry and no-approval
refusals, one byte-equal approved request, scheduled/missed/cancel outcomes and
owner review/signoff. A generated archive or inventory is insufficient.
The owner matrix includes Claude Desktop through MCPB, Claude Code and Codex
drafting/requesting a send, one scheduled request, Claude Code's `draft_reply`,
conversation-resource session and `triage_inbox` account form, and VS Code's
prompt listing and alias-only completion. Native desktop PIN approval is required
for the accepted send, including its proposed schedule.

**Depends on:** All M8 items, M3/M4 acceptance, M8b for view-enabled hosts and
explicit owner approval of release assets and product behavior.

## Changed since the plan

The owner retained plan §6's public `draftyak mcp --client <name>` form.
The MCPB profile uses the canonical `claude-desktop` client name, rather
than substituting a hub URL for client selection. Client selection grants no
authority and does not choose or supply a Node runtime.

M2.11 defines the single payload contract consumed by M8.1, M8.4a and M10:
the compiled entry is `.mjs`; importing the module does not start the CLI. It exports
`async main(argv: readonly string[]): Promise<number>`. A protected launcher
passes `process.argv.slice(2)` once, awaits shutdown, and accepts only an integer
exit status from 0 through 255. Stdout carries MCP only and diagnostics use
stderr. M2.11 owns the exported definition at `apps/cli/src/payload-contract.ts`;
the consumer tests import that definition instead of restating a second one.

This backlog establishes requirements, not a merged bridge or packer.
M8.1 owns public option adoption and native acceptance; M10 owns validating the
same real compiled entry. Packer tests with synthetic payloads do not complete
those gates. ADR 0004's session-pending URL removal/legacy transport corrections
and ADR 0005's local translator remain subject to their recorded owner gates.
No other plan departure is approved here.

## Shared handoffs and owner questions

- M2.11 owns `packages/bounded-files/**`, the CLI skeleton and shared payload
  definition. MCPB, conformance and M10 inventory consume the same bounded
  regular-file reader with per-operation `finally` cleanup and no global close
  latch, preserving each consumer's own exclusions and empty-file policy.
  Doctor's metadata checks need no artifact byte reader; future M2c
  runtime-integrity checks are a separate owner-gated adoption.
- Take the Node floor from `tools/fetch-node/versions.json`, including M10's
  launcher. Who provisions/verifies the required runtime when the installing
  MCPB host resolves `node` from its own PATH? The archive bundles no runtime.
- Complete M8.1/M10 adoption of the entry and argv contract above before
  real-product packaging. Test the actual public `--client` invocation and
  shared compiled entry; an unpublished CLI composition is not a merged
  prerequisite or installed-client acceptance.
- Land the backlog before consumers that depend on these item IDs. MCPB and
  conformance importers must be regenerated by normal installation when their
  independent changes merge, preserving the existing dependency resolutions.
