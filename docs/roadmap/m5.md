# M5 backlog: Gmail

M5 delivers the Gmail channel, account connection and lifecycle, native wizard,
and reusable offline Gmail/OAuth fixtures from the approved plan's sections 3–5,
7–8 and 12–14. It depends on M3; device UI follows M4. The items below define
ownership and acceptance, not implementation or completion claims. Run results
belong in PR bodies; the roadmap contains no worktree verification diaries.

**M5 is done when:** full contract/emulator suites pass; a full-mode connection
without `gmail.modify` fails; history 404 causes a bounded resync; read-only has
no send path; deletion canaries including FTS and contacts are clean; threading
headers match goldens; disclosure precedes consent; a scheduled reply sends once
inside its approved window with claim-time Date; a long “Mail sending” 429 past
the deadline becomes NEEDS_REAPPROVAL; and Gmail-UI scheduled mail never counts
as sent. Every applicable M5 item and M0 Gmail behavior decision remains
required. M11's installed real-account and compliance gates remain required
before launch; a successful synthetic fixture proves neither vendor behavior
nor a connected native account.

## Desktop pilot scope

The pilot retains full Gmail on Windows, Apple-silicon macOS and Ubuntu 24.04,
using the desktop app and its bundled hub. Scheduled send requires the app to be
awake and running and binds the exact approved content and time window. A missed
window requires fresh approval. Encryption, credential protection, native PIN
approval, recovery, deletion canaries and duplicate-send prevention stay required.

Headless distribution and SSH-tunnel connection, browser login, mobile/SMS,
Python, context tools and MCP are postponed. Their saved work and landed shared
contracts remain preserved; they are not pilot implementation or gate inputs.
The hub-host OAuth callback and a second computer's native desktop code relay
remain required. Postponing browser login does not waive OAuth state/PKCE,
Host/Origin/CSRF, pairing, WebKit or native approval protections.

Selected installers are Windows NSIS, Apple-silicon DMG and Ubuntu 24.04 deb.
Real per-OS owner checks remain required before the release candidate. Gate
records may explicitly mark those checks pending until then; a pending cell,
synthetic fixture or documentation update supplies no passing native result.

  consumes the real M2 store/authorization/PIN/executor/broker and M3 content,
  sync/draft/client APIs. No fixture or plugin result creates native authority.

  refusal codes. Request missing shared contracts through M1. M2 owns the common
  M2.26 credential service and per-credential refresh mutex, DNS/egress policy,
  tickets, executor, scheduling and storage/lifecycle services. M3 owns common
  content, MIME processing, hub-derived direction and shared SPA/client hooks.
- Gmail-specific request plans and response decoders can live in the plugin;
  credentials and trusted send rendering/classification stay in the hub. Use
  existing common MIME code; do not fork its parser/renderer or establish a
  second fetch, credential, signing or approval path. Inbound changes reach the
  hub only through the plugin's `channel_sync`/`channel_listen` contracts as
  `NormalizedChange[]`; the hub never supplies a parallel Gmail response decoder.
- Below, hub paths are relative to `apps/hub/src/`; plugin paths to
  `plugins/channel-gmail/`. Each item owns matching tests. Existing shared hub
  account/API/policy, app routing/commands and registry hooks receive only small
  changes agreed with their owner. Namespace migrations are owned here; the
  store/migrator implementation is not. Shared manifests/lockfiles receive only
  the item's own registration/dependencies; keep both sides of Cargo.lock
  conflicts, never a workspace-wide update.
- New dependencies use the settled exact-pin, age and licence policy. Ordinary
  product packages use TypeScript and Vitest tiers. Before submission, rebase onto
  the current base, run frozen installation, touched-package checks, guard and
  the item's offline acceptance. Ready PRs require passing `required` and

  boundary attacks and mutation proofs; unrelated full/Windows suites use CI

  Each new head needs review before automatic integration; the owner signs off

- M0 owns S8/live Gmail sessions and ADR 0010; absorb its decisions without
  running vendor calls here. M11 owns launch disclosures/legal review and the
  final installed real-account runbook. Clean-room sign-in work remains outside
  every M5 item.
- M5.21 uses the accepted M2/M3/M4 services and M3's real scripted compatible

## Work items

### M5.1 Gmail channel core and trusted renderer

- **Inputs:** merged channel/manifest/snapshot contracts, M2 broker and builtin
  renderer interfaces, M3 common MIME/content code and ADR 0010.
- **Owns:** plugin manifest/package, `src/{index,main,boundary,read,decode,sync-data}.ts`
  and sealed artifact builder; hub `outbox/renderers/gmail*` and the Gmail-specific
  outcome-classifier adapter, with agreed builtin-renderer registration.
- **Outputs:** merged `gmail-v1` and `gmail-readonly-v1` profiles, full/read-only
  describe/probe/body/sync/send/
  reconcile handlers through the real SDK; `gmail-rfc5322` renderer and classifier.
  Sending forwards only the exact hub-rendered ticketed request.
- **Acceptance:** process-mode channel contracts and emitted artifact under
  production flags. Deny `/batch`, unmatched methods, method override and
  arbitrary URLs; the read-only broker profile denies organize and send.
  CRLF/header/address/body smuggling fails; recipient/threading/
  MIME goldens parse back to the exact approved content. Separate 429 “Mail
  sending” from “Too many concurrent requests”, and handle Gmail 403 rate-limit
  reasons through the existing broker outcome rules.

### M5.2 Portable mbox writer

- **Inputs:** stored raw mail and the shared MIME rules; owner-initiated export.
- **Owns:** plugin `src/mbox.ts` pure writer and its tests, or its agreed common
  module after consolidation; no second retained writer in the hub.
- **Outputs:** deterministic mbox framing/escaping from exact raw RFC 5322 bytes.
- **Acceptance:** independent parse-back, binary/line-ending and quoted-From
  controls preserve message bytes and boundaries; bounded streaming/cancellation
  and empty export. This writer grants no mailbox access or export authority.

### M5.3 Lazy bodies and eviction

- **Inputs:** M3 apply/content APIs and the M2 store/clock.
- **Owns:** hub `channels/gmail/body.ts` and its body-cache metadata/migration.
- **Outputs:** lazy bounded raw-body retrieval; 90 days without access by default
  before configurable eviction, with re-fetch on demand. Metadata remains while
  connected. Plugin parsing/direction never becomes hub-verified content.
- **Acceptance:** access/eviction races and restart preserve current account,
  mode and source; no stale fetch publishes after close/purge. Re-fetch is
  budgeted and parsed by the real bounded content worker; eviction removes body/
  derived text/index material according to the common storage policy.

### M5.4 History sync

- **Inputs:** merged change types, M3 sync/apply and M2 durable jobs/budget.
- **Owns:** hub `channels/gmail/{cursor,sync,job,sync-binding}.ts` and their
  namespace migrations; plugin `src/history/**` request plans and response
  decoders, with a narrow registration in M5.1's sync handler.
- **Outputs:** the plugin decodes bounded paged history to `NormalizedChange[]`
  through `channel_sync`/`channel_listen`. The hub owns budgeted scheduling,
  opaque uint64-decimal history IDs, guarded idempotent application and durable
  cursor checkpoints, with one worker per account. No native polling or rescan
  adapter decodes Gmail responses as another inbound source.
- **Acceptance:** malformed/cyclic/oversized pages, wrong account/generation,
  stale source and cancelled jobs fail closed. Page application and cursor commit
  are atomic; partial plugin pages prove no complete scan or deletion. Restart
  neither loses a page nor repeats an effective write. Process integration proves
  the plugin contract is the sole inbound path, including the 404 rescan.

### M5.5 Initial and expired-history rescan

- **Acceptance:** interruption/restart, pagination changes, cursor expiry and

### M5.18 Hub-owned Google OAuth flow

- **Inputs:** M2.3/.4 authority/credential/broker, M3 L1 and the M2 control CLI,
  M5.10, BYO Desktop client, M1.28 (Gmail code relay over L2: `client`,
  `authorize`, `relay`) and M1.26 (the review path `account.connect` uses through
  M4.13). These contracts merge into M1 before implementation starts.
  Hub-host and FakeDevice paths start first; native-device relay
  integrates after M4's hooks merge, without holding the independent hub flow
  for the desktop wizard.
- **Owns:** hub `channels/gmail/connection/**` except M5.10's credential module;
  flow/account/installation/completion namespace migrations and tests; the single
  Gmail L1 `/oauth-cb/<flowId>` registration and L2 relay endpoints by agreement.
- **Outputs:** hub-generated state/PKCE/authorization URL, exact callback and
  client binding; native-device code relay and hub-host loopback. The headless
  SSH-tunnel fallback is postponed. Code is single-use; tokens remain in the hub.
  Account alias
  defaults to owner-editable `gmail-1`, never provider-derived authority.
  `start`, `current` and `cancel` are hub API routes through `hub_request` (TS
  only), importing M1.28's shared types rather than adding another relay spec.
- **Acceptance:** swapped/replayed/expired state, code, callback, client, device,
  subject, installation and flow generation fail; actual mTLS/PIN/admin approval
  is rechecked before persistence. Full mode requires `openid email gmail.modify`;
  read-only requires `openid email gmail.readonly`, accepting Google's equivalent
  `https://www.googleapis.com/auth/userinfo.email` name for `email`. Test each
  missing required scope separately. Companion Gmail scopes may be the narrower
  `gmail.readonly`, `gmail.metadata`,
  `gmail.labels`, `gmail.compose`, `gmail.send` and `gmail.insert` in full mode;
  read-only may additionally carry only `gmail.metadata`. Here `gmail.*` denotes the Google
  `https://www.googleapis.com/auth/gmail.*` scope names. In each mode refuse
  `https://mail.google.com/`, `gmail.settings.*` and every Gmail scope outside
  that mode's permitted set, including `gmail.modify` in read-only mode. Refuse
  rather than silently changing mode. An invalid initial connection persists no
  usable credential and revokes the rejected grant, visibly reporting cleanup
  that is not confirmed. A failed reconnect or mode switch preserves the existing
  live connection and grant, with no automatic revoke: Google's endpoint revokes
  the account's whole grant to that client. No live Google client ID in the repo;
  token metadata or an ID token alone grants no identity or approval. Bound
  requests, cancellation/retirement and genuine native task settlement;
  pending/failed construction adds no new usable credential.
