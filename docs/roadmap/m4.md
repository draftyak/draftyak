# M4 backlog: devices and desktop

M4 delivers the full L2 device surface and the desktop app on the approved plan's
sections 3, 7, 8 and 12–14. It consumes M3 and M1b; it does not replace their
implementations. M4.1–M4.21 divide that scope into stable, separately owned items.
An item below is an acceptance target, not a claim that its code or checks have
landed. Run results belong in the PR body, not in roadmap verification diaries.

**M4 is done when:** the Windows debug app runs “This computer is my hub” through
native PIN approval; a killed sidecar restarts within 60 seconds; a second profile
pairs through native paste and the decided SAS flow, then approves only after
confirmation; wrong SPKI, replay, revoked-device and missing-PIN attempts fail;
the XSS corpus is clean; and a scheduled send appears in the tray Quit list,
holds and releases keep-awake, then becomes NEEDS_REAPPROVAL (Missed), with no
send, if the app stops past its window. Every applicable item and dependency gate
below must also pass before owner sign-off.

## Integration and ownership

- Item branches target the current `m4` integration branch. They contain only
  their own changes and dependencies already merged into that base. M1 and
  M2–M3 flow into M4; M1b also flows into M4. No later milestone is an input.
- M1 owns every change under `packages/protocol/`, `spec/` and
  `crates/draftyak-protocol/`. Request missing contracts there before consuming
  them. M4 uses merged codecs, hashes, scheduling checks and statement types.
- M2 owns identity/PIN/epoch authorization, persistent bootstrap/recovery,
  outbox claims, policy and the scheduler. M3 owns the minimal L2/L1 APIs, client,
  content, drafts and SPA. M4 adds full device/native flows through their hooks.
- Each **Owns** row includes its matching tests. Native paths below are relative
  to `apps/app/src-tauri/src/`; web and hub paths are written in full. If a
  provisional implementation uses a different path, coordinate its extraction
  with the existing owner before editing it. A new directory reserves no right
  to duplicate an existing security service.
- M4.2 initially creates the app package. Later items take over only their named
  modules. Shared startup, `lib.rs`, Tauri command/capability registration,
  `apps/web` routing/navigation and hub API registration receive only the small
  additions agreed with the current owner. Cargo members, pins and lock entries
  are similarly append-only; keep both sides of Cargo.lock conflicts and never
  resolve them with `cargo update --workspace`.
- Product packages follow the repository's TypeScript/Vitest tier rules.
  Platform-native tests additionally use Rust and the real app features. Test
  stores, development keys and auto-confirm hooks are test-only, with release
  exclusion checks. No vendor call or live credential is part of offline tests.
- Before an item submission, run frozen installation, the touched packages’
  tests/typechecks/builds, `pnpm guard` and the item checks below on the current
  PR base. Required CI, including Windows, supplies full verification. Changes
  to CI selection or verification tools additionally run the affected checks
  locally. Submit related review fixes together; reviewed heads merge through
  auto-merge. Only the owner signs off milestone gates.

## Work items

### M4.1 Native pairing workflow

- **Inputs:** M1.21 consent/roles, M1b's native transport boundary and ADR 0007.
- **Owns:** `crates/draftyak-desktop-pairing/**` and its Cargo member/lock entries.
- **Outputs:** native state machine and public projections for consent,
  correlated completion, cancellation and expiry. No renderer or caller supplies
  confirmation authority.
- **Acceptance:** Rust unit tests reject out-of-order, stale, cancelled, expired
  and mismatched callbacks. SAS acknowledgement alone grants no capability.
  Transport and real trusted-surface acceptance remain M4.11, not a unit claim.

### M4.2 Runnable desktop shell

- **Inputs:** M1 workspace/toolchain and settled Tauri security requirements.
- **Owns:** the initial `apps/app/**` package, Cargo app registration and its
  manifest/lock entries; narrow app routing additions in existing CI/verification.
- **Outputs:** Windows debug executable, hub/connect mode choice, bundled main
  UI from the one `apps/web` SPA and a separate trusted-window foundation. The
  SPA uses React 19.3 with React Compiler 1.0, Vite 8, TanStack Router/Query/Virtual,
  shadcn/ui on Base UI, Tailwind v4, DOMPurify 3.4 and `openapi-fetch`, with
  ADR 0001 V12 pins and Vitest tiers; Tauri bundles its build as `frontendDist`.
  Keep isolation pattern, freezePrototype, per-window capabilities, strict CSP
  and Trusted Types together.
- **Acceptance:** the executable opens; mock-runtime ACL tests refuse foreign
  origins/labels/commands and navigation. Test custom-protocol responses too.
  No remote IPC or shell/fs/http/websocket JavaScript plugin. The actual desktop
  feature compiles and passes clippy; the strict all-target audit must pass
  without advisory suppressions before submission.

### M4.3 Profiles, single instance and native intake

- **Inputs:** M4.2; M1b's settled payload decoder for real pairing intake.
- **Owns:** native `profile*`, `instance*`, `intake*`, `clipboard*`, native intake
  tests and the small startup/deep-link registration hooks.
- **Outputs:** `com.draftyak.client`, lowercase platform data paths and Tauri
  directory overrides; separate identifier, data and keychain service per
  `--profile`; single-instance forwarding; native clipboard/dialog paste.
- **Acceptance:** two profiles coexist without sharing stores; a duplicate
  profile forwards safely; malformed profile/link arguments fail. A pairing link
  only opens the screen, never connects. Pairing code, secrets and addresses
  never enter JS or logs. Startup consumes M2.11's synced-folder refusal.

### M4.4 Device stores, transport and hub-key changes

- **Inputs:** M1b.1–.4, merged `hub-key-rotate.v1`, M2.24's hub-side rotation,
  M4.2–.3.
- **Owns:** native `device_store*`, `transport_adapter*`, `trust*`, `forget*` and
  device-side rotation/reconnection tests; narrow native store adapter hooks.
- **Outputs:** one persisted paired hub, native keys/pins/signing and forget;
  device acceptance of a successor hub identity or statement key only through
  `hub-key-rotate.v1` verified with the currently trusted old key.
- **Acceptance:** reload the real identity and reconnect; wrong SPKI refuses.
  Rotation checks exact hub, epoch, key use, successor and signature, persists
  the replacement atomically, and survives restart. Unsigned discovery, stale,
  replayed, wrong-key-use, wrong-epoch and forged changes cannot replace a pin.
  Forget deletes device secrets. Store failures never choose a volatile/mock
  fallback; no secret state reaches JS. M2.24 retains rotation issuance and
  hub-side retirement; M6b retains the SMS-host consumer.

### M4.5 L2 pairing windows and claims

- **Inputs:** M3.6 minimal L2, M2.3 authority, M1b transport, M1.26’s
  pairing-window L2 call, M1.21b’s commit-reveal claim and relevant ADR 0007/0012
  checks.
- **Owns:** new hub `identity/device-pairing/**`, full pairing adapters under
  `apps/hub/src/api/`, and `apps/hub/test/m4-pairing/**`; only agreed registration
  additions to M3's minimal listener/pairing hook.
- **Outputs:** five-minute role-aware windows, advertised-address payloads,
  three-failure burn, single claim and pending-device records through existing
  identity services. TLS 1.3 only, with hub session tickets disabled.
- **Acceptance:** real Node TLS tests refuse a device presenting another SPKI
  and prove the hub issues no session tickets, absorbing ADR 0012's hub-side
  `transport-skeleton/tests/check.rs` cases. Unknown peers reach only pairing
  paths during an open window. Live exporter/certificate binding, role mismatch,
  replay, expiry and exhausted attempts fail; pending clients have no ordinary
  route, approval or admin rights. No L1/L3 pairing route.

### M4.6 Confirmation, recovery and revocation

- **Inputs:** M4.5, M1.26’s pair-confirm review, the M1.5 confirmation presets
  and M2.2–.4/.10/.12 authorization/PIN/recovery services.
- **Owns:** new hub identity `device-confirmation/**`, `device-recovery/**`,
  `device-revocation/**` and their M4 integration tests.
- **Outputs:** persistent bootstrap-once on the trusted hub surface; existing
  desktop approver plus PIN for later approvers; CLI-only read/draft and mobile
  read/draft/organize ceilings; recovery-code/24-hour-delay flow with alerts;
  revocation closes sockets and delegates approval invalidation to M2.
- **Acceptance:** restart cannot reopen bootstrap. Consent, claim success and
  SAS comparison never confirm or elevate a device. Missing/wrong PIN, revoked
  signer and replay fail. Last-approver CLI protection holds. APPROVED/SCHEDULED/
  RETRY_WAIT items affected by revocation need re-approval. If SMS is enabled,
  only a desktop approver confirms a host, which cannot sign device statements.

### M4.7 L2 capability routes and resumable events

- **Inputs:** M4.5–.6, M2.3/.5, M3.8 and M1.26’s event frames and route rules;
  host clauses require an S12 go and settled SMS roles.
- **Owns:** new hub `identity/device-routes/**`, `identity/device-events/**`,
  full L2 route snapshots and M4 event tests; coordinated listener registration.
- **Outputs:** complete desktop/mobile/device allowlists, applicable host-only
  stubs and authorized resumable ID-only events using the existing event store.
- **Acceptance:** role × capability × confirmation × epoch snapshots refuse
  cross-role calls; revocation closes connections. Expired/replayed cursors and
  event resume cannot widen access. Every L2 request uses mTLS, never a bearer
  shortcut; device/admin/approval routes remain absent from L1/L3.

### M4.8 Loopback browser login and pending records

- **Inputs:** M3.7/.8, M4.6, M1.26’s login challenge/review extension, merged
  `login.v1` and M2.3 authorization handoff. The rendered login subject and its
  challenge cases land first in a separate `m1` PR naming M4.8 and M1.26.
- **Owns:** new hub `identity/browser-login/**`, native `login*`, web
  `apps/web/src/desktop-login/**`, the `apps/cli` login-code command file and
  coordinated browser-login API registration.
- **Outputs:** PIN-protected CLI login-code and desktop code matching; the
  server-owned login pending-record shape with challenge/code binding, expiry,
  requesting context and one-use consumption; an eight-hour loopback session
  with `__Host-` HttpOnly SameSite=Strict cookie and CSRF secret.
- **Acceptance:** wrong/expired/replayed code, swapped pending record, foreign
  Host/Origin and CSRF fail. M2.3 checks the actual confirming desktop's current
  authority. Browser access remains read/draft/organize/cancel only. Resolve
  cookie/listener compatibility with the contract owner before implementation.
  Linux Playwright WebKit and a macos-15 loopback `__Host-` Secure cookie probe
  must pass before accepting that compatibility. M3.9/.13 and the existing e2e
  workflow own Linux WebKit runs (and macOS where selected); Windows browser
  checks are Chromium-only. Until those results exist, compatibility is an
  explicit acceptance gap. M1.18’s local-time check defines no login pending record.

### M4.9 Sidecar process supervision

- **Inputs:** M4.2, M2.11/M3 lifecycle and final ADR 0007 supervisor handoff.
- **Owns:** native `sidecar/**`, its resource/staging entries and process/frame
  tests; narrow coordinated hub framed-control startup/exit hooks. Own both
  codec ends outside `spec/`, keep M0.22’s `tests/sidecar.rs` with `hid` and add
  the hub-side counterpart. Use M1.26 L2 calls for window open and sync pause.
- **Outputs:** verified official `draftyak-node-<triple>` launching
  `--disable-sigusr1 hub.mjs` without a shell/inspector; suspended Windows spawn
  into a kill-on-close Job Object; bounded stdin/stdout frames, stderr-only logs;
  ten-second health checks and 1–60-second backoff, at most five restarts/five
  minutes. The app is an ordinary paired device, with no privileged hub API.
- **Acceptance:** kill/unhealthy restart takes under 60 seconds; descendants
  die on restart/close and abrupt parent death, including POSIX's ignored-EOF
  backstop and actual process-group check. Stdin EOF exits. Quit stops claims
  and drains at most ten seconds. Malformed/partial/oversized frames fail safely;
  secrets never reach argv/environment/logs. macOS's scrubbed environment permits
  exactly the required `__CF_USER_TEXT_ENCODING` exception, never NODE_*.

### M4.10 Hub onboarding, master key and bootstrap

- **Inputs:** M1b.3/.5, M2.2/.11/.12, M3, M4.4–.6/.9, M1.26’s PIN-setup
  bootstrap call and ADR 0007 keychain.
- **Owns:** native `onboarding/**`, `master_key/**`, `bootstrap/**` and onboarding
  views; agreed app/kernel bootstrap hook.
- **Outputs:** hub/connect choice, OS-stored master key, trusted recovery-code
  display and PIN setup; bootstrap material over stdin; same pinned-loopback-L2
  exporter-bound claim. First approve/admin rights follow PIN setup and genuine
  trusted-surface confirmation, never receipt of a supervisor frame.
- **Acceptance:** first run completes and restart preserves identity/bootstrap.
  Owned key buffers use best-effort erasure; no key reaches JS/argv/env/logs.
  Without Linux Secret Service use only the approved passphrase-wrapped
  `mk.wrapped` fallback and stay LOCKED until unlock. On macOS consume the owner's
  update-prompt decision, test a changed binary identity and denied reads, and
  define the approved fallback without silently replacing a key.

### M4.11 Real pairing screens and trusted SAS comparison

- **Inputs:** M4.1/.3–.7, M1b.6, M1.26’s status and M1.21b’s commit-reveal

- **Owns:** native `pairing*`, trusted pairing views/capabilities and native/e2e

- **Outputs:** native paste, hub-name/ID consent, real keys/transport and bounded

### M4.12 Trusted approval rendering

- **Inputs:** merged snapshot/hash/schedule contracts including M1.18, M1b,

- **Owns:** native approval `render*`, `snapshot*`, `time*` and

- **Outputs:** Rust fetches by ID, re-hashes and renders the exact operation:

- **Acceptance:** hash/render mismatch refuses; hostile text stays data; foreign
  windows cannot fetch approval assets. Own custom-protocol origin, no storage/
  service worker/navigation escape; isolation/CSP/Trusted Types together.
  Shared schedule/DST vectors agree. SMS segment recomputation waits for settled
  contracts and M6b, with mismatch refusal and the fixed plain-SMS disclosures.

### M4.13 PIN approval, administration and pending operations

- **Inputs:** M4.4/.6/.12, M2.3/.4, M1.26’s `admin_open`, operation reviews,

- **Owns:** native approval `confirm*`, `statement_adapter*`, `admin*`, `consent*`,

- **Outputs:** approval-window-only PIN collection and exact-hash native signing;
  `admin_open(kind, ids)` creates a server-owned pending operation over L2 before

  Wire merged consent/login/agent-session/pair-confirm statements as available;

- **Acceptance:** forged origin/label, main-window IPC, missing/wrong PIN,
  pending-operation mutation/substitution, expired/replayed challenge, revoked
  device and mobile/browser approval fail. Argon2id/lockout stays in M2 outside

### M4.15 Scheduling controls and cancellation

- **Inputs:** M1.18/shared schedule contracts, M1.27’s scheduling status,
  M2 scheduler, M3.10 and M4.12–.14.
- **Owns:** native schedule projections, `apps/web/src/desktop-scheduling/**`,
  app scheduling views/tests and agreed composer/outbox hooks.
- **Outputs:** explicit gap/fold selection, time/zone/lateness/hold controls,
  one-time stored sidecar acknowledgement through M4.15’s own setting route,
  per-account Scheduled view and trusted
  “Approve & schedule”; availability, hold and missed/restored reasons. Cancel
  returns to draft; Reschedule and Send now cancel first and need a fresh PIN.
- **Acceptance:** desktop and loopback-browser cancellation race the real claim
  safely. Edits clear authority; live drafts lock; a proposed time binds only
  through PIN approval. Stop/sleep past the window yields NEEDS_REAPPROVAL with
  zero sends, never a late/immediate fallback. Acknowledgement grants no approval.

### M4.16 Tray and guarded Quit

- **Inputs:** M4.9/.14–.15, M1.27’s tray/Quit summary and M1.26’s sync-pause
  L2 call.
- **Owns:** native `tray*`, `quit*`, `apps/app/quit/**` and lifecycle tests.
- **Outputs:** status/count/next send; Open, Pause sync, Pair device and Quit.
  Main-window close keeps the hub running. Quit lists the next five sends with
  time/account/recipient and missed-window explanation; Keep running is default.
- **Acceptance:** cancelling Quit leaves the hub active. Quit anyway stops claims,
  drains/shuts down and removes owned children. Pause preserves claim-time reads.
  Destroy webviews before exit to release WebView2 files; create/destroy off
  event-loop handlers. Stale pending lists do not silently close the app.

### M4.17 Keep-awake and resume

- **Inputs:** ADR 0007, M4.9/.15 and M2's scheduler frames/tick.
- **Owns:** native `power/**`, platform adapters and power/lifecycle tests.
- **Outputs:** Windows SystemRequired, macOS PreventUserIdleSystemSleep and Linux
  logind idle inhibitor from T−5 minutes until deadline/terminal state; resume
  frame triggers an immediate tick. Restore the hold from the hub's current
  frame after each start, release by `untilMs`, hub exit, null frame or Quit.
- **Acceptance:** acquisition/release/deadline/crash/quit and resumed delivery
  pass on supported platforms; refused Linux inhibition is nonfatal and logged.
  Fake-power coverage plus a real Windows check; owner-authorized real sleep/
  wake checks remain distinct from compilation. No wake timer/away mode or
  promise to override explicit sleep, lid close or power limits.
