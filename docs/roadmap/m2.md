# M2 backlog: security core and plugin runtime

The approved implementation plan, sections 3, 4, 7, 9, 12 and 13, defines this milestone. Full planning artifacts stay outside the repository. The owner's request on 2026-10-17 to build M1b, M3 and M4 authorizes the M2 prerequisites those integrations require. Early local work does not waive the M1 or M0 gates.

M2 is incomplete. M3 and M4 must use its real security services; an in-memory store, fake approval, or permissive authentication adapter is not a production substitute. Only the owner signs off and merges a milestone into main.

## Branching and ownership

Item branches use `m2-<nn>-<slug>` in worktrees outside synced folders and rebase onto `origin/m2`. Later items use merged prerequisites; contract changes land in M1 first. Related items may share a PR. Before opening a ready PR, run frozen installation, touched-package tests/typecheck/build, changed-file lint, vendor-guard and item acceptance. CI supplies full Linux and Windows verification. The milestone gate still requires Windows milestone verification and owner sign-off.

M2 owns the hub's `kernel`, `store`, `audit`, `identity`, `authz`, `policy`, `accounts`, `jobs`, `events`, `outbox`, `credentials` and `plugins` core, plus the minimum immutable draft-revision persistence needed by the outbox gate. M3 consumes those revision primitives for sync, content, draft lifecycle, AI and API/UI wiring; M4 owns later device pairing routes and desktop adapters. Shared hub package/config entries require narrow registration changes. Product code never imports spikes.

Stream 2a is the gate core; stream 2b is the plugin runtime. M2.18 is a 2b component delivered with M2.6–M2.8 because ticket minting and guarded claim share one authority boundary. M2.21 combines the two streams; its composed checks run after both have merged.

## Changed since the plan

- M2.2 initializes the plan-named `@peculiar/x509@2.2.0` with exact runtime `reflect-metadata@0.2.2` (Apache-2.0), approved by the owner on 2026-10-20. Existing dependencies and the normal release-age, locked-graph, security, licence and verification requirements remain.
- M2.11 refuses startup in a detected synced data folder with `DATA_DIR_SYNCED`. This is stricter than plan §7, which makes doctor refuse and startup at most warn. The owner decides this choice at the M2 review; later startup/doctor acceptance follows that answer. Missing Temporal alone warns and leaves existing approved UTC claims usable.
- M2.6 brings forward only immutable draft-revision rows and their transactional freeze/lock interface from M3. M3.4 consumes that interface and adds the draft lifecycle and API/UI integration. M2 never depends on the later M3 branch, and this move creates no new snapshot protocol.
- ADR 0003 selects tagged host frames on stdin/stdout, FIFO stdin/stdout/stderr on Linux/macOS and spawn pipes on Windows. The shared `@draftyak/protocol/plugin-stdio` contract lands in M1.14b before runtime consumers. Plugin exit triggers nonblocking output drain and FIFO cleanup; cleanup never waits for EOF. This replaces the plan's fd-3 host channel.
- FakeDevice is an M2 acceptance client using Node TLS and merged M1 device contracts. M2-only identity, kernel, rotation and client work does not depend on M1b's later Rust transport.

## M2.2 native identity and PIN handoff

M2.2 owns wrapped key persistence, certificate/TLS material, native PIN counters and scoped preparation/proof primitives. It adds only identity metadata, users and PIN foundation schema; M2.3 owns owner creation, epoch/device/bootstrap state and authenticated bootstrap composition. Native callers explicitly lock identity/PIN services before destroying the master key or closing the store. The internal live-write guard is not a root package export. No generic statement-signing endpoint or ticket format is added: M2.24 owns outgoing-identity-key rotation; gated statement-key/ticket consumers remain with their own items. M2.11 owns master-key intake and startup lifecycle; M2.12 owns restore/master-key rotation.

## Runtime item details

### M2.11b CLI payload and discovery mechanism

This complete standalone component needs M2.1 only and imports no hub or native
service. It supplies the shared payload contract, argument snapshot/dispatcher,
fixed owned command and diagnostic directories, automatic source/build discovery
and the complete staged JavaScript closure. The workspace package is private
`@draftyak/cli`; the executable and public distribution name remain `draftyak`.
Only implemented help is installed. Packaging authenticates the entire payload
before import and owns public launch/re-exec policy; no artifact is published here.

M2.11 retains its full M2.1–M2.10 and ADR 0007 prerequisites and every remaining
native acceptance clause: real authenticated unlock/control/status, LOCKED and
maintenance claim inhibition, all master-key sources and erasure, safe drain/EOF,
owner checks, synced-folder refusal, Temporal warning, Unicode-version checking
and interrupted-first-initialization recovery. M2.11b neither supplies substitutes
for those services nor completes M2.11 or its gate. Real doctor checks join as
feature-owned files after their prerequisites merge. The bounded-reader component
and its path/record validators remain separately owned M2.11 work.


### M2.15 Pilot installer policy

The pilot accepts only the bundled first-party IDs `channel-gmail`,
`channel-slack`, `ai-messages-api`, `ai-responses-api` and
`ai-chat-completions`. `channel-hello` remains a contract fixture and is not
bundled. Third-party installation, the plugin-author kit, context tools, Python
and json-template sends are postponed. The installer must refuse those excluded
packages or manifest features even if their historical schema still validates;
omitting a screen or package alone does not prove refusal. The installed artifact
still requires the actual M2.13 config-loaded extension-module registry. A
descriptor validator or registry interface does not supply that input.

Installer acceptance covers both initial installation and upgrades: exact version,
package integrity, read-only unpack, no scripts, strict manifest validation,
per-file hashes and refusal of missing, extra, tampered, symlinked, junction or
hard-linked files. A stray unlisted file, including `.DS_Store`, fails closed.
The same controls apply on Windows, Apple-silicon macOS and Ubuntu24.04; document
the extra-file refusal rather than silently ignoring platform metadata. Positive
controls admit each selected bundled plugin, and negative controls refuse an
otherwise valid third-party package, tool kind, Python runtime, `url-secret` or
json-template send. Historical tool admission/write-class/ws/send rules remain
saved for the postponed tool surface; they do not authorize pilot tool admission.
M2.25 consumes the verified installed artifact without creating a reverse
dependency from the installer to activation.

### M2.16 Retained process acceptance

The supervisor uses the merged shared stdio and argv contracts after actual
propagation. Channel-account and provider-instance processes retain exact flags,
the Node floor, scrubbed environment, real-path filesystem grants, file rehashing,
RSS sampling, call/startup timeouts, crash accounting, leases and idle exit. Tool
instance and Python runtime rules are postponed. A reviewed generation enters
through the narrow activation seam; this low-level item does not depend on or
import the later M2.25 registry or M2.26 vault. No synthetic generation establishes
production authority.

Required platform controls cover Windows pipes and process teardown, plus macOS
and Linux FIFOs, descriptor reinstatement, held writers, backpressure and bounded
exit drain/cleanup. macOS additionally covers real-path grants and plugin staging
from the read-only app bundle, including the `/var` to `/private/var` alias and
the permitted `__CF_USER_TEXT_ENCODING` environment entry. Retain the applicable
POSIX sampler/process-group teardown and parent-death controls; native acceptance
must prove them on the selected OS. ADR 0013's applicable JavaScript sandbox fixes
remain required after their exact routing is confirmed; postponing Python does
not waive JavaScript isolation. Pure argv/codec or synthetic process fixtures do
not complete the native supervisor or its platform checks.

### M2.17 Retained broker composition

The pilot retains `gmail-v1`, `gmail-readonly-v1`, `slack-v1` and the three
bundled providers' allowlist verifiers. Preserve URL/header canonicalization,
method-override/system-parameter stripping, profile classification, account-mode
checks, exact executor-minted ticket binding and one-shot consumption, credential
injection, one common refresh coordinator, size/time bounds and audited denials.
Slack's `chat.scheduleMessage`, `chat.deleteScheduledMessage` and

## M2.1 scope and handoffs

The first item adds the real encrypted file and migration/audit primitives. It does not initialize an approver, expose a listener, approve, schedule or send. The master-key wrapper uses unpooled storage, keeps bytes private and supports erasing its owned buffer; JavaScript garbage collection and intermediate immutable strings do not provide a whole-process zeroization guarantee.

The foundation also binds the actual encrypted connection to its master key without exposing a fingerprint, reserves transaction and connection-control statements in every query method, runs read callbacks with SQLite's query-only setting, bounds audit reads before stored values enter JavaScript, and exports bounded JSONL pages from the verified chain. Namespace-to-folder mappings are copied at construction from the kernel's bundled configuration; `migrate(namespace)` cannot select another folder. Native-only package exports expose the facade, audit operations and key wrapper; raw database and cleanup helpers stay internal.

Sequential export retains one bounded authenticated head and cursor. Ordinary writes and audit appends through that same store preserve the resume: it checks the retained rows, count and current authenticated head, verifies the newly appended tail, and verifies the requested page. A retained checkpoint that no longer matches (including a rolled-back write) is discarded and the chain is fully verified with fresh page state; only full verification can refuse it as corrupt. Schema changes, another connection's commits or another reader owner conservatively require full verification again. Changes during a page refuse it. A page ends before its byte bound and returns the first excluded event on the next page.

Audit operations explicitly address the durable `main` schema, so temporary tables cannot conceal corruption, redirect an append or substitute an empty chain. Synchronous callback refusal observes ordinary returned native Promise rejections without reading caller `then` accessors. Proxy callbacks/results and accessor-based thenables are refused without invoking their hooks. Promise constructor/species changes within the native process remain trusted behavior.

Failed file or native-connection initialization retains the actual owned resource and blocks new opens until cleanup succeeds. `HubStore.close()` immediately revokes SQL and key-comparison authority, retains an unproved native close for a later retry, and recognizes a close that completed before throwing. The caller owns and must retain a returned store until close succeeds. Closing the store leaves the caller's master-key lifetime independent.

Validation includes real native database reopen and wrong-key checks, plaintext-file refusal, transaction rollback/expired handles, async callback refusal, atomic migration rollback with triggers, newer-schema refusal, audit mutation/truncation and subkey separation. Persistence integration, PIN, recovery, snapshots, rotation, runtime composition and the rest of the gate are subsequent items; passing these foundation tests does not complete M2.

The audit namespace owns only audit_events and audit_meta. Identity, devices, PIN, epoch, recovery and wrapped-key tables belong to M2.2 through M2.3 and M2.12; store tests use an independent fixture namespace. Clock implementation and the kept timers test belong to M2.7.

Audit append accepts the merged AuditEvent (id, at, action, actor kind/id and typed refs); M1.11 AuditSink and M2.14's free sink consume that same type. Native storage bounds each event to at most 32 refs. Every append authenticates both its row and the durable {seq, mac} head in the same transaction. SQL row/head rewinds without a valid head tag are refused. A captured earlier authenticated state or a restored older whole database still needs an anchor outside the database to detect rollback; selecting that anchor is open for the owner's M2 review, and this item does not build one.

M2.1 currently ports ADR 0002's kept open/HKDF/reported-settings, migration/rebuild/SQLite-rollback and live/checkpointed db/WAL/SHM canary cases. It also ports the native build-default comparison, encrypted-to-unkeyed backup refusal with a real plaintext control, and no-plaintext-temporary-file case with live FILE controls. M2.12 owns rotation and the deleted-text tests requiring both secure-delete settings and WAL truncation. M3.3 Apply and durable sync jobs, which owns the native content namespace migrations creating `fts_messages`, absorbs FTS5 triggers with `trusted_schema=OFF`, REPLACE, FTS secure-delete and `incremental_vacuum`; coordinate that item before removing those spike copies. `spikes/s01-sqlite3mc` remains until all absorbing work deletes the corresponding cases. M2.7 absorbs ADR 0015's timers case.

M2.1 does not infer new audit authority from an existing empty or initialized file. In the same process, only an untouched exclusive first-create reservation may retry. After a process stops before audit genesis commits, a subsequent open refuses genesis with explicit recovery instructions; under `create`, an unowned empty file is refused before native initialization. Restore a valid backup or remove only the unused, never-initialized database and create it afresh. Automatic restart recovery for this interrupted first run is a required M2.11 startup decision and acceptance case; the current conservative rule is not a completed recovery implementation.

The commands above are acceptance targets for their owning items, including paths not implemented yet. M2.1's current commands are `pnpm install --frozen-lockfile`, `pnpm --filter @draftyak/hub exec vitest run --reporter=default test/store`, `pnpm --filter @draftyak/hub typecheck`, `pnpm --filter @draftyak/hub build` and `pnpm guard`. Run results belong in the PR body.

M2.11a's shared reader exports `readBoundedRegularFile` with mandatory safe-integer maximum (1 byte through 512 MiB), optional minimum and expected size, and fixed content-free path/file/bounds/ownership errors. It preserves canonical absolute paths, no UNC or ancestor links, regular-file/single-link/nonzero-inode checks, before/open/after/named identity/size/time checks, bounded positional reads and an EOF growth probe. Each operation closes its own handle in `finally`; close failure refuses that operation without a global latch disabling later independent reads. Callers retain their selection/exclusion and size policies. Installed module metadata resolved through the module loader does not weaken the untrusted-artifact hardlink refusal.

### M2.6a Pure draft normalization

`normalizeDraftBody(body)` converts CRLF and lone CR to LF, then NFC, before
shared validation, flags and immutable hashing. Its 400,000-unit raw UTF-16
intake budget is a native resource policy, not an M1 wire or byte limit.
`normalizeDraftContent(input)` returns detached, strictly validated email/chat
content. Shared output bounds count code points: email body 100,000, chat body
40,000, subject 2,000 and filename 1–256. Subjects and filenames remain unchanged
when valid; CR/LF refuses rather than folding or replacing characters. Attachment
media types lose parameters and become lower-case, with application/octet-stream
as fallback. Body, subject and filename text is not trimmed. No content hygiene,
recipient changes or authority facts are introduced. Full M2.6 persistence/proposal and later M3.4 lifecycle acceptance
remain required; both consume this one normalization implementation after merge.
