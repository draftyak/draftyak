# M1b — Native device transport

M1b implements the native client transport below the desktop and mobile surfaces. It consumes merged M1 contracts; it does not define contracts, confirm devices, grant capabilities, approve sends or start a listener. Each item lands on current `m1b` with only its own work and merged prerequisites. M1b flows into M4, never the reverse.

**M1b is done when:** “Pairing vectors pass both ways; a wrong SPKI, a replayed proof or a mismatched transport key fails” (plan §12). M1b.1 owns the independent TLS checks, M1b.3 persisted identity and reconnection, M1b.7 claims and proofs after M1.21b, and M1b.6 the SAS API and vectors after M1b.7. Each row's acceptance and M1b.8's gate are required: `pnpm verify:m1b` green on Windows, CI green apart from `dco`, then the owner's sign-off. A successful claim or public preview grants no confirmation authority.

## Conventions

- Rebase item PRs onto the current `m1b` tip, with prerequisites already merged. Run the touched packages' checks and `pnpm guard` before pushing; docs-only changes run `node tools/verify/verify.ts --profile docs` and the guard. CI's applicable full suites, Windows included for product changes, provide full PR verification. A local whole-repository `pnpm verify` is not a ready-PR prerequisite (owner decision D25).
- Item PRs use auto-merge after the required checks and review pass at their current head. At the milestone gate the owner signs off and merges; a passing item PR is not milestone sign-off.

## Pairing contract and connection checks

Owner decision D29 selects commit-reveal for m1.md D18. M1.21b first applies that answer to the M1 contract after M1.26; M1b.7's claim format/proof input and M1b.6's SAS implementation wait until M1.21b and its vectors are merged into `m1b`. The decision does not waive ordinary prerequisites or dependency approvals. M1b.1's pinned verifier, client certificate, payload codec and HTTP checks proceed independently, as do WebSocket transport, key stores, statement signing and sidecar derivation subject to their own prerequisites and confirmations.

M1.21b implements the selected option (a): the claim gains `c`, the proof covers it, the hub's answer gains `nh`, and the reveal exchange opens `c` with `nd`. That M1 contract PR first changes `spec/pairing-v1.md`, `packages/protocol/src/pairing.ts` and `spec/vectors/pairing/`; its merge into `m1b` supplies M1b.7 and M1b.6. They consume the resulting formula and delivery rules rather than preserve the skeleton's superseded SAS. The hub's SAS stays on the trusted surface or in the pending pair-confirm review fetched by a current confirmed approver; the candidate computes its own SAS and receives no hub SAS in its claim, status, events or logs.

The Node TLS peers below are synthetic offline automated tests, not vendor sessions or the `test:live` tier. M1b.1's independent checks use an actual Node TLS peer and the merged `pairingEkm`, without a local copy:

- A hub whose SPKI is not `hid` is refused before any request byte is sent.
- The client's exporter equals the merged `pairingEkm` for that connection.
- An mTLS request presents the generated client certificate.
- TLS deadlines, bounded responses, TLS 1.3-only negotiation, explicit ring configuration and disabled client resumption remain enforced.

After M1.21b merges, M1b.7's actual Node peer answers Rust-created claims through the merged `readPairingClaim` and `verifyPairingClaim`. It checks strict claim encoding, then separately refuses a proof replayed on a second connection presenting the **same client certificate** (only its EKM differs) and a claim whose `transportSpkiSha256` differs from the presented certificate. The replay must receive `PAIR_PROOF_INVALID` from proof binding, not pass solely because a different client SPKI was refused.

Vector ownership is exclusive: M1b.1 takes `payloads.json` and `proofs.json`'s `ekm`/`hubIds`; M1b.5 takes `sidecar`; M1b.6 takes `sas` and M1.21b's reveal cases; M1b.7 takes `proofs` and `claims.json`. No item claims every block in the pairing folder. M1b.7 proves that claims use the reloaded stored identity; M1b.6 then adds complete claim/reveal/reload/reconnect acceptance, so M1b.7 has no reverse dependency on M1b.6.

M1b.3 retains the initial `hid` pin across restarts; discovery and connection responses cannot replace it. M4.4's device-trust flow owns accepting `hub-key-rotate.v1`: verify against the existing pin, atomically replace the stored pin, and refuse every other pin change. That later flow is not an input to M1b's unchanged-pin reconnection checks.

## Platform store checks

M1b.3's private `tools/transport-tests` package uses the shared Vitest heavy tier to invoke the real Rust store checks. Store choice requires an actual write and read, not successful construction. Once a platform case is selected, a missing or unusable store fails; it never silently chooses the mock or a volatile identity. The explicit test store supports ordinary offline CI identity tests only.
