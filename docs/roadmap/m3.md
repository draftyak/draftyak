# M3 backlog: desktop pilot vertical slice on fakes

M3 turns fake inbound mail into an AI suggestion, a saved owner edit, and one
PIN-approved request whose bytes match the hub's frozen render. It also proves
browser approval refusal and scheduled-send cancellation, exactly-once delivery
and missed-window handling on the injected clock. The milestone remains open
until the native composition and owner gate below pass.

The approved plan sections 3, 5, 6, 8, 9 and 11–14, with the adopted desktop
pilot scope, govern this backlog. Item numbers and the 100 original coverage
rows are stable. Windows, Apple-silicon macOS and Ubuntu 24.04 are required.
Changes to shared protocol definitions, schemas and Rust contracts belong to M1.

## Scope, availability and dispositions

This is a planning backlog, not implementation or gate evidence. M3 depends on
M2; M1b runs in parallel and M4 consumes M3 later. No reverse dependency on a
native desktop implementation is introduced. The selected product retains the
desktop app/bundled hub, Gmail/Slack drafting and one-off scheduled send with
unchanged encryption, credential, PIN, recovery and duplicate-send protections.
Paired remote desktops and their hub connections remain in scope.

The document is based on actual M3 `15005be6` and the original backlog document
at `878fb856` (component work submitted separately). On this base the content
and MIME package manifests, draft normalization/revision/proposal paths, device
routes, jobs/events indexes, data-directory component and M3 demo runbook are
absent at their selected paths. These observations do not rule out alternate
implementations. Existing M0/M1 scaffolding and the M2 store foundation are not
a completed native composition. The later M2 public backlog at `a174cdba` adds
requirements/component status, not proof of propagation into this M3 base.

Content/prompt/MIME source and the runbook described in the original submitted
work are **only-on-submitted-source**, not merged-on-base inputs. Every item
path and package command below is **planned/unavailable on this base** unless
explicitly identified as existing verification infrastructure. An Inputs field
states required actual merged/propagated inputs, not their current availability.
Every consuming item must confirm those real producers before implementation;
a plan, pure helper, schema, permissive callback or donor cannot supply native
authority, persistence, routing or successful acceptance.

All M3.1–M3.14 items, including M3.5a, remain retained. M3.5, M3.9 and M3.13
are mixed items with only the precise postponed clauses identified below. The
shared M3.7 route catalogue/settings/OpenAPI and the M3.8 typed client are kept
for desktop access over L2. Browser login/cookie APIs and browser cancellation
are postponed with A1; release builds must not mount them. Their absence and
fixed refusals require evidence, not inference from a missing UI. X7 e2e work
is retained; the t5 point 16/T12 loopback-login cookie probe is parked until the
browser feature resumes. D37 is not waived for that later feature, and no probe
is claimed passed.

Context tools/M7b, MCP/Apps/public issuer/discovery, SMS/M6b, Python/M2c and
mobile implementation are postponed. S11/S12 are postponed, not no-go results.
Keep their original obligations and restart owners without making them pilot
prerequisites or calling their suites passed. Optional sign-in remains separately
maintained and nonblocking. Its unmerged general admin/profile/auth-descriptor
and authorization seams are unavailable and fail closed, not permanently absent;
later approved owning contracts may admit them through normal review. No
optional source, design, mount or acceptance is supplied by this document.

M3.5a stays with the compatible-provider implementation owner. M3.14 retains
the owner-demo runbook; extracting this backlog transfers neither deliverable.
The integration owner alone writes `docs/roadmap/m3-gate.md` after gate review.

## Dependencies and boundaries

- M2 supplies the encrypted store, namespace migrator, short synchronous
  transactions, durable jobs/events, account lifecycle, device authorization,
  challenges/PIN verification, executor, scheduler and structural broker. Each
  item names the subset it consumes. M3 never replaces these with an allow-all
  callback to demonstrate a send.
- M1b runs in parallel with M3. Its hardened Rust client, keystores and paired
  native UI are M4 inputs, not a global M3 dependency. M3 uses M2's test-only
  authenticated FakeDevice and the merged signed-message contracts for its
  minimal device route and approval tests.
- Retained M2.16-19 and native plugin-process tests consume the selected ADR 0003 tagged
  stdin/stdout channel, Linux/macOS FIFOs and Windows spawn pipes after the shared
  M1.14b plugin-stdio contract merges. Plugin exit triggers nonblocking drain and
  cleanup without waiting for FIFO EOF. M2.17 owns the single
  resolved-address/pinned-connection guard, including current hub binds and
  reserved ports. M3 consumes its classification evidence; endpoint classification alone does
  not satisfy that native guard.
- M7 supplies provider implementations. Its compatible request/response core
  lands in M3 before the native drafting pipeline consumes it. Real provider
  logins, tokens and live sessions are outside fake-only acceptance.
- Postponed M7b.8 owns tool-context hygiene, independent random `B2` and the separate
  `<context-{B2}>` block, with M7b.12's context evidence and revision flags. The
  basic M3 thread builder supplies neither context calls nor that later block;
  M7b must extend the prompt through its owned adapter and test independent
  delimiters without turning tool data into instructions.
- SMS remains unavailable in native M3 drafting. The native drafting entry point
  must refuse SMS before calling the email prompt helper, and protected policy
  must take classes only from the merged `DataClass`. M6b owns SMS-specific
  trusted drafting instructions, no automatic SMS drafting, sensitive-text
  exclusion and the FakeSmsHost suite when SMS resumes with its actual owner
  decisions and M1.23/M1.24 contracts. Preserve those rows as postponed history.
- M5 owns the Gmail request adapter and ADR 0010's transport decision about
  preserving Bcc. The shared MIME renderer refuses nonempty Bcc until that decision; it exposes
  no preservation option and grants no send authority.

## Changed since the plan

- **Supporting cleaner corpus.** Cleaner JSON regressions live under
  `packages/content/test/fixtures/content.json`. Required injection cases use the approved
  `security/injection-corpus/*.yaml` path with raw local fixtures. Ingest-to-prompt
  checks supplement the obedient-model/native gate; they do not replace it.
- **MIME foundation brought forward.** `packages/mime/` supports M3.11's frozen
  request comparison before M5. Gmail wrapping, credential injection, network
  sending and ADR 0010's Bcc choice remain with M5 and the M2 broker/executor.
- **Parser and cleaner budgets.** Every worker has a separate ten-second startup
  deadline. Ready cleaners have 32 MiB old/8 MiB young heaps and two seconds;
  mail decoding has 256/16 MiB and ten seconds for raw messages up to 35 MiB,
  matching MIME rendering. Cleaner input stays at 1 MiB and output at 40,000
  UTF-16 units. A body refusal retains validated headers/authentication and
  attachment size/type/hash metadata, never an unseen plain-text alternative.
  The pinned parser retains encapsulated messages as opaque attachments, so
  acceptance tests exercise reachable limits and pin that option instead of
  claiming unreachable forwarded-message/depth counters ran.

## Milestone verification

Ordinary documentation changes use relevant successful exact-head required/title
CI and one independent review, with public source/commit hygiene. No duplicate
local installation/suite, new event or receipt/tree reconstruction is required
solely because the base later moves. A real conflict, dependency or changed-source
interaction still needs resolution. Protected implementations and changes to CI
selection/reporting/refusal controls retain their applicable checks and narrow
local self-validation; CI cannot validate its own altered controls.

The completed milestone requires applicable default verification, the planned
`pnpm verify:m3`, all retained native/model/security/rendering/OpenAPI/demo cases
on Windows, Apple-silicon macOS and Ubuntu 24.04, and owner review/sign-off.
M3.13 consumes every real retained M2 gate except postponed M2.20. Retain native
claim/attempt durability, epoch/PIN/challenge/hash/revocation, recovery and
duplicate-effect prevention. Required missing native/platform evidence fails;
skipped, unrun or component-only results are not passes. Actual hands-on platform
checks remain separate and must complete at their required gates before RC.

`pnpm demo`, `pnpm verify:m3`, content/MIME/native hub/client/web checks and OpenAPI
generation above are planned until their actual owning implementations merge.
Existing root default/docs verification infrastructure does not install those
commands. This backlog adds no script, package, workflow, control or runbook.
Keep component source/coverage, native producer gaps, postponed obligations and
owner/platform evidence distinct. Run results belong in the change review and
gate evidence, not this backlog. The integration owner writes the gate record.
