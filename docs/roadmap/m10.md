# M10 backlog: packaging, headless and mobile

The approved implementation plan, especially sections 7, 11 and the M10 row in
section 12, is the source of truth. M10 follows M4 and receives earlier milestones
through integration. Independent offline tools may be prepared earlier when no
runtime or owner decision controls them. This backlog assigns work; results
belong in PR bodies. M10.12 delivers the gate checks; the gate report is written
after the gate review.
The M9 gate is not a prerequisite: its public doctor checks and M10's local
checks extend M2.11's earlier file-based loader independently. M10.6's later
installed-image L3/proxy case consumes M9 source contracts after propagation;
M9's baseline never waits for M10's installed-artifact evidence.

Each item owns the concrete paths below. Acceptance commands name outputs the
item must add; they do not claim those commands or artifacts exist already.
`tools/fetch-node/versions.json` remains the single Node version bump point.
Contracts and shared-file changes land with their earlier owner before consumers.

## Conventions and verification

Use TypeScript and the shared Vitest unit/heavy tiers. Run shared-machine heavy
and medium commands through the prescribed admission tool; heavy work waits for
the bench lock and at least 6 GB of free RAM. Compose tests use random host ports
and a unique project name under that lock, and remove only their own containers and volumes.
Separately verify the distribution compose file's fixed loopback bindings.

Before a ready PR, run the touched packages' tests, typechecks/builds, changed-file
lint, the item's acceptance commands and `pnpm guard` with zero findings. CI runs
the full suites, including Windows; a local whole-repository `pnpm verify` is not
a prerequisite to submission. Changes to verification, CI policy or workflows
run affected controls locally with attack and mutation checks. Unrelated full
and Windows suites use passing CI at the exact PR head. Review and
auto-merge require `required`, `pr-title` and `review` at the reviewed head. Owner
sign-off supplies DCO at the milestone gate.

On the shared dev box, installer, upgrade, shutdown, restore and desktop-pairing
tests use a test build with a separate identifier and product name, or a named
`--profile` with a separate identifier, data directory and keychain service.
They install per-user into a temporary folder with autostart off, and never
reach a running `com.draftyak.client` instance. In success and failure cleanup,
remove their own uninstall entries, shortcuts, autostart entries, credentials
and data folders, then check for leftovers. Real-identity silent install and
upgrade run only on M10.8's disposable runners. Cases that install, upgrade or
launch a native app are outside plain `pnpm verify`: Rust integration cases use
`#[ignore]`, and the owning heavy wrapper runs them explicitly with `-- --ignored`
under the bench lock. Ordinary Rust tests remain non-mutating. M10.12's strict
gate invokes those wrappers with the isolated development profile.

The repository is public; standard hosted runners have no billed-minutes push
limit. Keep expensive platform builds on the declared triggers and avoid
duplicate installer workflows and matrices.

publication. No image push, npm/PyPI upload or release publication occurs without
explicit owner approval. Manual and scheduled workflows require their files on
the default branch; before the gate use owner-approved `m10-rc-*` tag pushes only
after the M0 workflow-policy prerequisite to M10.8 reaches this branch. The release environment and remote
CI dispatch remain owner controlled. M10.12 runs the local Windows milestone gate.

## Earlier CLI and shared-file contracts

M2.11 creates `apps/cli` and its package/config/lock skeleton, argv handling and
file-based command dispatcher. New commands add files rather than rewrite a
shared command list. Its `apps/cli/src/payload-contract.ts` defines a self-contained
`dist/main.mjs` payload, staged as `cli/main.mjs`, exporting `main(argv)` that
returns the exit code (directly or asynchronously). Importing it does not run it;
stdout is reserved for MCP when bridging. M8.1/M8.4 and every M10 distribution
consume that contract after actual M2.11 merge and branch propagation.

M2.11 also owns `packages/bounded-files/**`: one bounded regular-file reader,
portable path/record validators and descriptor-ownership handling. Callers retain
their own selection, exclusions and size policies. The owner adds
`/packages/bounded-files/ @nicksavov` to M11's existing `.github/CODEOWNERS` after
this backlog merges; M10 creates no CODEOWNERS file. No second reader, record
format or caller-selected runtime manifest is added.

Command ownership follows the feature: M2.11 delivers `unlock` and native control
commands; M3 delivers `serve --test-upstreams`; M4 delivers `pair` and `login-code`;
M8.1/M8.4 deliver `mcp` and `mcp add`; M9 delivers `doctor --public` checks. M2.11
also creates `doctor` and its file-per-check loader under
`apps/cli/src/doctor/checks/`. M9 and M10 each add check files, without a shared
registration line or a dependency on one another. M8.1 and M8.4 list M2.11 under
Depends on. M10 adds only the commands and checks below.

## M10.1 Offline doctor

- **Goal:** diagnose the native Node process and optional data directory without
  opening or enumerating user data.
- **Inputs:** `tools/fetch-node/versions.json` and the plan's inspector,
  data-directory, environment-key and Temporal rules.
- **Outputs:** a TypeScript source-checkout command and importable fixed-code
  diagnostic report, initially with a private known-sync-folder predicate.
- **Owns:** `tools/doctor/**` and its lockfile importer. No shared diagnostics
  package, public-listener check, artifact manifest or support bundle.
- **Acceptance:** `pnpm --filter @draftyak/doctor typecheck` and
  `pnpm --filter @draftyak/doctor test`; linked invocation reports and refuses
  correctly, while importing the entry does not execute it. Unsupported Node
  refuses before diagnostic import. Cover permission scopes, normalized positive
  and negative signal flags, and all configured OneDrive names. Known/configured
  synced paths fail with `DATA_DIR_SYNCED`. Aliases, malformed paths and unreadable
  metadata fail with their own fixed codes. Only `typeof Temporal === 'undefined'` warns for Temporal;
  `DRAFTYAK_MASTER_KEY` produces a content-free warning. No paths or secret values
  appear in reports. Turbo hashes the external runtime policy; tests use Vitest.
- **Depends on:** merged M0 runtime policy and M1 package conventions. M10.11
  later replaces the private predicate after actual M2.11 propagation.

## Changed since the plan

Doctor's predicate stays private until M2.11 propagates, then M10.11 removes it;
no shared diagnostics package is added. M2.11 owns the earlier CLI contract and
bounded reader so M8 and M10 consume dependencies in branch order. Bundle/npm/
release ownership is separate. No-publish dry runs report publishing-only
attestations/provenance as not applicable; launch enables them in publishing
steps. The real-Mac release-candidate install remains section16's owner action.

The current submission rule uses touched-package checks, acceptance and guard
before a ready PR, with full suites in CI. Reviewed heads merge through required
checks and auto-merge; only the owner applies gate sign-off. Standard public
runners remove the former private billed-minutes constraint. M0 owns the narrow
release/mobile tag policy before M10 consumes it. The integration owner writes
the gate report after the gate review.

W4 leaves M2.11's startup refusal stricter than section7 pending the M2 review;
M10.11's acceptance follows the recorded answer, while doctor retains refusal.
Container L1's explicit mode consumes M3.7's admin-authorized configuration and
preserves Host/Origin enforcement at the mapped port. ADR0012's fallback consumes
the conditional M1 KeyClass contract. M10.13a-M10.13c place M8/M8b release-dependent
checks in M10 after M10.8, preserving forward-only dependency order. M10.14 does
the same for M4.20's desktop release assertions, in a separate module with actual
release-build controls and deliberate refusal mutations.

## Deferred

`doctor --bundle`, automatic backups, release code signing, auto-update and app
stores remain deferred unless the owner changes the plan. Ad-hoc DMGs are part
of M10.5, not release code signing.
