# M11 backlog: launch readiness

> **Status:** backlog established; launch readiness remains open. M11.1's community baseline (#64) and contribution guidance (#92) are merged. Documentation infrastructure, launch validation, the release candidate and owner sign-off remain open.
> **Source of truth:** the approved implementation plan, kept outside the repository. Section numbers below refer to that plan. Recorded owner decisions take precedence where they amend it.
> **M11 is done when** (§12): the owner completes the §14 runbook on Windows with real accounts; every supported scaffolder kind and language passes its own CI; documentation builds and link checks pass; the release candidate passes the automated gate and the owner signs off. Publication requires separate, explicit owner approval.

## Inputs and boundaries

- M11 depends on all preceding milestone gates. Documentation can start from M1, but it must distinguish available behavior from requirements still waiting for implementation or an owner decision.
- M0's live sessions and their runbooks remain with the M0 owner. M11 assembles the release check; it does not replace their results or authorize new live sessions.
- Python work is conditional on the owner's S11 decision. SMS host work is conditional on the owner's S12 decision and M6b completion. On a no-go, remove the corresponding launch claims and checks with an explicit reason; do not count them as passing.
- Sign-in implementation and its UX are outside this backlog's implementation scope. The owner supplies the protected sign-in check for §14 step 8. Its absence remains an open release gate.
- Protocol, schema, vector and shared protocol crate changes belong in M1. Product fixes found during launch checks return to their owning milestone; M11 does not silently patch those paths.
- No production account, message, calendar, address, token, private key or local filesystem path belongs in committed examples, reports or fixtures. Fakes use synthetic values. Reports retain only counts, versions, test identifiers and pass/fail facts.
- Sending reports, vendor requests or other messages is an owner action. Use only the contacts already approved in the community documents.
- Nothing here adds post-MVP features. In particular, no mobile approval, recurring sends, cloud backup, plugin index, auto-update, store listing or `doctor --bundle` is included.

## Command and ownership conventions

Each item is a PR into `m11`, with its tests and only its declared paths; related items may share a PR when they form one coherent change. Prerequisites must already be merged into the base. Rebase onto the current base before submission, install from the frozen lockfile, run touched-package checks, the item's applicable acceptance checks and `pnpm guard`, then open the PR ready. Changes to controls that decide what runs, skips or passes require every affected check locally, with boundary attacks and mutation proofs. Preserve mandatory test exclusions. Exact-head full/Windows CI supplies unrelated suites; no blanket local `pnpm verify` is required before a ready PR. Missing, skipped or failed evidence is not a pass. Integration verification retains all default local steps with the exclusions; milestone gates retain applicable profile, platform and owner checks. DCO remains open until the owner's milestone sign-off. GitHub merges after the required checks and the current-head review pass; only the owner applies sign-off.

Commands below are **acceptance obligations, not results**. `pnpm verify`, `pnpm guard`, `pnpm adr` and `node tools/verify/verify.ts --profile docs` already exist. The docs app, launch-check package and `pnpm verify:m11` are introduced by the items named below. A missing command or prerequisite fails the gate; it is never a successful no-op. Conditional checks must state the owner's decision and the excluded scope.

M11.2a introduces the working private `@draftyak/launch-checks` package with its metadata implementation and unit tests. Its later `docs`, `community`, `privacy`, `threats`, `performance`, `migrations`, `templates`, `issues`, `terms`, `runbook` and `candidate` scripts are added only with their implemented modules by their owning items; no empty modules or placeholder scripts are introduced. Each command refuses missing inputs and stale or unrelated results. Verification must use exact current source and artifact versions; historical results do not establish a current pass. Where an item owns `src/<module>.ts` "and tests", its unit-test path is exactly `tools/launch-checks/test/<module>.test.ts`; any additional fixture path is listed in the item.

M11.2a establishes the launch-check package files. Each later check owner appends only its named script in `tools/launch-checks/package.json`, without changing other entries or dependencies. M11.3 additionally owns its implemented docs-check export, exact required dependency additions and README section, with their normal generated lockfile closure. Serialize these edits after the preceding merge. Checks own their command entry modules; no item edits a shared CLI registry. M11.2a's metadata module is consumed by M11.1's `community` entry, so that entry follows M11.2a; complete community acceptance still requires the shipped quickstarts and release disclosures. Any additional shared-file change needs its own declared scope.
