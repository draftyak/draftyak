# M6 backlog: Slack

M6 connects Slack through native approval, broker, sync and retention services,
following plan sections 3–5, 9 and 12–14. This backlog assigns work and acceptance;
it reports no implementation or completed milestone. Shared M1/M2/M3 services,
the SDK/runtime contracts and ADR 0008 remain dependencies. The Slack installation
UI joins the single React SPA in `apps/web`; trusted token entry follows M4's
native approval-window admin hooks, and CLI installation can precede it. Written
Slack confirmation and legal review are M11 launch gates, not M6 fake acceptance.

## Conventions and accepted changes

2's stack; Tauri bundles that SPA. Tokens are entered only through the CLI or

## Frozen send inputs and claim handoff

Derive canonical `DraftAuthorKind` entries from the merged snapshot's frozen
`source.authors` records, never a client `origin` label. Only all-owner
text preserves deliberate markup; any `ai`, `agent` or `plugin` contribution
escapes the whole body in `&`, `<`, `>` order. The shared snapshot accepts
1–100 author records. Any narrower component admission ceiling is local,
not a replacement contract, and must surface before approval.

Use frozen `body.text` and `body.footer`. Empty footer adds nothing; otherwise
append exactly one LF and the always-literally-escaped footer, preserving
existing layout. Claim uses no current footer setting or editable revision.
The renderer's broadcast input binds merged `chat.broadcast`. The proposed
wire behavior emits `reply_broadcast:true` only for a true thread reply and
omits the field otherwise. This extends plan section 4 for section 9.3's
explicit broadcast intent and remains pending the owner's decision. Until
that decision, do not add the field or silently discard an approved true
broadcast intent; hold the affected proposal rather than send altered intent.

M6.5 renders during proposal/freeze and refuses before approval for noncanonical
text, post-escape 40,000-code-point overflow, 128 KiB UTF-8 body overflow or any
other render failure. Some draft-schema-valid text cannot pass these local
limits. Preserve the same frozen body, authors, thread/channel and broadcast
through approval and claim re-rendering.

Slack has no json-template approved render hash. At claim the hub re-renders
from the snapshot; the broker compares actual plugin method, URL, body/header
hashes to that native claim render and consumes one ticket. Never invent a
Slack snapshot render hash. Native injection, blob/reference carriage above a
smaller frame cap and evidence of request-byte writes remain broker-owned.

At proposal enforce at most 100 scheduled items per account and 30 per channel
in five minutes. Native execution is serial per account, immediate sends first,
with at least one second between sends to a channel. Retain those bounds and
current account mode/epoch/policy/approver checks at claim/retry. Every scheduled
claim and every retry needs complete ten-second bounded info plus history or
replies reads since the watermark (limit 20), then the shared transactional
hold-if-reply check. Scheduled sends use both clock/window checks, with the
second clock from the broker-observed Date plus monotonic time; immediate sends
use the hub clock. A failed or incomplete read retries later and eventually
misses; it never stands in for fresh facts. A Retry-After past the delivery
window becomes NEEDS_REAPPROVAL (`missed`), never a late send. Reconciliation
compares the provider's stored rendered form, including footer, and exact
attempt identity rather than unrendered text.

## Channel-facts codec and preflight

Approved input uses the merged frozen chat shape: `channelId`, `channelName`,
`channelType`, `external`, `memberCount`, optional `threadTs`, and `broadcast`.
`broadcast:true` requires `threadTs`; no approved `shared` field exists. Invent no
approved sharing/archive/membership facts. Native snapshot validation and a
successful bounded read using the owner's token remain caller preconditions;
the helper attests neither identity nor freshness.

Current fields are `channelId`, `type`, `external`, `memberCount`, `archived`,
`member` and a nullable direct-conversation name. A strictly validated optional
`pendingExternal` boolean is a local current-only conservative restriction,
not a new shared wire or frozen field. True always means `channel_changed`,
even when approved `external` was already true. Separate org-wide sharing
tracking still needs the owner/M1 frozen-fact decision.

The codec reads fixed own enumerable data descriptors from a plain
`ok:true`/`channel` envelope and returns detached frozen facts. Type precedence:
`is_im` → `dm`; `is_mpim` → `group_dm`; `is_private`/`is_group` → `private`; else
`public`. MPIM's documented simultaneous `is_group`/`is_mpim` is admitted. ID
prefixes do not create type facts; present flags must be primitive booleans.
Proxies, selected getters and malformed data refuse without invoking them.
Topic/purpose/message/identity branches remain unread; native transport bounds
and parses response bytes first.

Public/private channels require nonempty bounded name/count/archive/membership and
external-sharing facts. Compare names only for channels; archive, lost
membership, new external status, pending sharing or count growth both strictly
over 10% and at least three members blocks claim. Never copy current sharing
into the approved snapshot to make it pass.

Sparse IM names map to null and fixed member count two. Missing MPIM count maps
to zero as an unknown-count sentinel, not a measurement. DM/MPIM names and count
growth are not compared because these conversations cannot grow in place. A
successful owner's-token read supplies membership when the direct shape omits
it; explicit false still blocks. Absent direct archive state maps to false.
External/pending flags still restrict direct types. Explicit frozen/read-only/
thread-only restrictions refuse rather than erase a posting restriction.
M6.2 fixtures must use documented sparse objects, not artificial complete DMs.

Hold-if-reply uses exact timestamp ordering, including an absent prior inbound
watermark; channel change takes precedence. Facts/display data never become
render bindings. One-billion-member and 256-unit-name ceilings are local helper
admission limits, not new shared schema bounds.

## Retention, revocation and policy acceptance

M6.7 enforces the plan's minimum necessary retention and rolling 90-day cap.
Daily purge removes messages, bodies, FTS, contacts and `tool_runs` whose newest
activity is older than 90 days; terminal Slack drafts and outbox rows follow the
same rule, including NEEDS_REAPPROVAL. A valid SCHEDULED row remains, and a
scheduled reply still renders from its frozen snapshot after local thread purge.

Only hub-observed `app_uninstalled`/`tokens_revoked` or a hub-made `auth.test`
answer of `token_revoked`/`invalid_auth` establishes revocation. A plugin's
`AUTH_REVOKED` triggers the native check, never purge by itself. Disconnect is
an admin operation; confirmed revocation and disconnect first cancel APPROVED,
SCHEDULED and RETRY_WAIT items. Then stop the plugin, revoke both user and app
tokens through the native path, offer the internal-app deletion link, purge in
batches, run incremental vacuum and audit deletion counts. The plan requires
observed-revocation purge within 14 business days. Delete the relevant
pre-migration snapshots, and list existing backup files still containing the
account so the owner can delete or recreate them; do not promise automatic
deletion from external backups. Contacts, FTS, blobs, context presets, consents
and `tool_runs` all participate. Slack export is age-encrypted JSONL.

Classify credentials and account rows as `slack.metadata`; preserve data classes
on drafts, outbox and attempts. Synced content is absent from every backup;
targets refusing `slack.*` receive no Slack rows. Paid backups and push content
exclude `slack.*`, and Slack features are never gated behind payment. Acceptance
includes the refusing-BackupTarget canary through the shared M2 owner.

Slack data never trains a model. Non-local destinations require the plan's
provider-named opt-in and training-off acknowledgement, and may-train
destinations are refused. Slack-derived tool values also require provider-named
consent; their results are job-scoped and never stored. M6 preserves data classes
and consumes the accepted native broker/routing/consent hooks without taking
ownership of them. Provider/tool integration checks join in M7/M7b when those
features land, in whichever stream lands last. Do not use Slack's Real-time
Search API or Slack-provided MCP server.
